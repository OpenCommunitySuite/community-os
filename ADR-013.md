# ADR-013 — Runtime architecture, границы модулей, приложений и API

**Статус:** Proposed / Предложено
**Язык документа:** русский

---

## Контекст

ADR-001–ADR-011 определили предметные контексты, их семантику, правила, историю, идентичность, доступ и интеграционные границы Community OS. ADR-012 принял commercial multi-tenant SaaS, Control Plane, Community Placement и lifecycle как первые технические границы Stage K.

Следующий технический шаг должен определить структуру runtime и приложений так, чтобы предметные границы сохранялись без искусственного превращения каждого bounded context в отдельный process, service, schema или deployment unit.

Community OS должен начинаться как logical modular monolith. Web/API и persistent background workers должны иметь общую application/domain основу, но независимо запускаемые entry points. Внутренние modules должны взаимодействовать через явные contracts, не используя shared PostgreSQL как скрытый API. Web, Public API, Telegram и integrations должны использовать общую application logic, сохраняя разные transport contracts и lifecycle compatibility.

## Проблема

Без явной runtime architecture modular monolith может превратиться в loose monolith с прямыми ссылками на internal classes, repositories и tables. Обратная крайность — premature microservices, internal HTTP и broker между всеми modules — создаст operational complexity, distributed failure и ложную физическую изоляцию до появления соответствующей необходимости.

Также требуется избежать смешения:

- bounded context и technical module;
- domain entity и API DTO;
- synchronous coordination и event notification;
- semantic event и durable delivery;
- application transaction и HTTP request;
- shared database и public module contract;
- projection и source of truth;
- process-specific coordinator и universal Workflow Engine;
- Shared Kernel и общий каталог domain entities;
- technical authorization coordination и ownership domain admissibility.

## Область решения

Настоящий ADR определяет:

- logical modular-monolith baseline;
- категории technical modules и runtime hosts;
- practical layered architecture и направления зависимостей;
- public application contracts и encapsulation modules;
- command/query semantics;
- synchronous coordination и event taxonomy;
- logical transaction boundaries;
- cross-module reads, read models и projections;
- process-specific coordinators;
- Web/API Host, Worker Host и workload classes;
- federated ownership Web API, Public API и Integration Contracts;
- compatibility classes contracts;
- minimal Shared Kernel;
- acyclic module dependency graph;
- Control Plane module boundary;
- coordination technical authorization и domain admissibility;
- architecture enforcement principles.

Настоящий ADR не определяет physical database schemas, RLS details, authentication implementation, job/outbox/inbox storage, deployment topology, implementation stack или конкретный module/package catalog.

## Связь с ADR-001–ADR-012

Настоящий ADR технически реализует, но не меняет ownership и семантику ранее принятых контекстов.

Bounded contexts ADR-002 остаются semantic ownership boundaries. Они не отображаются автоматически один к одному на runtime modules, assemblies, services, schemas или deployments.

История и provenance ADR-004 не становятся event stream или operational log. Rules ADR-005 не становятся infrastructure policy engine. Finance, Resource Accounting, Governance, Documents и Communications сохраняют собственные facts и invariants согласно ADR-006–ADR-009.

Technical authorization и domain admissibility остаются различными согласно ADR-010. Integration semantic contract ADR-011 не становится internal application contract. Control Plane, Placement, Subject Identity Anchor и Community lifecycle сохраняют границы ADR-012.

## Решение

### 1. Logical modular-monolith baseline

Community OS использует logical modular monolith со строгими module boundaries и без искусственной physical isolation.

Modules могут исполняться in-process и вызывать public application contracts обычными language-level calls. HTTP, message broker или serialization между внутренними modules не требуются только ради границы.

Module boundary не означает отдельный service, process, database schema или deployment unit. Future extraction в отдельный service допустим только при самостоятельном архитектурном обосновании и не должен менять domain semantics.

Web/API runtime должен быть stateless там, где это практически возможно, и допускать horizontal scaling. Persistent background work выполняется отдельно запускаемым Worker Host.

### 2. Категории technical modules

Архитектура различает следующие conceptual categories:

1. **Functional domain/application module** — cohesive technical boundary, владеющая своими application capabilities, domain internals и implementation details.
2. **Platform functional module** — technical module platform responsibility, включая Control Plane capabilities, но не присваивающая Community domain ownership.
3. **Module Public Contract** — минимальный опубликованный application contract module.
4. **Read Model / Projection** — опубликованное derived read representation.
5. **API/Application Composition** — composition конкретных Web/Public use cases через published contracts и read models.
6. **Runtime Host** — composition root и entry point процесса, но не владелец domain semantics.
7. **Infrastructure Adapter** — реализация persistence, transport или другой technical dependency.
8. **Shared Kernel** — минимальный набор фундаментальных стабильных primitives с повышенным порогом включения.

Эти категории не задают concrete package, project или assembly layout и не требуют одинаковой гранулярности во всех частях системы.

### 3. Practical layered architecture

Используется practical layered model:

```text
Web / API / Telegram
          ↓
     Application
          ↓
        Domain

Infrastructure реализует technical dependencies
Runtime Hosts выполняют composition
```

#### Transport layer

Web/API/Telegram adapters отвечают за:

- transport semantics;
- intake authentication context;
- parsing request или update;
- transport-level validation;
- DTO и protocol representation;
- преобразование transport result/error.

Transport layer не определяет domain admissibility и не работает напрямую с module repositories.

#### Application layer

Application отвечает за:

- orchestration use case;
- logical transaction boundary;
- coordination technical authorization;
- вызов обязательных domain-specific admissibility checks;
- вызов собственного Domain;
- вызов public contracts других modules;
- publication применимых application events.

Application не присваивает ownership domain rules, Power, Representation, Competence или domain admissibility.

#### Domain layer

Domain содержит:

- domain state;
- invariants;
- domain rules;
- domain admissibility, принадлежащую context-owner.

Domain не зависит от HTTP, Telegram, API DTO, ORM, concrete PostgreSQL API, Infrastructure или Runtime Host.

Interfaces и abstractions вводятся для реальной boundary, substitution или testability need. Interface для каждого класса только ради pattern не требуется.

### 4. Направления зависимостей

Разрешённые зависимости направлены внутрь:

- Transport и API adapters зависят от Application contracts/use cases;
- Application зависит от собственного Domain и разрешённых Module Public Contracts;
- Infrastructure реализует ports, требуемые Application или Domain;
- Runtime Hosts знают composition/wiring, но не становятся обходным cross-module API;
- Shared Kernel не зависит от functional или platform modules;
- Module Public Contracts не зависят от internals module.

Functional module dependency graph на compile-time/application level должен быть acyclic.

### 5. Module Public Contracts и encapsulation

Каждый крупный functional или platform module имеет явно определённый public application contract в объёме, необходимом его consumers.

Public contract может включать применимые:

- commands;
- queries;
- result/value contracts;
- published application events;
- declared read models.

Другие modules не используют напрямую:

- internal domain objects;
- repositories;
- implementation classes;
- ORM entities;
- internal persistence details;
- private tables или views.

Физическая доступность class или table не делает её public contract. Public contract должен быть намеренно опубликован и минимален.

### 6. Command и Query

**Command** выражает намерение изменить state.

**Query** получает data и не изменяет domain state.

Это семантическое различие не требует mandatory CQRS framework, CommandBus, QueryBus, mediator library или separate read database. Handlers или use-case classes допустимы, но их concrete arrangement относится к Implementation Baseline.

### 7. Synchronous inter-module coordination

Если для завершения текущего use case необходим немедленный результат другого module, вызывается его explicit synchronous public application contract.

Event не используется вместо обычного synchronous call только для уменьшения видимой coupling. Скрытая temporal coupling через asynchronous response не считается улучшением границы.

Двусторонняя business interaction не оправдывает mutual implementation references. Направление dependencies разрешается через правильно направленные contracts, events, process coordinator или действительно общий stable contract, если он обоснован.

### 8. Event taxonomy

Различаются четыре категории без универсальной сущности Event:

1. **Local Domain Event** — module-local выражение уже произошедшего domain fact/change. Оно не обязано публиковаться или сохраняться durably.
2. **Inter-module Application Event** — минимальный published semantic contract после самостоятельного commit-worthy fact, на который могут реагировать другие modules.
3. **Durable Application Event** — published application event, business-significant reaction на который должна переживать crash/restart.
4. **External Integration Message / Information** — received или transmitted external representation по ADR-011; оно не становится domain/application event автоматически.

Не каждый Local Domain Event становится inter-module event. Не каждый inter-module event требует durable delivery.

Event описывает уже произошедший факт. Намерение выполнить действие выражается Command, а необходимость немедленного результата — synchronous contract.

Event taxonomy не вводит universal Event entity, universal Message, event sourcing или обязательный event bus.

### 9. Semantic event и durable delivery

Semantic event contract и delivery mechanism различаются.

Если reaction business-significant и должна переживать process termination, restart или deployment, delivery должна быть durable, а handling — idempotent. Outbox или equivalent accepted mechanism обеспечивает границу local domain transaction и asynchronous continuation.

Durable delivery не означает universal exactly-once. Job storage, outbox/inbox schema, lease, retry, ordering, deduplication, broker и serialization определяются ADR-016.

### 10. Application transaction boundary

Transaction boundary принадлежит Application use case, а не repository и не всему HTTP request автоматически.

Одна application operation может атомарно изменить несколько aggregates, repositories или modules только если одновременно выполнены условия:

- это одна cohesive local business operation;
- все данные находятся в одной фактически resolved transactional storage boundary;
- module owners участвуют через public contracts;
- transaction не пересекает Community Placement;
- transaction не пересекает platform/community storage boundary;
- external systems и object storage не включены;
- long-running steps не включены;
- correctness не обещает future distributed atomicity.

Shared PostgreSQL является необходимым, но недостаточным условием cross-module local atomicity. Его физическая общность не оправдывает arbitrary mega-transaction или обход ownership.

External API, Telegram, bank, DNS, object storage и long-running/background operations используют local commit и durable continuation, reconciliation или другой context-specific mechanism. Distributed transaction с ними не вводится.

Physical transaction implementation, schemas, RLS и connection/session mechanics принадлежат ADR-014; durable continuation — ADR-016.

### 11. Cross-module operational reads

Обычный operational use case читает data другого module через public application query contract owner module.

Прямой cross-module read internal tables запрещён. Cross-module JOIN по internal tables не становится API только потому, что PostgreSQL общий.

### 12. Read Models и Projections

Для dashboards, reports, search, complex read-heavy queries и BFF composition допускаются explicitly published read models/projections.

Каждая projection:

- derived и не является source of truth;
- имеет declared producer/owner;
- имеет определимый Community/tenant scope;
- имеет visibility/authorization semantics;
- имеет declared freshness/consistency expectation;
- является read-only для consumers;
- не используется для command-side mutation domain state;
- rebuildable там, где это допускают source facts и semantics.

Stale projection не может grant Access Right, Power или domain admissibility и не может подтверждать irreversible operation, когда требуется current authoritative state.

BFF, Public API, reports и search используют projection только в пределах её declared semantics. Physical storage, rebuild strategy, indexes и isolation projection относятся к ADR-014; freshness monitoring — к ADR-017.

### 13. Process-specific coordinators

Для действительно complex multi-step process допустим specialized application-level process coordinator.

Coordinator:

- принадлежит конкретному named use case/process;
- не является universal Workflow Engine или universal State Machine;
- не владеет domain facts участвующих modules;
- использует public application contracts и published events;
- хранит только необходимый orchestration progress/context;
- является persistent/resumable для long-running process;
- допускает retry, recovery и idempotent steps, где они требуются;
- не предполагает distributed transaction с external systems.

Coordinator не требуется для каждого multi-module call.

Provisioning и Community relocation могут иметь Control Plane coordinators согласно ADR-012. Import и bank reconciliation используют собственную integration/Finance semantics ADR-006/011. Onboarding или Go-Live используют coordinator только там, где process действительно multi-step; это не создаёт общий onboarding workflow engine.

### 14. Runtime Hosts

Baseline имеет два separately runnable runtime entry points:

- **Web/API Host**;
- **Worker Host**.

Оба используют общие Application/Domain modules и contracts одного application release. Они могут независимо запускаться, перезапускаться и масштабироваться и могут иметь разные infrastructure permissions.

В Development допускается совместный запуск для удобства. Это не меняет architecture boundaries.

Runtime Host является composition root, а не domain owner. Наличие module в Host не делает его internals доступными другим modules.

### 15. Web/API Host

Web/API Host принимает Web API, Public API, Telegram или другие supported interactive/HTTP entry points в пределах configured adapters.

Shared API host/composition responsibility включает:

- routing;
- technical authentication integration;
- common versioning mechanics;
- correlation;
- common error representation;
- publication/composition API surfaces.

API Host не владеет business rules и не заменяет functional modules.

### 16. Worker Host и workload classes

Worker Host выполняет persistent/background work через те же Application contracts и Domain rules.

Worker не получает право:

- обходить Application/Domain boundaries;
- читать private module tables;
- игнорировать Community/tenant scope;
- использовать service credentials как authorization bypass;
- игнорировать Placement resolution или Placement Generation;
- подменять attribution semantics ADR-004/010/012.

Один общий Worker runtime поддерживает logical workload/queue classes. Worker instance может обслуживать один или несколько workloads, а workloads могут масштабироваться независимо.

Workload class является technical execution category, а не bounded context, domain module или data owner. Exact workload names, topology, CLI и queue implementation не определяются.

### 17. Federated API ownership

Functional module владеет semantics собственных application/API operations и соответствующих contracts в пределах этого ownership.

Общий API Host владеет publication/composition mechanics, но не присваивает domain semantics. Domain entity не является автоматически API DTO.

Один module может предоставлять application capabilities нескольким API surfaces, но endpoints, DTO, compatibility и lifecycle этих surfaces не обязаны совпадать.

Cross-module API operation допустима как явно owned application composition/use case. Composition вызывает public contracts/read models и не становится universal façade над internal repositories.

### 18. Web API / BFF

Собственный Web UI использует логически отдельный Web API/BFF contract.

BFF может:

- агрегировать результаты нескольких modules;
- использовать published read models;
- адаптировать DTO к конкретному UI;
- выполнять transport/application composition.

BFF не владеет business rules, не читает internal tables modules и не становится universal domain façade.

Отдельный physical BFF service не требуется. В initial implementation BFF может находиться в том же deployable application.

### 19. Public API

Public API является самостоятельным external contract, отличным от Web API и Internal Module Application Contracts.

Breaking changes Public API не выполняются silently. Требуются explicit compatibility/version policy и deprecation policy; old version может поддерживаться в transition period.

Exact version transport — URL, header или другой механизм — не определяется.

### 20. Integration Contracts

Integration Contracts имеют самостоятельную integration semantics, versioning и lifecycle согласно ADR-011.

Integration adapter может вызывать те же Application use cases, что Web/Public API, но external protocol DTO, received information, mapping и domain recognition не становятся internal module contract автоматически.

### 21. Contract compatibility classes

Различаются:

```text
Domain Model Version
≠ Internal Module Application Contract evolution
≠ Web API compatibility
≠ Public API Version
≠ Integration Contract Version
≠ Application Release Version
```

#### Internal Module Application Contracts

Long-term versioning обычно не требуется, поскольку producer и consumers выпускаются одним immutable release artifact. Breaking internal change допустим, если все consumers обновлены together в одном release.

#### Web API

Web API эволюционирует вместе с own Web UI и по умолчанию не обещает long-term backward compatibility. Transitional compatibility window требуется только если deployment model допускает временную работу старого client с новым backend.

#### Public API

Public API имеет explicit version, compatibility и deprecation policy.

#### Integration Contracts

Версионируются независимо в соответствии с ADR-011.

Same-release update internal contracts не обещает safe mixed-version Web/Worker deployment. Mixed-version compatibility и rollout mechanics определяются ADR-017.

### 22. Minimal Shared Kernel

Shared Kernel должен оставаться минимальным. Добавление type требует более сильного обоснования, чем небольшое local duplication при различающейся semantics.

В Shared Kernel не переносятся автоматически:

- Subject;
- Object;
- Payment;
- Document;
- Voting;
- User Account;
- Subject Identity Anchor;
- Resource;
- repositories;
- application services;
- shared business rules;
- arbitrary shared DTO.

Shared meaning не означает shared type.

Допустимыми кандидатами могут быть opaque identifiers, correlation и narrow stable technical primitives. Даже Community entity не является Shared Kernel; может быть обоснован узкий opaque Community identifier. Money не считается автоматически universal primitive до определения общей semantics.

Concrete set и representation types относятся к Implementation Baseline и architecture review.

### 23. Acyclic dependency graph

Compile-time/application dependency graph functional modules должен быть acyclic. Hidden mutual implementation reference запрещён.

Business interaction в обе стороны реализуется через correctly directed public contracts, events, process coordinator или действительно общий contract/kernel при достаточном обосновании.

Выделение contracts в отдельный package не устраняет cycle, если contract скрыто зависит от implementations обоих modules.

### 24. Control Plane module boundary

Control Plane сохраняется как separate platform responsibility ADR-012 и технически представлен platform functional modules внутри logical modular-monolith baseline.

Control Plane modules:

- соблюдают те же layers и public-contract rules;
- входят в тот же acyclic dependency discipline;
- проверяются теми же architecture tests;
- не читают internal persistence Community functional modules;
- не присваивают ownership Community domain facts.

Community modules не читают Control Plane internals. Entitlement, Placement и lifecycle information доступны через narrow published platform contracts или read models.

Control Plane process coordinator может вызывать Community initialization/readiness contracts в пределах конкретного process, не присваивая их semantics. Community operations зависят от stable Placement Resolver или Entitlement contract, а не от orchestration implementation.

Отдельный Control Plane service или host не обязателен. Web/API Host и Worker Host могут выполнять соответствующие entry points с применимыми permissions. Возможный третий host или future service является отдельным deployment/evolution decision.

### 25. Authorization и domain admissibility

Transport layer принимает authenticated technical context, но authentication не доказывает Subject, Power или domain admissibility.

Application координирует technical authorization и вызов обязательных domain-specific checks. Context-owner Domain владеет domain admissibility и invariants конкретного действия.

Technical Access Right или Access Role не может override mandatory negative domain result. Domain Power не предоставляет technical access автоматически.

Bootstrap administrator может быть authorized actor platform operation без fake Subject, если это допускают applicable technical authorization и domain admissibility. Worker service identity также не становится Subject и не создаёт bypass.

Настоящий ADR не выбирает RBAC, ABAC, ReBAC, policy engine, token/session или security middleware.

### 26. Architecture enforcement

Architecture as code применяется там, где правило можно надёжно проверить автоматически.

Future CI/architecture tests должны иметь возможность проверять:

- forbidden module dependencies;
- dependency cycles;
- обращение к другим modules только через allowed contracts;
- отсутствие dependencies Domain на Web/API/Telegram/ORM/Infrastructure;
- отсутствие случайной публикации module internals;
- отсутствие dependencies Shared Kernel на functional modules;
- соблюдение Application boundaries Web/API и Worker Hosts.

Нарушение объективно проверяемого architecture rule должно fail CI.

Architecture tests не заменяют semantic architecture review. Вопрос, какому context/module принадлежит конкретная business capability, не выводится автоматически из dependency graph.

Exact architecture-test framework, library и CI implementation относятся к Implementation Baseline.

## Архитектурные инварианты

1. Bounded Context не равен автоматически technical module, assembly, service, schema или deployment unit.
2. Functional module владеет своими internals и публикует explicit application contract.
3. Cross-module access выполняется только через published contracts, read models или events.
4. Internal persistence другого module не является public API.
5. Domain не зависит от transport, ORM, infrastructure или runtime host.
6. Application координирует use case, но не присваивает domain ownership.
7. Context-owner владеет domain admissibility.
8. Shared database не стирает module boundaries.
9. Transaction не пересекает unresolved Placement или storage boundary.
10. External system и object storage не входят в local database transaction.
11. Если нужен немедленный результат, используется explicit synchronous public contract.
12. Event представляет уже произошедший факт, а не скрытый command.
13. Не каждый Local Domain Event публикуется.
14. Published semantic event не означает durable delivery автоматически.
15. Durable delivery не обещает exactly-once.
16. Read projection является derived и не является source of truth.
17. Stale projection не предоставляет права там, где требуется current state.
18. BFF/API composition не владеет business rules.
19. Domain entity не становится API DTO автоматически.
20. Internal Module Contract, Web API, Public API и Integration Contract различаются.
21. Worker не обходит Application/Domain boundaries.
22. Workload является execution classification, а не domain ownership.
23. Process coordinator является process-specific и не становится universal Workflow Engine.
24. Functional module dependency graph является acyclic.
25. Shared Kernel остаётся минимальным.
26. Shared semantic concept не становится shared type автоматически.
27. Control Plane не присваивает Community domain ownership.
28. Control Plane и Community modules взаимодействуют через published contracts/read models.
29. Same-release internal compatibility не обещает mixed-version runtime compatibility.
30. Объективно проверяемые architecture rules должны контролироваться автоматически.
31. Architecture tests не заменяют semantic architecture review.
32. Module boundary не создаёт premature microservice boundary.
33. Technical authorization не преодолевает mandatory negative domain result.
34. Runtime Host является composition root, а не domain owner.
35. Universal Event, Workflow, State Machine или cross-module persistence model не вводятся.

## Последствия решения

### Положительные последствия

- domain ownership сохраняется при простом initial runtime;
- modules развиваются независимо логически без premature distributed system;
- Web и Worker используют одну application/domain semantics;
- cross-module coupling становится явной и архитектурно проверяемой;
- API surfaces могут развиваться с разными compatibility policies;
- read-heavy composition не требует обхода ownership;
- future service extraction возможна без изменения domain semantics;
- Control Plane остаётся отдельной responsibility без premature microservice;
- durable work может развиваться отдельно от semantic events.

### Цена и риски

- module boundaries требуют дисциплины и architecture tests;
- неправильно спроектированные public contracts могут создать central coupling;
- cross-module synchronous call chains могут стать скрытой runtime coupling;
- projections требуют явной freshness и visibility semantics;
- shared transaction удобна, но может затруднить future decomposition при чрезмерном использовании;
- minimal Shared Kernel требует осознанного local duplication;
- separate Web/Worker entry points требуют release compatibility discipline;
- in-process boundaries легче случайно нарушить, чем network boundaries.

## Рассмотренные и отклонённые альтернативы

### Loose monolith с прямыми internal references

Отклонено: shared process и database не должны стирать ownership или превращать implementations в public API.

### Bounded Context автоматически равен service, schema или microservice

Отклонено: нарушает ADR-002 и создаёт premature physical decomposition.

### Internal HTTP everywhere

Отклонено: transport не улучшает semantics boundary автоматически и добавляет distributed failure.

### Message broker между каждым module и event-driven everything

Отклонено: immediate result требует synchronous contract; event описывает уже произошедший fact. Broker и durability не являются semantic boundary.

### Mandatory CommandBus, QueryBus или full CQRS

Отклонено: Command/Query различаются семантически без обязательного framework или separate read database.

### Shared database как cross-module API и arbitrary JOIN

Отклонено: physical access не предоставляет semantic ownership. Для reads используются owner contracts или published projections.

### Universal Workflow Engine или State Machine

Отклонено: coordinators принадлежат конкретным processes и не создают universal lifecycle.

### Universal Event entity

Отклонено: local domain, published application, durable и external integration events/messages имеют разные ownership и semantics.

### Giant Shared Kernel / Common Model

Отклонено: размывает module ownership и создаёт глобальную связанность; local duplication безопаснее при различающейся semantics.

### Domain entities как REST DTO

Отклонено: transport representation и domain model имеют разные boundaries и compatibility.

### Один универсальный API contract для Web, Public API и integrations

Отклонено: consumers, compatibility и semantic contracts различаются.

### Worker с privileged domain bypass

Отклонено: background execution обязано соблюдать те же Application/Domain и authorization/admissibility boundaries.

### Отдельный physical service для каждого workload с первого дня

Отклонено: workload является execution category; один Worker runtime допускает independent workload scaling без service proliferation.

### Premature Control Plane microservice

Отклонено: separate responsibility реализуется platform modules logical modular monolith; future extraction требует отдельного основания.

### Distributed transaction с external systems

Отклонено: external actions используют durable continuation и reconciliation после local commit.

## Намеренно отложенные решения

### ADR-014 — Persistence, isolation и storage

- physical PostgreSQL schemas, tables и ownership mapping;
- RLS policies, database roles и tenant isolation mechanics;
- connection/session и transaction implementation;
- physical projection storage и rebuild mechanisms;
- files/object storage;
- backup, restore и recovery.

### ADR-015 — Authentication, authorization и security

- built-in authentication и OIDC implementation;
- tokens, sessions и credentials;
- RBAC/ABAC/ReBAC или policy enforcement engine;
- authorization middleware/enforcement points;
- secrets/KMS и encryption implementation;
- security audit implementation.

### ADR-016 — Reliable background work и integrations runtime

- persistent job storage;
- lease, visibility и heartbeat;
- outbox/inbox physical implementation;
- retries, ordering и deduplication mechanics;
- broker или queue library;
- integration adapter runtime.

### ADR-017 — Deployment и operations

- physical deployment/process topology;
- mixed-version rollout compatibility window;
- CI/CD implementation;
- runtime scaling topology;
- observability stack;
- production operational readiness.

### Implementation Baseline

- programming language и frameworks;
- project, package и assembly layout;
- concrete module catalog;
- ORM, DI и mediator libraries;
- architecture-test library;
- REST routes и API version transport syntax;
- OpenAPI tooling;
- event serialization format;
- workload names и CLI;
- exact Shared Kernel types.

## Совместимость с ADR-001–ADR-012

### ADR-001 и ADR-008

Voting Right, Vote, Governance Result и Governance Decision остаются domain concepts. Technical modules, events, DTO и projections не создают или не изменяют их semantics.

### ADR-002

Bounded contexts сохраняют semantic ownership и не отображаются автоматически на modules/services/schemas. Technical modules защищают, а не заменяют эти границы.

### ADR-003

Community Configuration не становится runtime module или deployment configuration. Profile и configured values сохраняют собственную semantics.

### ADR-004

Domain history/provenance не равна event stream, outbox или operational log. Events не вводят universal history mechanism; automatic work не создаёт fake Subject.

### ADR-005

Rules и Rule Versions остаются domain-owned. Application orchestration и technical policy mechanisms не становятся универсальным Rule owner.

### ADR-006

Finance владеет Payment, Allocation, Charge, Financial Obligation и Expense. Module/API contracts не объединяют эти concepts и не позволяют другим modules изменять Finance persistence напрямую.

### ADR-007

Resource Accounting владеет Reading, Consumption, Meter и Accounting Point. Telemetry adapter и external message не становятся Reading или Resource domain event автоматически.

### ADR-009

Document, Revision, Representation, File, Publication, Notification и Delivery сохраняют различия. API DTO, object storage и delivery workload не присваивают их semantics.

### ADR-010

Application координирует technical authorization и mandatory domain checks, но domain admissibility остаётся у context-owner. User Account, Subject, Power и Access различаются; Worker/bootstrap actor не требует fake Subject.

### ADR-011

Integration Contract и external information отличаются от internal Module Contract/Event. Transport, mapping, recognition и domain fact сохраняют отдельные boundaries.

### ADR-012

Control Plane реализуется platform modules без присвоения Community domains. Placement resolution ограничивает local transactions и background work. Web/Worker сохраняют Community scope и Placement Generation contract.
