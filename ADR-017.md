# ADR-017 — Production delivery, observability and operational readiness

**Статус:** Proposed / Предложено
**Язык документа:** русский

---

## Контекст

ADR-012–ADR-016 сформировали техническую архитектуру Community OS до production operations boundary. Приняты commercial multi-tenant SaaS, Control Plane, Community Placement и Placement Generation; logical modular monolith с независимо запускаемыми Web/API Host и Worker Host; PostgreSQL и S3-compatible object storage; tenant isolation, backup/recovery и schema evolution; authentication, Workload Identity, Secrets и Security Audit; Persistent Work, at-least-once exposure и durable compatibility.

Для production остаются открытыми общие свойства deployment, availability, mixed-version rollout, runtime health, maintenance/degraded operation, Control Plane outage, observability, capacity/failure containment и privileged operational changes. Без них конкретный Implementation Baseline вынужден был бы принимать архитектурные решения неявно.

## Проблема

Необходимо определить, как Community OS доставляется и эксплуатируется в первом production:

- какие failures runtime должен переносить и где начинается DR;
- когда допустим rolling deployment, а когда maintenance window безопаснее;
- как связаны artifact, environments, configuration и authorization promotion;
- что происходит при недоступности Control Plane или иных dependencies;
- как instance принимает/прекращает traffic и Persistent Work;
- какие operational signals и alerts обязательны;
- как выполняются privileged changes, emergency actions и restore verification;
- как capacity/failure containment сохраняют multi-tenant semantics.

Решение должно быть достаточно определённым для Implementation Baseline, не выбирая конкретную инфраструктурную технологию.

## Область решения

ADR определяет:

- first-production failure-domain и availability posture;
- Web/API и Worker scaling/deployment properties;
- hybrid rolling/maintenance deployment;
- bounded mixed-version и schema/work-contract compatibility;
- Development, Staging и Production boundaries и immutable artifact promotion;
- Control Plane outage behavior и bounded cached resolution;
- scoped Operational Maintenance / Degraded Mode;
- Startup, Runtime Readiness, Liveness и Draining;
- observability и actionable alerting baseline;
- production change, emergency и DR governance;
- measurement-driven capacity, scaling и failure containment;
- operational integration backup/restore, Placement/relocation, Secrets и Security Audit.

## Не является целью

ADR не выбирает hosting/cloud provider, orchestrator, container/runtime technology, operating system, CI/CD product, registry, load balancer, PostgreSQL HA/failover product, connection pooler, cache, broker, scheduler, observability stack, DNS/TLS product, secret manager, backup tool или exact runbook implementation.

ADR не определяет exact replica count, autoscaling formula, capacity number, alert threshold, probe endpoint/protocol, drain/lease timeout, cache TTL/invalidation protocol, rollout percentage, maintenance schedule, restore-drill frequency или approval UI.

ADR не вводит universal Deployment, Runtime, Health, Alert, Incident, Environment или Infrastructure domain entity и не изменяет domain model, Community lifecycle, Persistent Work semantics или module boundaries.

## Ключевые различия

```text
Runtime Readiness
≠ Community Readiness
≠ Capability Readiness

Operational Maintenance / Degraded Mode
≠ Community lifecycle state
≠ Subscription lifecycle
≠ domain admissibility

Application rollback
≠ Schema rollback
≠ restore / PITR
≠ Selective Community Recovery
≠ domain Correction
≠ process Compensation

Operational Log
≠ Metric
≠ Trace
≠ Security Audit
≠ Domain History / Provenance
≠ Integration Provenance
≠ Persistent Work state
```

Operational health является technical condition, а не domain fact. Deployment и failure не меняют молча domain facts или historically significant attribution.

## Связь с ADR-001–ADR-016

- Автоматизация/Workload не становится Subject; историческая attribution и corrections сохраняются (ADR-001, ADR-004, ADR-010).
- Deployment topology не переопределяет bounded contexts, modules или domain ownership (ADR-002, ADR-013).
- Configuration/rules/mapping versions сохраняют ownership и historical determinability (ADR-003, ADR-005, ADR-011).
- Finance, resource recognition, governance и communication lifecycle не выводятся из telemetry/logs/provider health (ADR-006–ADR-009).
- Control Plane, Community lifecycle, Placement/Generation и relocation остаются authoritative semantics (ADR-012).
- Web/API и Worker используют Application/Domain boundaries, а mixed-version policy не превращает internal storage в API (ADR-013).
- Persistence, RLS, migrations, backup/recovery, RPO/RTO и object storage сохраняют ADR-014 semantics.
- Workload Identity, current-sensitive authorization, Secrets, privileged access и Security Audit сохраняют ADR-015 boundaries.
- Persistent Work/Operation/Attempt, outbox/idempotency, Unknown Outcome, cancellation и compatibility сохраняют ADR-016 guarantees.

## Решение

### 1. First-production availability и failure domain

Первый production развёртывается в пределах одного основного **Failure Domain** / региона. Multi-region production не является требованием первого этапа и явно deferred.

Architecture не зависит от единственного экземпляра Web/API Host или Worker Host. Stateless-where-practical Web/API и общий Worker runtime допускают несколько одновременно работающих/replaced instances и independent scaling workload classes.

Для critical persistent services должны быть определены availability, durability, failover/recovery properties, позволяющие достигать принятых operational objectives ADR-014. Настоящий ADR не выбирает physical PostgreSQL/object/job-store topology, число узлов или managed/self-managed realization.

Потеря отдельного replaceable Web/API/Worker instance не должна сама по себе терять authoritative state, Persistent Work или committed delivery obligation. Потеря всего основного Failure Domain может требовать DR restoration; zero-downtime regional survival не обещается.

Shared Placement failure может затронуть несколько размещённых там Communities. Failure containment означает controlled blast radius и отсутствие unnecessary cascade, а не обещание физически независимого выживания каждой Community внутри одного failed Shared Placement.

### 2. Runtime topology и horizontal scaling

Web/API Host, Worker Host и Control Plane responsibilities сохраняют logical/runtime boundaries ADR-012/013. Их physical co-location или separation не фиксируется.

Web/API instances:

- допускают horizontal scaling;
- не используют instance-local state или sticky affinity как correctness requirement;
- получают authoritative shared state через принятые contracts/persistence boundaries;
- не используют local filesystem как authoritative shared binary/state store.

Worker instances:

- могут исполняться параллельно;
- прекращают/возобновляют claims согласно Runtime Readiness/Draining;
- используют ADR-016 claim/retry/idempotency semantics после process failure;
- не предполагают exactly-once или единственного Worker;
- сохраняют Workload Class fairness/backpressure и tenant/Placement boundaries.

Transport affinity и local caches допустимы как optimization, если потеря instance не нарушает correctness, authorization, revocation или durable state.

### 3. Hybrid deployment и mixed-version behavior

Production использует hybrid deployment model:

- rolling deployment для изменений, удовлетворяющих declared compatibility window;
- controlled maintenance window для изменений, где safe mixed-version compatibility чрезмерно сложна, не доказана или рискованна.

Zero/low-downtime deployment является желаемой capability для compatible changes, но не absolute invariant. Data/domain/security/durable-work correctness имеет приоритет над отсутствием planned downtime. Конкретное время maintenance является operational policy.

Во время rolling deployment old/new versions сосуществуют только в ограниченном, явно определимом compatibility window. New runtime поддерживает разрешённые previous states/contracts, а old runtime не получает несовместимые state/contracts до завершения draining.

Compatibility охватывает как минимум:

- internal/public/integration contracts, которые пересекают version boundary;
- Web/API и Worker interactions;
- schema state;
- Persistent Work payload/contract version;
- outbox/delivery/inbox records;
- configuration/rule/mapping versions, когда они historically relevant;
- security/tenant context contracts.

Schema evolution следует `expand → deploy → backfill → contract`. Contract phase начинается только после прекращения old consumers/instances и обработки, migration или explicit quarantine durable work, которой нужна старая форма. Unsupported work/version fails closed и не интерпретируется молча по новой semantics.

### 4. Rollback, roll-forward и recovery distinctions

Application artifact rollback допустим только если previous runtime совместим с current schema, Persistent Work/contracts и security/config state. Rollback binary не откатывает database или domain history.

Destructive schema rollback не является normal release recovery. Предпочтителен compatible roll-forward/corrective migration; exact response зависит от verified current state.

Не смешиваются:

- application rollback/roll-forward;
- schema migration/correction;
- backup restore/PITR;
- Selective Community Recovery;
- domain Correction;
- ADR-016 Compensation.

Restore не используется как способ отменить ordinary failed release, если это откатывает unrelated valid domain facts. Любое recovery соблюдает authoritative Placement, history/provenance и controlled reconciliation ADR-014.

### 5. Environments и Immutable Artifact promotion

Логически различаются **Development**, **Staging** и **Production**. Это isolation of purpose, data/access/secrets и change authority, а не требование трёх идентичных physical infrastructure комплексов. Development может включать local developer environments.

Release path:

```text
Development / build
→ uniquely identified Immutable Artifact
→ Staging
→ verification
→ explicit Production authorization
→ Production
```

Production использует тот же verified artifact identity; artifact не пересобирается специально после Staging verification. Environment-specific configuration, Secret References/material, endpoints и credentials отделены от artifact.

Production promotion выполняется только authorized operator/process и имеет attributable artifact/change identity, target, result и verification. Настоящий ADR не определяет artifact packaging/registry, environment topology или pipeline product.

Production data/secrets не становятся обычными Development fixtures. Transfer/masking/test-data policy deferred, но tenant/security/data-minimization boundaries обязательны во всех environments.

### 6. Control Plane outage и cached resolution

Control Plane authority не означает synchronous dependency каждого обычного Community data-plane request. Для уже известных Communities допускается bounded, Generation-aware cached resolution/current state, достаточный для clearly safe operations.

Cache:

- не является authority;
- не изменяет stable Community identity;
- содержит/проверяет applicable Placement Generation и freshness evidence;
- не разрешает stale Generation писать в old Placement;
- не выдаёт Access Right/domain admissibility сам по себе;
- при недостаточной уверенности fails closed для sensitive/current-critical operation.

При недоступности Control Plane останавливаются Control Plane mutations, provisioning, relocation и другие operations, для которых нельзя подтвердить current authority/state. Data-plane operation может продолжаться только если её contract разрешает bounded cached state и все остальные tenant/security/domain/persistence gates подтверждены.

TTL, invalidation/replication technology и exact failover implementation принадлежат Implementation Baseline.

### 7. Operational Maintenance и Degraded Mode

Operational state является scoped и capability-aware. Scope может относиться к platform, Placement, runtime component, Workload Class, capability или external provider/integration.

**Operational Maintenance** — controlled operational admission condition для planned/required technical change. **Degraded Mode** — condition, при котором часть capabilities/dependencies недоступна или имеет reduced service, а explicitly safe functions могут продолжаться.

Operational Maintenance/Degraded Mode:

- не является Community lifecycle MAINTENANCE/SUSPENDED/ARCHIVED;
- не меняет Community/Subscription lifecycle;
- не переписывает domain facts/history;
- не подменяет Community Readiness или Capability Readiness;
- не bypass authentication/authorization, mandatory domain admissibility, tenant isolation, RLS/persistence boundaries, lifecycle restrictions или current-sensitive checks.

Architecture стремится сохранять functions, correctness которых доказуема, и блокировать affected operations. Sensitive action при uncertain current state fails closed. Universal read-only mode не обещается: при недоступности authoritative persistence безопасный read path может отсутствовать.

Один global maintenance boolean не является основной моделью. Exact state matrix/notification/UI/automation deferred.

### 8. Startup, Runtime Readiness, Liveness и Draining

Различаются четыре technical conditions:

1. **Startup** — instance инициализируется и ещё может быть не готов принимать работу.
2. **Runtime Readiness** — instance способен принимать новую работу своего типа.
3. **Liveness** — сам process способен продолжать исполнение и не находится в irrecoverable local dead state.
4. **Draining** — instance прекратил admission новой работы и имеет bounded opportunity завершить/checkpoint уже начатую.

Runtime Readiness не является Community Readiness или Capability Readiness.

Unready/draining Web/API instance не получает новый traffic. Unready/draining Worker не получает новые claims. Temporary external dependency failure не превращает исправный process автоматически в non-live restart loop; dependency availability отражается в readiness/degraded signals согласно affected capability.

Graceful shutdown сначала прекращает admission/claims, затем позволяет bounded completion, local commit/checkpoint или safe interruption. После termination незавершённая durable work восстанавливается ADR-016 retry/reclaim/idempotency/Unknown Outcome semantics. Drain не обещает exactly-once и не может гарантировать завершение external action до timeout.

Endpoints, probes, protocols, timeouts, lease duration и orchestrator actions deferred.

### 9. Observability baseline

Production baseline требует:

- structured correlated Operational Logs;
- Metrics;
- targeted Tracing/correlation capability;
- actionable Alerting.

Tracing не обязано охватывать каждый request/Attempt. Signals должны позволять определить:

1. работает ли platform/affected scope;
2. где находится проблема;
3. накапливается ли проблема;
4. сохраняется ли Operational Readiness.

Минимальные observable/alertable problem classes:

- availability и repeated restart/unready states;
- saturation/resource pressure;
- relevant latency/error conditions;
- Persistent Work backlog, repeated failures/retries/quarantine;
- stale/invalid Placement Generation attempts;
- backup completion и restore-verification health;
- certificate/Secret expiry/rotation readiness, где применимо;
- Security Audit pipeline operational health;
- provider/integration degradation и rate-limit pressure;
- migration/deployment/drain failure.

Correlation связывает request, Operation/Attempt, delivery, integration evidence и deployment/change identity без превращения telemetry в authoritative semantic record.

Observability соблюдает tenant isolation, least privilege, data minimization, redaction и bounded cardinality. Secret material, credentials, tokens/passwords/OTP и prohibited security data не попадают в telemetry.

Operational Log/Metric/Trace не является Security Audit, Domain/Integration Provenance или Persistent Work state и не используется как единственный authoritative record. Exact products, formats, sampling, retention, dashboards, thresholds и paging deferred.

### 10. Alerting и operational ownership

Alert является actionable только если имеет определимые affected scope/class, severity/impact basis, responsible operational owner или escalation path, correlation evidence и resolution/verification expectation.

Alerting фокусируется на user/platform impact, error-budget/saturation/backlog trends, data/recovery risk и security-control health, а не на каждый low-level event. Отсутствие сигналов не считается доказательством health без applicable checks.

Exact SLO/SLA, thresholds, on-call schedule/product, notification channel и escalation times являются policy/Implementation Baseline. ADR-014 RPO/RTO остаются internal ordinary DR objectives, не external SLA.

### 11. Production changes и privileged operations

Production deployment, migration, restore, relocation, security-sensitive configuration/Secret rotation и другие privileged operations выполняются как controlled attributable workflows.

Для significant operation определимы:

- actual operator/Workload Technical Identity;
- authorization и scope;
- purpose/reason, где требуется;
- target Environment/Placement/component;
- Immutable Artifact/change/config/schema identity, где применимо;
- preconditions;
- execution result;
- post-change verification;
- compatible rollback или roll-forward/recovery strategy.

На первом этапе один authorized Platform Admin может выполнить такую operation, если сохранены authorization, attribution и Security Audit requirements. Universal two-person approval не требуется настоящим ADR.

Platform Admin не получает automatic tenant-content access или DB/RLS bypass. Migration/restore identities отделены от normal runtime и ограничены purpose. Domain-significant effects используют owning contracts; infrastructure operator не становится Subject.

### 12. Emergency operation и hotfix path

Emergency path может сокращать обычную sequence/lead time, но не отменяет authentication, authorization, scope, reason, attribution и subsequent result/verification/audit.

Emergency artifact/config change получает stable identity и не становится untracked mutable production state. Если предварительная verification ограничена, после change обязательны explicit validation и reconciliation/roll-forward plan.

Break-glass сохраняет ADR-015 requirements и не bypass mandatory domain admissibility/invariants. Emergency deploy и break-glass связаны только если конкретная operation требует такой elevation; они не являются синонимами.

Exact approval count, communication, pipeline bypass controls и hotfix branching deferred.

### 13. Backup, restore и DR operational discipline

ADR-014 backup/PITR, coordinated recoverable set, off-failure-domain requirement, RPO ≤1 hour и RTO ≤4 hours для ordinary DR являются обязательными inputs.

Production operations должны иметь:

- explicit ownership backup/recovery responsibilities;
- documented DR/restore runbooks;
- monitored backup/recovery prerequisites;
- periodic real restore verification, а не assumption из факта backup creation;
- verification PostgreSQL, object storage, Placement catalog/Generation, schema/application/work compatibility и security/Secret/key recovery requirements;
- retained evidence результата test/recovery без domain-history substitution.

Restore drill frequency, tools, storage topology и automated failover deferred. Selective Community Recovery остаётся exceptional isolated-copy extraction/reconciliation, а не production Shared Placement rollback.

### 14. Capacity, scaling и failure containment

Capacity planning является measurement-driven. Architecture не фиксирует universal numbers Communities/users/objects/operations/concurrency per server.

Для relevant runtime, storage, Workload Class, Placement и provider boundaries определяются **Capacity Envelopes**: измеряемые operating ranges, headroom, saturation indicators и response options. Numeric values являются load/capacity targets Implementation Baseline/operations policy и не становятся identity/domain invariant.

Возможные responses:

- horizontal Web/API scaling;
- Worker/Workload Class scaling;
- fairness/backpressure/rate/concurrency adjustment;
- resource adjustment;
- Community relocation;
- Shared Placement split;
- Dedicated Placement, когда justified.

Exhaustion одной Community, Workload Class, Placement или provider по возможности containment-ится и не вызывает unnecessary platform-wide failure. Это не absolute physical isolation: Shared Placement outage естественно затрагивает несколько Communities.

Scaling/admission не bypass ordering, tenant isolation, Placement Generation, authorization или provider quotas. Exact thresholds, autoscaling algorithm, hardware sizing и Dedicated trigger deferred.

### 15. Component/dependency failure semantics

- **Web/API instance failure:** remove from admission; other compatible instances may continue; no authoritative state loss.
- **Worker failure:** claims stop/recover; durable work retries/reconciles per ADR-016.
- **Control Plane outage:** bounded safe cached data-plane operations only; mutations/provisioning/relocation stop.
- **Placement/PostgreSQL outage:** affected authoritative reads/writes stop/fail closed; unrelated Placements may continue; recovery follows ADR-014.
- **Object storage outage:** binary-dependent operations degrade/stop; DB metadata does not falsely claim completed representation.
- **External provider outage:** affected integration/work backlog/backpressure applies; domain facts are not rewritten; Unknown Outcome handled separately.
- **DNS/TLS control-plane outage:** existing served traffic may continue while valid configuration/certificates permit; changes/renewal risk alerts; no false guarantee when certificates/routing fail.
- **Observability dependency outage:** application correctness state remains elsewhere, but monitoring blind spot is itself health/alert condition.
- **Security Audit pipeline outage:** privileged action requiring audit does not proceed silently; exact durable audit buffering/fail-closed realization deferred.

## Validation scenarios

1. **Web instance exits during rolling deploy.** Load admission removes it; durable/authoritative state remains; other compatible instances continue.
2. **Worker drains with in-flight external request.** It stops new claims; timeout may leave Unknown Outcome; ADR-016 reconciliation applies, not exactly-once claim.
3. **Old Worker sees expanded schema/new work contract.** It receives only declared compatible form or drains before incompatible activation; contract phase waits.
4. **Rollback binary after schema expansion.** Allowed only if old binary remains compatible; database/history is not rolled back automatically.
5. **Control Plane unavailable.** Safe existing data-plane request may use bounded Generation-aware cache; relocation/provisioning/sensitive uncertain operations stop.
6. **Community Placement Generation changes during cached request.** Stale context cannot write old Placement and fails/re-resolves.
7. **Shared Placement unavailable.** Its Communities may be affected; other Placements continue where dependencies permit; no absolute per-tenant survival promise.
8. **Object store unavailable while metadata DB works.** Binary operation is degraded/unavailable and cannot be recorded as fully completed falsely.
9. **External bank/provider timeout.** Health/degradation/backpressure signalled; Unknown Outcome not converted to failure/blind retry.
10. **Planned incompatible migration.** Controlled maintenance stops admission/claims, runs verified migration/roll-forward plan, and resumes after readiness checks.
11. **Temporary provider outage makes a component unready for one capability.** Process may remain live; scoped degradation avoids restart loop/global maintenance.
12. **One Community floods work.** ADR-016 fairness plus measurement-driven capacity prevents unnecessary starvation; no queue-per-tenant implied.
13. **Restore backup succeeds technically but object/catalog generation mismatch exists.** Restore verification fails until coordinated set/reconciliation is proven.
14. **Emergency hotfix.** Authorized attributed immutable change proceeds through shortened process with post-verification/audit; no unaudited server edit.
15. **Telemetry accidentally contains credential.** This violates ADR-015/017 redaction boundary regardless of monitoring product.

## Архитектурные инварианты

1. First production uses one primary Failure Domain; multi-region is deferred.
2. Correctness does not depend on a single Web/API or Worker instance.
3. Critical persistent services have explicit availability/recovery properties consistent with ADR-014 RPO/RTO, without prescribed topology.
4. Rolling deployment is used only inside declared compatibility; controlled maintenance is valid for incompatible/high-risk change.
5. Zero downtime is a desired compatible-change capability, not stronger than data/domain/work/security correctness.
6. Expand/deploy/backfill/contract waits for old consumers/work before contract.
7. Application rollback is not schema/history/restore/correction/compensation rollback.
8. Development, Staging и Production logically isolated; verified immutable artifact is promoted without production rebuild.
9. Environment configuration/secrets/endpoints/credentials are external to artifact.
10. Production promotion and privileged changes are explicitly authorized/attributable/verifiable/auditable where required.
11. Control Plane is authoritative but not synchronous dependency for every safe data-plane request.
12. Cached resolution is bounded/non-authoritative and stale Placement Generation fails closed.
13. Operational Maintenance/Degraded Mode is scoped and does not rewrite Community/domain lifecycle/readiness.
14. Degraded mode cannot bypass authorization, admissibility, tenant isolation, RLS or current-sensitive gates.
15. Runtime Readiness, Community Readiness and Capability Readiness are distinct.
16. Startup, Runtime Readiness, Liveness and Draining are distinct.
17. Unready/draining Web/Worker receives no new applicable work; durable work survives termination.
18. External dependency outage is not automatically process non-liveness or domain failure.
19. Logs, metrics, traces, Security Audit, domain/integration provenance and Persistent Work state remain distinct.
20. Observability is correlated/actionable, tenant-minimized and secret-free.
21. Restore is periodically proven and reconciles coordinated persistence/security state.
22. Capacity is measurement-driven; no discussed numeric targets become architectural limits.
23. Scaling/failure containment respects Placement, tenant, ordering, security and provider contracts.
24. Shared Placement failure may affect co-located Communities; no absolute tenant physical isolation is promised.
25. No concrete infrastructure product or mandatory microservice/multi-region topology is selected.

## Последствия

Положительно:

- Implementation Baseline получает clear production guarantees without product lock-in;
- compatible changes can roll with bounded mixed-version safety, while risky changes have honest maintenance fallback;
- Control Plane and Placement failures have explicit blast-radius/admission semantics;
- health/draining align with durable work instead of process-memory assumptions;
- observability, privileged operations и DR become verifiable disciplines;
- capacity decisions use measurements and support Placement evolution.

Цена и риски:

- compatible rollout requires contract/schema/work-version governance;
- bounded Control Plane cache requires precise freshness/fail-closed implementation;
- scoped degraded modes and alerts need explicit ownership/policy;
- redundancy, restore drills and immutable promotion add operational cost;
- single-region baseline still has regional DR downtime risk;
- without measured capacity targets initial sizing remains Implementation Baseline work.

## Отклонённые альтернативы

- single Web/API или Worker as correctness dependency;
- mandatory microservice/service-per-module split;
- mandatory multi-region first production;
- mandatory specific orchestrator/cloud/HA/monitoring product;
- arbitrary mixed-version compatibility или unconditional zero-downtime promise;
- rebuild production artifact after Staging;
- production configuration/secrets baked into artifact;
- synchronous Control Plane call for every data-plane request;
- indefinite/non-generation-aware cache as authority;
- one global maintenance boolean;
- universal read-only availability during authoritative persistence failure;
- one health flag/probe for startup/readiness/liveness/dependencies;
- kill/restart healthy process for every external dependency outage;
- raw logs as Domain History/Security Audit/Persistent Work state;
- unauthenticated/unaudited emergency change;
- application rollback as database/domain history rollback;
- backup existence without restore testing;
- fixed unverified Community/user capacity limits;
- absolute tenant survival promise inside failed Shared Placement;
- local filesystem/sticky session as authoritative correctness mechanism;
- exactly-once or distributed ACID during deployment/failover.

- DNS/ACME/certificate and Secret/KMS implementation;

- numeric load/capacity targets and Dedicated Placement triggers;
