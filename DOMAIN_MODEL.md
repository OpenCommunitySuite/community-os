# Community OS — Domain Model

**Статус:** Draft  
**Версия:** 0.1  
**Язык документа:** русский

> ⚠️ Документ находится в стадии обсуждения.
> Содержание является рабочей моделью предметной области и может
> изменяться по результатам обсуждения с представителями сообществ,
> бухгалтерией и другими участниками проекта.

---

## 1. Назначение документа

Настоящий документ описывает основные сущности предметной области Community OS и отношения между ними.

Документ является связующим уровнем между:

- Vision проекта;
- терминологией;
- бизнес-процессами;
- будущей функциональной спецификацией;
- технической архитектурой.

Документ не определяет:

- структуру базы данных;
- программный код;
- API;
- конкретные технологии реализации.

---

# 2. Общий принцип предметной модели

Community OS строится вокруг понятия **сообщества**.

Сообщество объединяет:

- объекты;
- собственников и других участников;
- лицевые счета;
- начисления;
- платежи;
- ресурсы;
- приборы учёта;
- расходы;
- поставщиков;
- документы;
- сотрудников;
- органы управления;
- собрания и голосования;
- обращения;
- информационные материалы.

При этом одна установка Community OS может обслуживать несколько независимых сообществ.

Данные различных сообществ должны быть логически изолированы.

---

# 3. Сообщество

**Сообщество** — самостоятельная организация или объединение собственников, использующее Community OS для управления своей деятельностью.

Сообщество имеет:

- тип;
- название;
- организационные данные;
- настройки;
- правила;
- пользователей;
- объекты;
- участников;
- финансовые данные;
- документы.

Тип сообщества определяет особенности его деятельности, но не должен определять фундаментальную структуру платформы.

---

# 4. Тип сообщества

На первом этапе предусматриваются:

- садовое товарищество;
- ОСББ;
- ЖСК;
- жилищный кооператив;
- гаражный кооператив;
- коттеджный посёлок;
- другие сообщества собственников.

Наличие нового типа сообщества не должно требовать создания отдельной версии Community OS.

---

# 5. Участники сообщества

В предметной модели необходимо различать:

- физическое или юридическое лицо;
- собственника;
- члена сообщества;
- пользователя системы;
- сотрудника;
- представителя органа управления.

Один человек может одновременно иметь несколько статусов.

Например:

Физическое лицо

→ собственник участка  
→ член СТ  
→ пользователь личного кабинета.

Или:

Физическое лицо

→ собственник квартиры  
→ член ОСББ  
→ член правления.

Статусы и права не должны быть жёстко связаны между собой.

---

# 6. Объект

**Объект** — базовая единица собственности, пользования и учёта в конкретном сообществе.

Для различных типов сообществ используются разные виды объектов.

### Для садового товарищества

Основным объектом является земельный участок.

Участок может иметь:

- номер;
- кадастровый номер;
- площадь;
- местоположение;
- собственников;
- лицевой счёт;
- приборы учёта.

### Для ОСББ / ЖСК

Объектами могут быть:

- дом;
- подъезд;
- квартира;
- нежилое помещение;
- машино-место;
- другие объекты.

Может использоваться иерархия объектов:

Дом
→ Подъезд
→ Этаж
→ Квартира.

Иерархия объектов должна быть универсальной и не ограничиваться конкретным типом сообщества.

---

# 7. Собственник и объект

Связь между собственником и объектом является отдельной сущностью предметной области.

Необходимо поддерживать:

- одного собственника нескольких объектов;
- нескольких собственников одного объекта;
- долевую собственность;
- изменение собственников во времени.

Пример:

Собственник А
→ Участок 101
→ Участок 102

Собственник Б
→ Участок 102.

При этом участок 102 имеет двух собственников.

История изменения собственников должна сохраняться.

---

# 8. Лицевой счёт

**Лицевой счёт** — финансовая сущность, предназначенная для учёта начислений, платежей, задолженности и других финансовых операций, связанных с объектом или группой объектов.

Для первого внедрения в СТ основной моделью является:

Участок → Лицевой счёт.

Если один собственник владеет двумя участками:

Участок 101 → Лицевой счёт 101  
Участок 102 → Лицевой счёт 102.

Это позволяет отдельно учитывать:

- площадь;
- кадастровые данные;
- начисления;
- платежи;
- задолженность.

При этом система должна допускать другие модели связи объекта и лицевого счёта, если этого требуют правила конкретного сообщества.

---

# 9. Связь нескольких объектов с одним прибором учёта

Несколько объектов могут использовать один прибор учёта.

Например:

Собственник  
→ Участок 101  
→ Участок 102  
→ общий счётчик электроэнергии.

Наличие общего прибора учёта не должно объединять сами объекты.

Каждый объект сохраняет самостоятельность для:

- начислений;
- права собственности;
- голосования;
- площади;
- других характеристик.

---

# 10. Ресурс

**Ресурс** — физический ресурс, потребление которого измеряется или рассчитывается системой.

На первом этапе:

- электроэнергия;
- вода.

В дальнейшем могут добавляться:

- газ;
- тепло;
- другие ресурсы.

Ресурс не должен быть жёстко связан с конкретным способом учёта или начисления.

---

# 11. Прибор учёта

**Прибор учёта** — средство измерения количества потреблённого ресурса.

Прибор учёта связан:

- с конкретным ресурсом;
- с одним или несколькими объектами либо с сообществом;
- с определённой ветвью учёта.

Предусматриваются:

- индивидуальные приборы;
- общие приборы;
- промежуточные приборы;
- другие приборы, необходимые для организации учёта.

---

# 12. Ветвь учёта ресурса

**Ветвь учёта ресурса** — самостоятельная цепочка учёта конкретного ресурса внутри сообщества.

Одно сообщество может иметь несколько независимых ветвей одного и того же ресурса.

Например, садовое товарищество может иметь три независимые ветви учёта электроэнергии:

Общий счётчик №1  
→ участки.

Общий счётчик №2  
→ участки.

Общий счётчик №3  
→ насосная.

При этом общий счётчик №3 не связан с индивидуальным потреблением участков.

Для воды может существовать отдельная ветвь:

Общий счётчик воды  
→ участки.

Каждая ветвь может иметь собственную иерархию:

Общий прибор  
→ промежуточный прибор  
→ индивидуальные приборы  
→ объекты.

---

# 13. Общий прибор учёта

**Общий прибор учёта** — прибор, по показаниям которого определяется объём ресурса, потреблённого сообществом или отдельной группой объектов, в том числе объём, используемый для расчётов сообщества с поставщиком.

В одном сообществе может быть несколько общих приборов одного ресурса.

Например:

- несколько общих электросчётчиков;
- один или несколько общих счётчиков воды.

Общие приборы могут иметь разные группы потребителей.

Общий прибор не обязательно является верхним уровнем всей системы учёта ресурса.

---

# 14. Промежуточный прибор учёта

**Промежуточный прибор учёта** — прибор, расположенный между общим прибором и индивидуальными приборами и предназначенный для дополнительного контроля потребления.

В садовом товариществе промежуточный прибор может быть условно назван **уличным счётчиком**.

Пример:

Общий счётчик СТ  
→ уличный счётчик  
→ индивидуальные счётчики участков.

Термин «уличный счётчик» является частным случаем промежуточного прибора и не должен становиться обязательной частью универсальной модели.

---

# 15. Показание прибора учёта

**Показание** — зафиксированное значение прибора учёта на определённый момент времени.

Показание содержит информацию о:

- приборе;
- времени;
- значении;
- источнике получения.

Источником показания может быть:

- собственник;
- сотрудник;
- автоматическая система;
- внешняя интеграция.

История показаний должна сохраняться.

---

# 16. Потребление ресурса

**Потребление ресурса** — количество ресурса, использованное объектом, группой объектов или сообществом за определённый период.

Потребление может определяться:

- по показаниям прибора;
- расчётным способом;
- по нормативу;
- другим установленным правилом.

Потребление ресурса само по себе не определяет способ его финансирования.

---

# 17. Индивидуальное потребление

**Индивидуальное потребление** — потребление ресурса, относящееся к конкретному объекту или группе объектов и используемое для определения финансового обязательства соответствующего собственника или пользователя.

Пример:

Участок  
→ 250 кВт·ч  
→ начисление собственнику.

---

# 18. Потребление сообщества

**Потребление сообщества** — потребление ресурса, относящееся к деятельности сообщества, его общему имуществу или инфраструктуре.

Примеры:

- электроэнергия насосной;
- электроэнергия освещения территории;
- вода для общих хозяйственных нужд.

Потребление сообщества не обязательно является основанием для индивидуального начисления собственнику.

Например, электроэнергия насосной может финансироваться за счёт членских взносов в соответствии со сметой.

---

# 19. Потери

**Потери** — разница между количеством ресурса, зафиксированным на вышестоящем уровне учёта, и суммой потребления на нижестоящем уровне.

Например:

Общий счётчик улицы  
− сумма индивидуальных счётчиков  
= потери улицы.

Или:

Общий счётчик СТ  
− сумма уличных счётчиков  
= потери между вводом и улицами.

Потери должны рассчитываться независимо на каждом соответствующем уровне ветви учёта.

---

# 20. Распределение потерь

Потери могут:

- учитываться только как аналитический показатель;
- учитываться при расчёте стоимости ресурса;
- распределяться между потребителями;
- формировать отдельное начисление.

Возможные алгоритмы:

- равномерно между потребителями;
- пропорционально потреблению;
- по другому правилу.

Правило распределения должно быть настраиваемым.

---

# 21. Тариф

**Тариф** — стоимость единицы ресурса или услуги либо правило определения такой стоимости.

Тариф может иметь:

- ресурс или услугу;
- период действия;
- единицу измерения;
- стоимость;
- условия применения.

История тарифов должна сохраняться.

---

# 22. Начисление

**Начисление** — операция определения суммы, которую необходимо предъявить собственнику или пользователю на основании установленного правила.

Основанием начисления может быть:

- площадь;
- фиксированная сумма;
- потребление ресурса;
- тариф;
- целевой платёж;
- членский взнос;
- пеня;
- компенсация потерь;
- другая формула.

Начисление должно сохранять информацию о причине и правилах его формирования.

---

# 23. Финансовое обязательство собственника

**Финансовое обязательство собственника** — сумма, которую собственник или пользователь должен уплатить сообществу в результате начислений или других оснований.

Одно обязательство может быть погашено одним или несколькими платежами.

Один платёж может погашать несколько обязательств.

---

# 24. Платёж собственника

**Платёж собственника** — факт поступления денежных средств от собственника или пользователя в пользу сообщества.

Платёж может быть:

- банковским;
- наличным;
- полученным через платёжный сервис;
- полученным другим поддерживаемым способом.

Один платёж может распределяться между несколькими обязательствами.

Например:

Платёж 10 000 грн

→ членские взносы 4 000 грн  
→ электроэнергия 3 500 грн  
→ вода 1 500 грн  
→ пеня 1 000 грн.

---

# 25. Наличный платёж и кассовый документ

Наличный платёж является полноценным способом оплаты и должен учитываться в общей финансовой модели.

Для наличного платежа может формироваться приходный кассовый ордер и другие необходимые кассовые документы.

Наличный и безналичный платежи должны иметь общую модель финансового результата, но различные способы оформления и учёта.

---

# 26. Пеня

**Пеня** — дополнительное начисление за несвоевременное исполнение финансового обязательства.

Пеня рассчитывается на основании:

- суммы просроченного обязательства;
- периода просрочки;
- установленных правил.

Пеня является отдельным видом начисления и должна учитываться отдельно от основного обязательства.

---

# 27. Поставщик

**Поставщик** — организация или физическое лицо, предоставляющее сообществу ресурс, услугу или иное материальное обеспечение.

Для первого внедрения предусматриваются, в частности:

- поставщик электроэнергии;
- поставщик воды;
- организация по вывозу ТБО.

Один поставщик может предоставлять несколько ресурсов или услуг.

---

# 28. Договор с поставщиком

**Договор с поставщиком** — основание, определяющее условия получения сообществом ресурса или услуги и порядок взаиморасчётов.

Договор может определять:

- поставщика;
- ресурс или услугу;
- период действия;
- тариф или порядок его определения;
- порядок учёта объёма;
- порядок выставления документов;
- сроки оплаты;
- другие условия.

---

# 29. Обязательство перед поставщиком

**Обязательство перед поставщиком** — финансовое обязательство сообщества перед поставщиком, возникшее вследствие получения ресурса, услуги или другого основания для оплаты.

Обязательство может возникать на основании:

- счёта;
- акта;
- данных приборов учёта;
- договора;
- другого первичного документа или установленного правила.

Обязательство может быть:

- непогашенным;
- частично погашенным;
- полностью погашенным;
- просроченным.

---

# 30. Платёж поставщику

**Платёж поставщику** — факт перечисления денежных средств сообществом поставщику в счёт исполнения финансового обязательства.

Платёж может погашать одно или несколько обязательств перед поставщиком.

---

# 31. Расчёты с поставщиком

**Расчёты с поставщиком** — совокупность операций по учёту обязательств сообщества перед поставщиком и их погашению.

Расчёты включают:

- регистрацию обязательств;
- регистрацию документов поставщика;
- платежи;
- контроль задолженности;
- сверку взаиморасчётов;
- формирование отчётности.

Для коммунальных ресурсов расчёты с поставщиком могут быть связаны с показаниями соответствующих приборов учёта.

---

# 32. Расход сообщества

**Расход сообщества** — затрата, понесённая сообществом для обеспечения его деятельности, содержания общего имущества, получения ресурсов и услуг или выполнения других задач.

Примеры:

- электроэнергия насосной;
- электроэнергия освещения территории;
- вода для общих нужд;
- вывоз ТБО;
- заработная плата;
- ремонт;
- обслуживание имущества.

Расход сообщества не обязательно является основанием для непосредственного начисления отдельному собственнику.

---

# 33. Смета

**Смета** — утверждённый план доходов и расходов сообщества на определённый период.

Смета может включать:

- планируемые расходы;
- планируемые источники финансирования;
- членские взносы;
- целевые взносы;
- расходы на коммунальные ресурсы;
- заработную плату;
- вывоз ТБО;
- ремонт;
- обслуживание;
- другие расходы.

Смета является инструментом планирования и не заменяет фактический финансовый учёт.

Фактические расходы и поступления учитываются независимо от плановых значений сметы.

---

# 34. Источник финансирования

**Источник финансирования** — вид денежных поступлений, за счёт которых сообщество планирует или фактически покрывает расходы.

Примеры:

- членские взносы;
- целевые взносы;
- платежи за индивидуальное потребление;
- другие поступления.

Один расход может финансироваться одним или несколькими источниками.

---

# 35. Финансирование расхода

**Финансирование расхода** — связь между расходом сообщества и источниками денежных средств, за счёт которых этот расход покрывается.

Например:

Электроэнергия насосной  
→ расход сообщества  
→ финансирование за счёт членских взносов.

Финансирование расхода и начисление собственнику являются различными операциями.

---

# 36. Сотрудник

**Сотрудник** — лицо, выполняющее работу для сообщества на основании трудовых отношений, гражданско-правового договора или другого законного основания.

Для первого внедрения предусматриваются, в частности:

- бухгалтер;
- слесарь;
- электрик;
- охранник.

---

# 37. Вознаграждение сотрудника

**Вознаграждение сотрудника** — сумма, начисленная сотруднику за выполненную работу.

Может применяться:

- фиксированная ставка;
- оклад;
- почасовая или иная тарифная система;
- ГПХ;
- другие варианты.

При расчёте вознаграждения должны учитываться соответствующие налоги и обязательные платежи.

---

# 38. Орган управления

**Орган управления** — лицо или группа лиц, имеющие полномочия по управлению сообществом.

В зависимости от типа сообщества могут использоваться:

- общее собрание;
- правление;
- председатель;
- ревизионная комиссия;
- другие органы.

---

# 39. Собрание

**Собрание** — организованная процедура рассмотрения вопросов и принятия решений участниками сообщества.

Собрание может включать:

- дату;
- место или формат проведения;
- повестку;
- вопросы;
- голосования;
- решения;
- протокол.

---

# 40. Голосование

**Голосование** — процедура выражения участниками сообщества своего решения по определённому вопросу.

Голосование должно учитывать:

- участников;
- право голоса;
- количество голосов;
- варианты ответа;
- результаты;
- кворум;
- итоговое решение.

Для садового товарищества предусматривается правило:

**1 участок = 1 голос.**

Правила определения количества голосов должны быть настраиваемыми в зависимости от типа сообщества и конкретного собрания.

---

# 41. Документ

**Документ** — электронный или связанный с системой документ, относящийся к деятельности сообщества.

Документ может быть связан с:

- сообществом;
- объектом;
- собственником;
- поставщиком;
- сотрудником;
- собранием;
- начислением;
- платежом;
- другим объектом предметной области.

---

# 42. Обращение

**Обращение** — запрос, заявление или сообщение пользователя, направленное сообществу или его представителю.

Обращение имеет жизненный цикл:

Создано  
→ Принято  
→ В работе  
→ Ответ подготовлен  
→ Закрыто.

История обработки обращения должна сохраняться.

---

# 43. Новость

**Новость** — информационный материал, публикуемый сообществом для информирования пользователей.

---

# 44. Объявление

**Объявление** — информационное сообщение, предназначенное для уведомления участников сообщества о событии, изменении, необходимости выполнить действие или другой информации.

---

# 45. Пользователь

**Пользователь** — лицо, имеющее учётную запись в Community OS.

Пользователь может иметь:

- один или несколько статусов;
- одну или несколько ролей;
- доступ к одному или нескольким сообществам.

Пользователь системы и собственник объекта являются различными понятиями.

---

# 46. Роль

**Роль** — набор полномочий пользователя в системе.

Примеры:

- собственник;
- бухгалтер;
- кассир;
- председатель;
- член правления;
- сотрудник;
- администратор.

---

# 47. Лицевой кабинет

**Личный кабинет** — пользовательский интерфейс, через который собственник или другой участник сообщества получает доступ к относящейся к нему информации и функциям.

В частности, личный кабинет может предоставлять:

- информацию об объектах;
- начисления;
- платежи;
- задолженность;
- показания приборов;
- документы;
- новости;
- объявления;
- обращения;
- онлайн-оплату в перспективе.

---

# 48. Историческая связь

**Историческая связь** — связь между сущностями, для которой важно сохранять период её действия.

Примеры:

- собственник владеет объектом определённый период;
- тариф действует определённый период;
- прибор установлен с определённой даты;
- сотрудник работает определённый период;
- договор с поставщиком действует определённый период.

Система должна позволять определить состояние такой связи на конкретную дату.

---

# 49. Универсальная сущность

**Универсальная сущность** — элемент предметной модели, который используется различными типами сообществ без изменения своей фундаментальной природы.

Например:

- сообщество;
- собственник;
- объект;
- лицевой счёт;
- начисление;
- платёж;
- документ;
- прибор учёта.

---

# 50. Специализация сообщества

**Специализация сообщества** — набор правил и функций, характерных для конкретного типа сообщества.

Например:

Для СТ:

- участок;
- кадастровый номер;
- членские взносы по площади;
- правило «1 участок = 1 голос».

Для ОСББ:

- дом;
- квартира;
- общее имущество;
- особенности распределения расходов.

Специализация не должна приводить к созданию отдельной программной системы.

---

# 51. Первое внедрение

Первая практическая реализация Community OS выполняется для садового товарищества.

Основными объектами первого внедрения являются:

- земельные участки;
- собственники;
- лицевые счета;
- приборы учёта;
- начисления;
- платежи;
- поставщики;
- расходы;
- смета;
- сотрудники;
- документы;
- собрания;
- голосования.

---

# 52. Проверка универсальности

После первого внедрения в садовом товариществе предполагается возможность использования Community OS в ОСББ/ЖСК.

Такой переход является практической проверкой универсальности предметной модели.

Например:

Садовое товарищество:

Сообщество  
→ Участок  
→ Лицевой счёт.

ОСББ:

Сообщество  
→ Дом  
→ Квартира  
→ Лицевой счёт.

Фундаментальные финансовые, ресурсные и управленческие механизмы при этом должны оставаться общими.

---

# 53. Независимость сущностей

Сущности предметной области не должны искусственно объединяться ради упрощения реализации.

В частности:

- собственник ≠ пользователь;
- собственник ≠ лицевой счёт;
- объект ≠ лицевой счёт;
- прибор учёта ≠ объект;
- потребление ≠ начисление;
- начисление ≠ платёж;
- обязательство ≠ платёж;
- расход сообщества ≠ начисление собственнику;
- поставщик ≠ обязательство;
- сообщество ≠ тип сообщества.

---

# 54. Расширяемость

Предметная модель должна позволять добавлять:

- новые типы объектов;
- новые типы сообществ;
- новые ресурсы;
- новые виды начислений;
- новые способы оплаты;
- новые алгоритмы расчётов;
- новые роли;
- новые виды документов;
- новые бизнес-процессы.

Добавление нового типа сообщества не должно требовать изменения фундаментальных сущностей платформы.

---

# 55. Принцип предметной модели

Предметная модель Community OS должна отражать реальную деятельность сообщества, а не особенности конкретной программной реализации.

Программная реализация должна адаптироваться к предметной области, а не заставлять сообщество изменять реальные процессы только ради удобства программы.
