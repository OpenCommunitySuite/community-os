# Community OS — Domain Model

**Статус:** Draft  
**Версия:** 0.3  
**Язык документа:** русский

> ⚠️ Документ находится в стадии обсуждения.
> Содержание является рабочей моделью предметной области и может
> изменяться по результатам обсуждения с представителями сообществ,
> бухгалтерией и другими участниками проекта.

---

# 1. Назначение документа

Настоящий документ описывает основные сущности предметной области Community OS и отношения между ними.

Документ является связующим уровнем между:

- Vision проекта;
- терминологией;
- бизнес-процессами;
- будущей функциональной спецификацией;
- технической архитектурой.

Документ не определяет:

- структуру базы данных;
- программный код;
- API;
- конкретные технологии реализации.

---

# 2. Общий принцип предметной модели

Community OS строится вокруг понятия **сообщества**.

Сообщество объединяет:

- объекты;
- собственников и других участников;
- лицевые счета;
- начисления;
- платежи;
- ресурсы;
- приборы учёта;
- инженерные системы;
- расходы;
- поставщиков;
- документы;
- сотрудников;
- органы управления;
- собрания и голосования;
- обращения;
- информационные материалы.

При этом одна установка Community OS может обслуживать несколько независимых сообществ.

Данные различных сообществ должны быть логически изолированы.

---

# 3. Сообщество

**Сообщество** — самостоятельная организация или объединение собственников, использующее Community OS для управления своей деятельностью.

Сообщество имеет:

- тип;
- название;
- организационные данные;
- настройки;
- правила;
- пользователей;
- объекты;
- участников;
- финансовые данные;
- документы;
- инженерную инфраструктуру.

Тип сообщества определяет особенности его деятельности, но не должен определять фундаментальную структуру платформы.

---

# 4. Тип сообщества

На первом этапе предусматриваются:

- садовое товарищество;
- ОСББ;
- ЖСК;
- жилищный кооператив;
- гаражный кооператив;
- коттеджный посёлок;
- другие сообщества собственников.

Наличие нового типа сообщества не должно требовать создания отдельной версии Community OS.

---

# 5. Участники сообщества

В предметной модели необходимо различать:

- физическое или юридическое лицо;
- собственника;
- члена сообщества;
- пользователя системы;
- сотрудника;
- представителя органа управления.

Один человек может одновременно иметь несколько статусов.

Например:

Физическое лицо

→ собственник участка  
→ член СТ  
→ пользователь личного кабинета.

Или:

Физическое лицо

→ собственник квартиры  
→ член ОСМД  
→ член правления.

Статусы и права не должны быть жёстко связаны между собой.

---

# 6. Объект

**Объект** — базовая единица собственности, пользования и учёта в конкретном сообществе.

Для различных типов сообществ используются разные виды объектов.

### Для садового товарищества

Основным объектом является земельный участок.

Участок может иметь:

- номер;
- кадастровый номер;
- площадь;
- местоположение;
- собственников;
- лицевой счёт;
- подключения к инженерным системам;
- связанные приборы учёта.

### Для ОСМД / ЖСК

Объектами могут быть:

- дом;
- подъезд;
- квартира;
- нежилое помещение;
- машино-место;
- другие объекты.

Может использоваться иерархия объектов:

Дом  
→ Подъезд  
→ Этаж  
→ Квартира.

Иерархия объектов должна быть универсальной и не ограничиваться конкретным типом сообщества.

При этом иерархия объектов собственности не должна использоваться для моделирования инженерных сетей сообщества.

Инженерная инфраструктура моделируется отдельно.

---

# 7. Инженерная и учётно-техническая структура

**Инженерная и учётно-техническая структура** — отдельное представление сообщества, предназначенное для моделирования инженерных систем, сетей, оборудования, приборов учёта и связей между ними.

Она существует независимо от иерархии объектов собственности.

Инженерная структура должна позволять описывать, в частности:

- системы электроснабжения;
- системы питьевого водоснабжения;
- системы поливной / технической воды;
- другие инженерные системы;
- источники ресурсов;
- магистральные линии;
- ответвления;
- узлы;
- насосные;
- оборудование;
- приборы учёта;
- точки подключения объектов;
- другие элементы инженерной инфраструктуры.

Например, система электроснабжения может быть представлена как:

Трансформаторная подстанция  
→ линия электроснабжения  
→ контрольный / промежуточный прибор учёта  
→ линия улицы  
→ индивидуальные приборы учёта  
→ точки подключения участков.

Система поливной воды может быть представлена как:

Источник воды  
→ насосная  
→ насосное оборудование  
→ магистраль  
→ ветви распределения  
→ точки подключения потребителей.

Инженерная структура может включать элементы, которые:

- относятся к конкретному объекту;
- обслуживают группу объектов;
- принадлежат сообществу;
- не связаны непосредственно с объектами собственности.

Например, насосная является элементом инженерной инфраструктуры сообщества и не является объектом собственности конкретного участка.

Инженерная структура должна позволять устанавливать связи между:

- инженерными элементами;
- объектами собственности;
- лицевыми счетами;
- приборами учёта;
- ресурсами.

При этом эти связи не должны превращать инженерный элемент в объект собственности.

Например:

Участок 101  
→ Лицевой счёт №101

и одновременно:

Участок 101  
→ точка подключения к электросети  
→ индивидуальный электросчётчик №E101  
→ линия №3  
→ общий прибор учёта №E03.

Таким образом, структура собственности, финансовая структура и инженерная структура являются самостоятельными представлениями предметной области, связанными между собой определёнными отношениями.

Один объект может быть подключён к нескольким инженерным системам.

Одна инженерная система может обслуживать множество объектов.

Не каждый элемент инженерной системы обязан иметь лицевой счёт.

Не каждый прибор учёта обязан быть связан непосредственно с объектом собственности.

---

# 8. Собственник и объект

Связь между собственником и объектом является отдельной сущностью предметной области.

Необходимо поддерживать:

- одного собственника нескольких объектов;
- нескольких собственников одного объекта;
- долевую собственность;
- изменение собственников во времени.

Пример:

Собственник А  
→ Участок 101  
→ Участок 102

Собственник Б  
→ Участок 102.

При этом участок 102 имеет двух собственников.

История изменения собственников должна сохраняться.

---

# 9. Лицевой счёт

**Лицевой счёт** — финансовая сущность, предназначенная для учёта начислений, платежей, задолженности и других финансовых операций, связанных с объектом или группой объектов.

Для первого внедрения в СТ основной моделью является:

Участок → Лицевой счёт.

Если один собственник владеет двумя участками:

Участок 101 → Лицевой счёт 101  
Участок 102 → Лицевой счёт 102.

Это позволяет отдельно учитывать:

- площадь;
- кадастровые данные;
- начисления;
- платежи;
- задолженность.

При этом система должна допускать другие модели связи объекта и лицевого счёта, если этого требуют правила конкретного сообщества.

Лицевой счёт является финансовой сущностью и не должен использоваться для моделирования инженерной структуры.

---

# 10. Связь нескольких объектов с одним прибором учёта

Несколько объектов могут использовать один прибор учёта.

Например:

Собственник  
→ Участок 101  
→ Участок 102  
→ общий счётчик электроэнергии.

Наличие общего прибора учёта не должно объединять сами объекты.

Каждый объект сохраняет самостоятельность для:

- начислений;
- права собственности;
- голосования;
- площади;
- других характеристик.

Связь прибора с объектами является отдельной связью и может существовать независимо от связи объекта с лицевым счётом.

---

# 11. Ресурс

**Ресурс** — физический ресурс, потребление которого измеряется или рассчитывается системой.

На первом этапе:

- электроэнергия;
- вода.

В дальнейшем могут добавляться:

- газ;
- тепло;
- другие ресурсы.

Ресурс не должен быть жёстко связан с конкретным способом учёта или начисления.

Один и тот же ресурс может использоваться в нескольких независимых инженерных системах и ветвях учёта.

Например, вода может одновременно использоваться:

- в системе питьевого водоснабжения;
- в системе поливной / технической воды.

---

# 12. Прибор учёта

**Прибор учёта** — средство измерения количества потреблённого ресурса.

Прибор учёта связан:

- с конкретным ресурсом;
- с одним или несколькими объектами либо с сообществом;
- с определённой инженерной системой или ветвью учёта.

Предусматриваются:

- индивидуальные приборы;
- общие приборы;
- промежуточные приборы;
- контрольные приборы;
- другие приборы, необходимые для организации учёта.

Прибор учёта является одновременно частью учётной модели ресурса и может быть элементом инженерной структуры.

---

# 13. Ветвь учёта ресурса

**Ветвь учёта ресурса** — самостоятельная цепочка учёта конкретного ресурса внутри сообщества.

В одном сообществе может существовать несколько независимых ветвей одного и того же ресурса.

Например, садовое товарищество может иметь три независимые ветви учёта электроэнергии:

Общий счётчик №1  
→ участки.

Общий счётчик №2  
→ участки.

Общий счётчик №3  
→ насосная.

При этом общий счётчик №3 не связан с индивидуальным потреблением участков.

Для воды может существовать отдельная ветвь:

Общий счётчик воды  
→ участки.

Каждая ветвь может иметь собственную иерархию:

Общий прибор  
→ промежуточный прибор  
→ индивидуальные приборы  
→ объекты.

Ветвь учёта может быть связана с соответствующей инженерной системой.

---

# 14. Общий прибор учёта

**Общий прибор учёта** — прибор, по показаниям которого определяется объём ресурса, потреблённого сообществом или отдельной группой объектов, в том числе объём, используемый для расчётов сообщества с поставщиком.

В одном сообществе может быть несколько общих приборов одного ресурса.

Например:

- несколько общих электросчётчиков;
- один или несколько общих счётчиков воды.

Общие приборы могут иметь разные группы потребителей.

Общий прибор не обязательно является верхним уровнем всей системы учёта ресурса.

---

# 15. Промежуточный прибор учёта

**Промежуточный прибор учёта** — прибор, расположенный между общим прибором и индивидуальными приборами и предназначенный для дополнительного контроля потребления.

В садовом товариществе промежуточный прибор может быть условно назван **уличным счётчиком**.

Пример:

Общий счётчик СТ  
→ уличный счётчик  
→ индивидуальные счётчики участков.

Термин «уличный счётчик» является частным случаем промежуточного прибора и не должен становиться обязательной частью универсальной модели.

Промежуточный прибор может одновременно являться элементом инженерной структуры соответствующей сети.

---

# 16. Показание прибора учёта

**Показание** — зафиксированное значение прибора учёта на определённый момент времени.

Показание содержит информацию о:

- приборе;
- дате и времени фиксации;
- значении;
- источнике получения;
- лице или системе, зафиксировавших показание, если это применимо.

История показаний должна сохраняться.

Источником показания может быть:

- собственник через личный кабинет;
- сотрудник со слов собственника;
- сотрудник при непосредственном снятии показания;
- контролёр при непосредственном снятии показания;
- автоматическая система;
- внешняя интеграция.

Обычная передача показаний и контрольное снятие показаний используют одну и ту же модель истории показаний.

Отдельная сущность «контрольная сверка» для хранения показаний не требуется.

---

# 17. Потребление ресурса

**Потребление ресурса** — количество ресурса, использованное объектом, группой объектов или сообществом за определённый период.

Потребление может определяться:

- по показаниям прибора;
- расчётным способом;
- по нормативу;
- другим установленным правилом.

Потребление ресурса само по себе не определяет способ его финансирования или порядок начисления.

---

# 18. Индивидуальное потребление

**Индивидуальное потребление** — потребление ресурса, относящееся к конкретному объекту или группе объектов и используемое для определения финансового обязательства соответствующего собственника или пользователя.

Пример:

Участок  
→ 250 кВт·ч  
→ начисление собственнику.

---

# 19. Потребление сообщества

**Потребление сообщества** — потребление ресурса, относящееся к деятельности сообщества, его общему имуществу или инфраструктуре и не относящееся непосредственно к индивидуальному потреблению конкретного собственника.

Примеры:

- электроэнергия насосной;
- электроэнергия освещения территории;
- вода для общих хозяйственных нужд.

Потребление сообщества не обязательно является основанием для индивидуального начисления собственнику.

Например, электроэнергия насосной может финансироваться за счёт членских взносов в соответствии со сметой.

---

# 20. Баланс потребления

**Баланс потребления** — сопоставление количества ресурса, зафиксированного на одном уровне учёта, с суммарным потреблением на связанном нижестоящем уровне.

Для соответствующей ветви учёта может рассчитываться:

Общее потребление  
− сумма индивидуального потребления  
= небаланс.

При анализе электроэнергии такой небаланс может использоваться как показатель потерь или неучтённого потребления.

Пример:

Уличный счётчик  
− сумма потребления всех участков улицы  
= небаланс улицы.

---

# 21. Анализ баланса потребления

**Анализ баланса потребления** — аналитический механизм, использующий историю показаний и структуру ветвей учёта для выявления и сравнения небалансов.

Основная практическая задача первого внедрения — выявление улиц или других зон с повышенными потерями электроэнергии для последующего технического обследования.

Например:

- 1 июля снято показание уличного счётчика;
- в максимально короткий срок сняты показания всех индивидуальных счётчиков участков данной улицы;
- 1 августа процедура повторена;
- система рассчитывает потребление по уличному счётчику;
- система рассчитывает суммарное потребление участков;
- система определяет абсолютный и относительный небаланс;
- результаты сравниваются с другими улицами и предыдущими периодами.

Аналитика может формировать:

- небаланс в единицах ресурса;
- небаланс в процентах;
- динамику небаланса по периодам;
- сравнение улиц или других зон;
- статистику по сообществу.

Community OS не должна автоматически определять причину выявленного небаланса.

Возможные причины могут включать:

- погрешность или неисправность индивидуальных приборов;
- ошибки при снятии или передаче показаний;
- технические потери в сети;
- проблемы с магистральными или присоединительными проводами;
- неучтённое потребление;
- неисправность общего или промежуточного прибора;
- другие причины.

Определение причины является задачей последующего технического обследования.

---

# 22. Потери ресурса

**Потери ресурса** — разница между количеством ресурса, зафиксированным на верхнем уровне соответствующей ветви учёта, и суммарным количеством ресурса, учтённым на связанных нижестоящих уровнях.

Для электроэнергии потери могут включать:

- технические потери в сети;
- погрешности приборов учёта;
- ошибки учёта;
- неучтённое потребление;
- другие расхождения между уровнями учёта.

Расчёт потерь является аналитическим результатом и не означает автоматического возникновения финансового обязательства собственников.

Потери должны быть связаны с:

- конкретным ресурсом;
- конкретной ветвью или зоной учёта;
- расчётным периодом;
- исходными показаниями и потреблением, на основании которых они определены.

Потери ресурса не следует автоматически отождествлять с эксплуатационными потерями или аварийными утечками.

Например, утечка воды в инженерной сети может быть отдельным фактом эксплуатации инфраструктуры, даже если она впоследствии учитывается в анализе общего баланса ресурса.

---

# 23. Распределение потерь

Community OS может поддерживать распределение выявленного небаланса между объектами или собственниками.

Распределение потерь является **настраиваемой функцией конкретного сообщества** и может быть:

- включено;
- отключено.

Если распределение отключено, выявленный небаланс используется только для аналитики и контроля.

Если распределение включено, сообщество должно определить правило распределения.

Возможные варианты:

- пропорционально индивидуальному потреблению;
- пропорционально площади объекта;
- поровну между объектами;
- по другому правилу, установленному сообществом.

Правило распределения должно быть явно определено и сохраняться в истории.

Распределённая сумма может использоваться для формирования соответствующего начисления собственнику.

Распределение потерь не должно изменять:

- исходные показания приборов;
- фактическое потребление;
- историю измерений.

Исходные данные:

Общий прибор → фактическое потребление

Индивидуальные приборы → фактическое потребление

остаются неизменными.

Распределение потерь является отдельной расчётной операцией.

---

# 24. Пример распределения потерь

Общий прибор за период:

**10 000 кВт·ч**

Суммарное индивидуальное потребление:

**9 000 кВт·ч**

Небаланс:

**1 000 кВт·ч**

Если распределение потерь отключено:

> 1 000 кВт·ч отображаются только в аналитике.

Если распределение включено:

> 1 000 кВт·ч распределяются между объектами согласно установленному правилу.

Например, пропорционально индивидуальному потреблению.

При этом:

**Фактическое потребление участка ≠ распределённые потери.**

Система должна позволять отдельно показывать:

- фактически измеренное потребление;
- долю распределённых потерь;
- итоговое начисление.

---

# 25. Тариф

**Тариф** — стоимость единицы ресурса или услуги либо правило определения такой стоимости.

Тариф может иметь:

- ресурс или услугу;
- период действия;
- единицу измерения;
- стоимость;
- условия применения.

История тарифов должна сохраняться.

---

# 26. Начисление

**Начисление** — операция определения суммы, которую необходимо предъявить собственнику или пользователю на основании установленного правила.

Основанием начисления может быть:

- площадь;
- фиксированная сумма;
- потребление ресурса;
- тариф;
- целевой платёж;
- членский взнос;
- распределённые потери;
- пеня;
- компенсация;
- другая формула.

Начисление должно сохранять информацию о причине и правилах его формирования.

Потребление ресурса и начисление являются различными сущностями.

---

# 27. Финансовое обязательство собственника

**Финансовое обязательство собственника** — сумма, которую собственник или пользователь должен уплатить сообществу в результате начислений или других оснований.

Одно обязательство может быть погашено одним или несколькими платежами.

Один платёж может погашать несколько обязательств.

---

# 28. Платёж собственника

**Платёж собственника** — факт поступления денежных средств от собственника или пользователя в пользу сообщества.

Платёж может быть:

- банковским;
- наличным;
- полученным через платёжный сервис;
- полученным другим поддерживаемым способом.

Один платёж может распределяться между несколькими обязательствами.

Например:

Платёж 10 000 грн

→ членские взносы 4 000 грн  
→ электроэнергия 3 500 грн  
→ вода 1 500 грн  
→ пеня 1 000 грн.

---

# 29. Наличный платёж и кассовый документ

Наличный платёж является полноценным способом оплаты и должен учитываться в общей финансовой модели.

Для наличного платежа может формироваться приходный кассовый ордер и другие необходимые кассовые документы.

Наличный и безналичный платежи должны иметь общую модель финансового результата, но различные способы оформления и учёта.

---

# 30. Пеня

**Пеня** — дополнительное начисление за несвоевременное исполнение финансового обязательства.

Пеня рассчитывается на основании:

- суммы просроченного обязательства;
- периода просрочки;
- установленных правил.

Пеня является отдельным видом начисления и должна учитываться отдельно от основного обязательства.

---

# 31. Поставщик

**Поставщик** — организация или физическое лицо, предоставляющее сообществу ресурс, услугу или иное материальное обеспечение.

Для первого внедрения предусматриваются, в частности:

- поставщик электроэнергии;
- поставщик воды;
- организация по вывозу ТБО.

Один поставщик может предоставлять несколько ресурсов или услуг.

Поставщик не ограничивается коммунальными ресурсами.

---

# 32. Договор с поставщиком

**Договор с поставщиком** — основание, определяющее условия получения сообществом ресурса или услуги и порядок взаиморасчётов.

Договор может определять:

- поставщика;
- ресурс или услугу;
- период действия;
- тариф или порядок его определения;
- порядок учёта объёма;
- порядок выставления документов;
- сроки оплаты;
- другие условия.

---

# 33. Обязательство перед поставщиком

**Обязательство перед поставщиком** — финансовое обязательство сообщества перед поставщиком, возникшее вследствие получения ресурса, услуги или другого основания для оплаты.

Обязательство может возникать на основании:

- счёта;
- акта;
- данных приборов учёта;
- договора;
- другого первичного документа или установленного правила.

Обязательство может быть:

- непогашенным;
- частично погашенным;
- полностью погашенным;
- просроченным.

Отдельная универсальная сущность «финансовое обязательство сообщества» вне конкретных отношений с поставщиком на данном этапе не вводится.

---

# 34. Платёж поставщику

**Платёж поставщику** — факт перечисления денежных средств сообществом поставщику в счёт исполнения финансового обязательства.

Платёж может погашать одно или несколько обязательств перед поставщиком.

---

# 35. Расчёты с поставщиком

**Расчёты с поставщиком** — совокупность операций по учёту обязательств сообщества перед поставщиком и их погашению.

Расчёты включают:

- регистрацию обязательств;
- регистрацию документов поставщика;
- платежи;
- контроль задолженности;
- сверку взаиморасчётов;
- формирование отчётности.

Для коммунальных ресурсов расчёты с поставщиком могут быть связаны с показаниями соответствующих приборов учёта.

---

# 36. Расход сообщества

**Расход сообщества** — затрата, понесённая сообществом для обеспечения его деятельности, содержания общего имущества, получения ресурсов и услуг или выполнения других задач.

Примеры:

- электроэнергия насосной;
- электроэнергия освещения территории;
- вода для общих нужд;
- вывоз ТБО;
- заработная плата;
- ремонт;
- обслуживание;
- покупка оборудования или другого имущества.

Покупка, ремонт или обслуживание имущества на данном этапе учитываются как статьи/виды расходов и не требуют отдельного модуля учёта имущества.

Расход сообщества не обязательно является основанием для непосредственного начисления отдельному собственнику.

---

# 37. Смета

**Смета** — утверждённый план доходов и расходов сообщества на определённый период.

Смета может включать:

- планируемые расходы;
- планируемые источники финансирования;
- членские взносы;
- целевые взносы;
- расходы на коммунальные ресурсы;
- заработную плату;
- вывоз ТБО;
- ремонт;
- обслуживание;
- другие расходы.

Смета является инструментом планирования и не заменяет фактический финансовый учёт.

Фактические расходы и поступления учитываются независимо от плановых значений сметы.

Плановые и фактические значения должны позволять формировать анализ отклонений.

---

# 38. Источник финансирования

**Источник финансирования** — вид денежных поступлений, за счёт которых сообщество планирует или фактически покрывает расходы.

Примеры:

- членские взносы;
- целевые взносы;
- платежи за индивидуальное потребление;
- другие поступления.

Один расход может финансироваться одним или несколькими источниками.

Источник финансирования расхода и основание индивидуального начисления собственнику являются различными понятиями.

---

# 39. Финансирование расхода

**Финансирование расхода** — связь между расходом сообщества и источниками денежных средств, за счёт которых этот расход покрывается.

Например:

Электроэнергия насосной  
→ расход сообщества  
→ финансирование за счёт членских взносов.

Другой пример:

Оплата поставщику электроэнергии  
→ часть финансируется платежами за индивидуальное потребление  
→ часть финансируется членскими взносами.

Финансирование расхода и начисление собственнику являются различными операциями.

---

# 40. Сотрудник

**Сотрудник** — лицо, выполняющее работу для сообщества на основании трудовых отношений, гражданско-правового договора или другого законного основания.

Для первого внедрения предусматриваются, в частности:

- бухгалтер;
- слесарь;
- электрик;
- охранник.

---

# 41. Вознаграждение сотрудника

**Вознаграждение сотрудника** — сумма, начисленная сотруднику за выполненную работу.

Может применяться:

- фиксированная ставка;
- оклад;
- почасовая или иная тарифная система;
- ГПХ;
- другие варианты.

При расчёте вознаграждения должны учитываться соответствующие налоги и обязательные платежи.

---

# 42. Орган управления

**Орган управления** — лицо или группа лиц, имеющие полномочия по управлению сообществом.

В зависимости от типа сообщества могут использоваться:

- общее собрание;
- правление;
- председатель;
- ревизионная комиссия;
- другие органы.

---

# 43. Собрание

**Собрание** — организованная процедура рассмотрения вопросов и принятия решений участниками сообщества.

Собрание может включать:

- дату;
- место или формат проведения;
- повестку;
- вопросы;
- голосования;
- решения;
- протокол.

---

# 44. Голосование

**Голосование** — процедура выражения участниками сообщества своего решения по определённому вопросу.

Голосование должно учитывать:

- участников;
- право голоса;
- количество голосов;
- варианты ответа;
- результаты;
- кворум;
- итоговое решение.

Для садового товарищества предусматривается правило:

**1 участок = 1 голос.**

Правила определения количества голосов должны быть настраиваемыми в зависимости от типа сообщества и конкретного собрания.

---

# 45. Документ

**Документ** — электронный или связанный с системой документ, относящийся к деятельности сообщества.

Документ может быть связан с:

- сообществом;
- объектом;
- собственником;
- поставщиком;
- сотрудником;
- собранием;
- начислением;
- платежом;
- инженерной системой;
- прибором учёта;
- другим объектом предметной области.

---

# 46. Обращение

**Обращение** — запрос, заявление или сообщение пользователя, направленное сообществу или его представителю.

Обращение имеет жизненный цикл:

Создано  
→ Принято  
→ В работе  
→ Ответ подготовлен  
→ Закрыто.

История обработки обращения должна сохраняться.

---

# 47. Новость

**Новость** — информационный материал, публикуемый сообществом для информирования пользователей.

---

# 48. Объявление

**Объявление** — информационное сообщение, предназначенное для уведомления участников сообщества о событии, изменении, необходимости выполнить действие или другой информации.

---

# 49. Пользователь

**Пользователь** — лицо, имеющее учётную запись в Community OS.

Пользователь может иметь:

- один или несколько статусов;
- одну или несколько ролей;
- доступ к одному или нескольким сообществам.

Пользователь системы и собственник объекта являются различными понятиями.

---

# 50. Роль

**Роль** — набор полномочий пользователя в системе.

Примеры:

- собственник;
- бухгалтер;
- кассир;
- председатель;
- член правления;
- сотрудник;
- администратор.

---

# 51. Личный кабинет

**Личный кабинет** — пользовательский интерфейс, через который собственник или другой участник сообщества получает доступ к относящейся к нему информации и функциям.

В частности, личный кабинет может предоставлять:

- информацию об объектах;
- начисления;
- платежи;
- задолженность;
- показания приборов;
- документы;
- новости;
- объявления;
- обращения;
- онлайн-оплату в перспективе.

Личный кабинет может использоваться собственником для самостоятельной передачи показаний приборов учёта.

---

# 52. Историческая связь

**Историческая связь** — связь между сущностями, для которой важно сохранять период её действия.

Примеры:

- собственник владеет объектом определённый период;
- тариф действует определённый период;
- прибор установлен с определённой даты;
- сотрудник работает определённый период;
- договор с поставщиком действует определённый период;
- правило распределения потерь действует определённый период;
- объект подключён к инженерной системе определённый период;
- прибор учёта установлен или используется в определённой ветви определённый период.

Система должна позволять определить состояние такой связи на конкретную дату.

---

# 53. Универсальная сущность

**Универсальная сущность** — элемент предметной модели, который используется различными типами сообществ без изменения своей фундаментальной природы.

Например:

- сообщество;
- собственник;
- объект;
- лицевой счёт;
- начисление;
- платёж;
- документ;
- прибор учёта;
- инженерная система.

---

# 54. Специализация сообщества

**Специализация сообщества** — набор правил и функций, характерных для конкретного типа сообщества.

Например:

Для СТ:

- участок;
- кадастровый номер;
- членские взносы;
- правило «1 участок = 1 голос».

Для ОСМД:

- дом;
- квартира;
- общее имущество;
- особенности распределения расходов.

Специализация не должна приводить к созданию отдельной программной системы.

---

# 55. Первое внедрение

Первая практическая реализация Community OS выполняется для садового товарищества.

Основными объектами первого внедрения являются:

- земельные участки;
- собственники;
- лицевые счета;
- приборы учёта;
- инженерные системы;
- начисления;
- платежи;
- поставщики;
- расходы;
- смета;
- сотрудники;
- документы;
- собрания;
- голосования.

Особое практическое значение для первого внедрения имеют:

- учёт электроэнергии;
- учёт воды;
- несколько независимых ветвей учёта;
- общие и промежуточные приборы;
- инженерная структура электроснабжения;
- инженерная структура питьевого и поливного / технического водоснабжения;
- анализ баланса потребления;
- выявление потерь электроэнергии по улицам;
- возможность распределения потерь в соответствии с правилами сообщества;
- финансирование общих расходов за счёт сметы и членских взносов.

---

# 56. Проверка универсальности

После первого внедрения в садовом товариществе предполагается возможность использования Community OS в ОСМД/ЖСК.

Такой переход является практической проверкой универсальности предметной модели.

Например:

Садовое товарищество:

Сообщество  
→ Участок  
→ Лицевой счёт.

ОСМД:

Сообщество  
→ Дом  
→ Квартира  
→ Лицевой счёт.

При этом отдельно может существовать инженерная структура:

Дом  
→ система электроснабжения  
→ ввод  
→ распределительное устройство  
→ приборы учёта  
→ квартиры.

Фундаментальные финансовые, ресурсные и управленческие механизмы при этом должны оставаться общими.

---

# 57. Независимость сущностей

Сущности предметной области не должны искусственно объединяться ради упрощения реализации.

В частности:

- собственник ≠ пользователь;
- собственник ≠ лицевой счёт;
- объект ≠ лицевой счёт;
- объект ≠ инженерная система;
- инженерная система ≠ объект собственности;
- прибор учёта ≠ объект;
- показание ≠ потребление;
- потребление ≠ начисление;
- начисление ≠ платёж;
- обязательство собственника ≠ платёж;
- обязательство перед поставщиком ≠ платёж поставщику;
- расход сообщества ≠ начисление собственнику;
- поставщик ≠ обязательство;
- сообщество ≠ тип сообщества;
- баланс потребления ≠ показание;
- потери ≠ исходное потребление;
- распределённые потери ≠ фактически измеренное потребление.

Аналитические показатели и расчётные результаты не должны без необходимости превращаться в самостоятельные первичные сущности.

---

# 58. Расширяемость

Предметная модель должна позволять добавлять:

- новые типы объектов;
- новые типы сообществ;
- новые ресурсы;
- новые инженерные системы;
- новые типы инженерных элементов;
- новые виды начислений;
- новые способы оплаты;
- новые алгоритмы расчётов;
- новые роли;
- новые виды документов;
- новые бизнес-процессы;
- новые виды аналитики;
- новые правила распределения.

Добавление нового типа сообщества не должно требовать изменения фундаментальных сущностей платформы.

---

# 59. Принцип предметной модели

Предметная модель Community OS должна отражать реальную деятельность сообщества, а не особенности конкретной программной реализации.

Программная реализация должна адаптироваться к предметной области, а не заставлять сообщество изменять реальные процессы только ради удобства программы.

При разработке новых функций необходимо сначала определить:

**реальная потребность  
→ бизнес-процесс  
→ предметная модель  
→ архитектурное решение  
→ документация  
→ техническое задание  
→ разработка.**
