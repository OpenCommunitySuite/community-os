# ADR-014 — Persistence, tenant isolation, storage and recovery

**Статус:** Accepted / Принято
**Язык документа:** русский

---

## Контекст

ADR-001–ADR-011 определили предметные контексты Community OS, их идентичность, историю, правила, доступ и интеграционную семантику. ADR-012 зафиксировал commercial multi-tenant SaaS, Control Plane, stable Community identity, Community Placement и Placement Generation. ADR-013 принял logical modular monolith, module-owned internals, application transaction boundaries, Read Models / Projections и отдельные Web/API и Worker runtime entry points.

Stage K должен определить persistence architecture, способную начать работу в Shared Placement и в дальнейшем поддержать несколько shared clusters, Dedicated Placement и relocation без изменения domain model. Одновременно shared storage не должен стирать module ownership, tenant isolation не должна зависеть только от application filters, а recovery одного Community не должен откатывать другие Communities.

Бинарные representations требуют отдельного object storage, но PostgreSQL и object storage не образуют общую транзакцию. Backup и recovery должны восстанавливать семантически согласованное authoritative state, а не только запускать базу данных. Schema migrations, relocation и final deletion должны оставаться контролируемыми и проверяемыми при сохранении исторической объяснимости.

## Проблема

Без явных persistence boundaries Community OS рискует получить одну из несовместимых крайностей:

- shared database, используемую как неограниченный cross-module и cross-tenant API;
- отдельную несовместимую persistence model для каждого Community или Dedicated Placement;
- доверие к `community_id` из client request или к connection-scoped tenant state;
- RLS как замену application scope, authorization или domain admissibility;
- JSONB/EAV как замену известной предметной модели;
- identity, зависящую от database, sequence, object key или Placement;
- distributed transaction между Platform, Community Placement и object storage;
- backup без доказанного restore либо rollback всего Shared Placement ради одного Community;
- migration, relocation или deletion как один большой необратимый технический шаг.

Требуется зафиксировать логические границы и invariants, не выбирая SQL layout, ORM, provider, migration tool, backup product или reliable job implementation.

## Область решения

Настоящий ADR определяет:

- PostgreSQL baseline и смысл persistence portability;
- Platform Persistence Boundary, Community Placement Persistence Boundary и Transactional Persistence Boundary;
- shared-table baseline, explicit Community Scope и trusted transaction-scoped Community context;
- application scope, RLS и tenant-aware constraints как defense in depth;
- stable identifiers и local/cross-boundary referential integrity;
- module ownership persistence structures;
- relational core, controlled JSONB и context-owned typed extension pattern;
- concurrency и local ACID transaction boundary;
- Read Models / Projections как отдельный persistence class;
- metadata в PostgreSQL и binary content в S3-compatible object storage;
- retention, backup, disaster recovery, Selective Community Recovery и restore verification;
- relocation persistence contract и Shared/Dedicated equivalence;
- schema state и migration principles;
- purpose-specific cross-Community/platform projections;
- indexing/uniqueness, deletion и persistence encryption boundaries;
- failure-scenario и cross-context invariants.

Настоящий ADR не определяет authentication/authorization implementation, reliable job runtime, deployment topology, physical database schema, SQL, конкретный provider/tool или domain-specific retention/correction rules.

## Связь с ADR-001–ADR-013

- Database, schema, persistence boundary и projection не являются bounded contexts и не меняют ownership ADR-002.
- Typed extensions не вводят universal Configuration entity и сохраняют context-owned applicability, meaning и history ADR-003.
- WAL, recovery point, Schema Version, concurrency token и storage timestamp не являются domain history или domain time ADR-004.
- Schema Version и technical constraint не являются Rule Version или universal Rule ADR-005.
- Finance, Resource Accounting, Governance, Documents и Communications сохраняют собственные distinct facts и lifecycle ADR-006–ADR-009.
- RLS, database role и Platform Admin status не являются Domain Power, Subject или domain admissibility ADR-010.
- External representation, received information и recognized fact различаются согласно ADR-011.
- Stable Community ID, Placement, Placement Generation, Platform Subject Identity Anchor и Community-owned Subject records сохраняют границы ADR-012.
- Shared persistence не является module API; local transaction, read models, Web/API и Worker соблюдают ADR-013.

## Решение

### 1. PostgreSQL baseline и portability

PostgreSQL является обязательной primary transactional DBMS Community OS. Архитектура может намеренно использовать PostgreSQL-specific capabilities, включая RLS, constraints, JSONB, locking, appropriate types и indexes.

Cross-RDBMS portability к MySQL, MSSQL, SQLite или другому transactional engine не является целью. Persistence portability означает возможность перемещать Community data между совместимыми PostgreSQL Placements/deployments без изменения stable domain identity, application contracts и domain semantics.

Архитектура не должна требовать proprietary capability одного managed PostgreSQL provider. Это ограничение не запрещает managed service, но сохраняет возможность восстановить или перенести authoritative state в совместимое PostgreSQL окружение.

### 2. Persistence boundaries

Архитектура различает:

1. **Platform Persistence Boundary** — persistence state, принадлежащее platform/Control Plane responsibilities.
2. **Community Placement Persistence Boundary** — authoritative persistence Community-owned state в resolved Community Placement.
3. **Transactional Persistence Boundary** — логическая persistence scope, внутри которой фактически доступны одна local ACID transaction и enforceable local constraints.
4. **Projection Persistence Class** — derived read-side state с отдельными freshness/rebuild semantics.
5. **Binary/Object Storage Boundary** — storage binary content, связанного через metadata и domain relationships.

Эти boundaries нормативно определяют ownership, independent schema state, recovery responsibility, transaction availability и cross-boundary contract. Они не требуют автоматически отдельного PostgreSQL server, process, cluster, catalog, database или schema в конкретной реализации.

Platform и Community persistence могут первоначально размещаться на одном PostgreSQL cluster/server. Architecture не зависит от такой co-location. Physical co-location не создаёт cross-boundary ACID, FK, direct SQL access или общий ownership автоматически.

Logical persistence boundary не является bounded context, module или новой domain entity.

### 3. Community persistence baseline

Community-owned transactional data использует shared relational structures внутри Community Placement Persistence Boundary. Каждый Community-owned record имеет explicit Community Scope, концептуально выражаемый stable `community_id`.

`community_id` является architectural invariant, а не необязательным application filter. Он остаётся explicit в Shared и Dedicated Placements.

Platform/global state не получает искусственный Community Scope. Каждый persistence structure должен быть явно классифицирован как platform-owned, Community-owned, purpose-specific cross-Community projection/reference или иная обоснованная категория.

Schema-per-Community и database-per-Community не являются baseline. Dedicated Placement является placement mode с той же logical persistence model, а не другим domain/storage design.

### 4. Trusted routing и persistence context

Community-scoped persistence access следует conceptual chain:

```text
hostname
→ Community ID
→ Placement + Placement Generation
→ authenticated/authorized application execution context
→ resolved Transactional Persistence Boundary
→ DB transaction
→ trusted transaction-scoped Community DB context
→ explicit application Community scope + RLS + constraints
```

Hostname не является Community identity или authorization. `community_id`, hostname, route value или иной client-supplied input не является trusted context сам по себе.

Trusted Community context формируется только из resolved application execution context после применимых authentication, authorization и Placement checks. ADR-014 определяет требование к persistence boundary, но не механизм authentication/authorization.

DB Community context устанавливается для transaction scope. Connection-scoped tenant state, способное пережить transaction и утечь при reuse pooled connection, не допускается как архитектурная основа.

Community-owned persistence должна fail closed при отсутствии, недействительности или mismatch trusted Community context. Persistence implementation при этом сохраняет explicit Community Scope там, где он нужен для queries, integrity, ownership и explainability.

Эти правила одинаково применяются к Web/API Host и Worker Host. Service/worker identity не создаёт Subject, Domain Power или право bypass tenant isolation.

### 5. RLS и defense in depth

PostgreSQL RLS является обязательной default линией defense in depth для Community-owned transactional tables, включая такие tables в Dedicated Placement.

Application-level Community Scope остаётся обязательным. RLS не заменяет:

- authentication или technical authorization;
- domain admissibility;
- module contracts и encapsulation;
- referential integrity и domain constraints;
- correct Placement resolution.

Exception из RLS default допустимо только для явно классифицированной persistence structure с документированным ownership, purpose и isolation justification.

Normal runtime roles не должны произвольно bypass RLS. Migration, maintenance, restore и recovery используют отдельные privileged technical boundaries. Cross-Community platform operation не реализуется casual отключением RLS; это explicit controlled process с purpose-specific access boundary. Детали roles, grants, privileged authorization и audit принадлежат ADR-015/Implementation Baseline.

### 6. Platform и Community persistence

Platform Persistence Boundary включает, где применимо:

- User Account;
- optional Subject Identity Anchor;
- SaaS Customer и Billing Account;
- Subscription, Plan и Entitlement state;
- Community registry;
- Placement catalog и Placement Generation;
- другое platform-owned state.

Community Placement Persistence Boundary включает Community-owned Subjects, Objects, Finance, Resource Accounting, Governance, Documents, Communications, Community configuration/history и связанные domain facts.

Между этими boundaries не предполагаются PostgreSQL FK или одна ACID transaction. Cross-boundary relations используют stable opaque identifiers и published application/domain contracts.

User Account не является Subject. Subject Identity Anchor остаётся minimal, optional и не является global full Subject profile/catalog. Community Subject может существовать без Account и Anchor. Linkage не создаётся по совпадению name, email, phone или contact data без допустимого verified linking process.

Один Anchor не создаёт cross-Community visibility. Community relocation перемещает Community-owned Subject records вместе с Placement, но не требует перемещать User Account или Anchor. Authentication/linking implementation относится к ADR-015.

### 7. Stable identifiers

Significant entity IDs являются stable, opaque, conceptually globally unique и Placement-independent. Они переживают Shared↔Dedicated relocation и изменение physical storage.

Global uniqueness не означает global visibility, platform ownership, authorization или admissibility. Knowledge of identifier не предоставляет access. Community Scope остаётся отдельным invariant и не выводится только из ID.

Placement-dependent surrogate/sequence допустим как internal optimization, но не становится portable domain/application identity, public contract или cross-boundary reference.

Exact identifier format не определяется.

### 8. Referential integrity

Внутри одного Transactional Persistence Boundary используются strong PostgreSQL constraints и FK там, где они семантически применимы. Tenant-safe integrity должна предотвращать inadmissible cross-Community relationships; Community-local uniqueness должна включать или иным образом enforce Community Scope.

RLS и referential integrity решают разные задачи: RLS ограничивает допустимый row access, constraints защищают structural integrity. Ни один механизм не определяет domain admissibility самостоятельно.

Across Platform↔Community boundaries или independent Placements используются stable references и application/domain contracts, а не fake cross-database FK.

### 9. Module-owned persistence

Каждая table, view, projection или иная persistence structure имеет одного owning module. Shared Placement DB не разрешает arbitrary SQL read/write internal tables другого module.

Within one Transactional Persistence Boundary controlled cross-module FK может enforce deliberately published stable identity/reference contract. Такой FK:

- не является application API или самим semantic contract;
- не разрешает direct SQL access чужого module;
- не раскрывает repository, Unit of Work, ORM session или persistence internals;
- не превращает physical schema в Module Public Contract;
- имеет lifecycle, координируемый owning modules и controlled migration process.

Если modules позже окажутся в разных persistence boundaries, stable semantic reference contract сохраняется, даже когда physical FK невозможен.

PostgreSQL schema-per-module не является обязательным invariant. Module boundaries обеспечиваются ownership, ADR-013 contracts/layers и architecture enforcement, а не SQL naming.

### 10. Relational core и controlled JSONB

Stable domain-significant concepts моделируются relationally, если они участвуют в identity, relationships, tenant isolation, temporal semantics, Finance, constraints, authorization/admissibility, important search/reporting или historically significant relations.

JSONB допустим для genuinely extensible, provider-specific, configuration-specific или weakly structured data. JSONB не используется, чтобы избежать modeling известного domain concept.

External/source representation в JSONB или binary storage остаётся distinct от received information и recognized domain fact ADR-011. Recognition не следует из persistence format.

Если extension становится domain-significant, architecture должна позволять promotion в explicit relational structure с сохранением applicable provenance, historical meaning и source representation. Promotion не переписывает прошлое молча.

### 11. Typed configurable attributes

Typed configurable attributes являются context-owned controlled extension pattern только для явно поддерживаемых extension points.

Owning bounded context определяет:

- applicability;
- type и validation;
- Community/domain scope;
- temporal meaning и history;
- authorization/admissibility;
- promotion в explicit modeled concept.

`Attribute Definition` и `Attribute Value` могут описывать локальный conceptual pattern, но не вводятся как universal platform-wide entities, способные хранить произвольные domain facts.

Attributes/EAV не заменяют Ownership, Financial Obligation, Payment, Voting Right, Power/Representation, Meter, Accounting Point, Reading, Document, Subject identity или другой known domain concept.

Где значение historically significant, фактически применимая definition/version/context должна оставаться определимой. Exact physical typed-value representation отложено.

### 12. Concurrency

Optimistic concurrency является default для domain-significant state. Blind last-write-wins не является default и не должно silently терять concurrent change.

Targeted short DB serialization/locking допустимы внутри application-owned local transaction, когда concrete invariant этого требует. Locks не удерживаются во время human interaction или внешнего/long-running process.

Technical concurrency token не является:

- domain history;
- Rule Version;
- Document Revision;
- Voting snapshot/version;
- Placement Generation;
- Schema Version.

Exact isolation levels, tokens и lock primitives определяются Implementation Baseline.

### 13. Transaction boundary

Одна ACID transaction ограничена одним resolved Transactional Persistence Boundary. Module boundary не равен transaction boundary: cohesive local use case может атомарно затронуть несколько modules только через их public contracts и только когда всё affected state фактически находится в одной boundary.

Transaction не пересекает Platform↔Community boundary, independent Placements, PostgreSQL↔object storage или external system. Mandatory distributed transaction/2PC не вводится.

Cross-boundary provisioning, relocation, binary convergence, selective recovery и final deletion являются explicit durable, resumable и recoverable processes. Настоящий ADR фиксирует persistence state/invariants таких processes, но job store, leases, outbox/inbox, retries, deduplication и broker определяет ADR-016.

### 14. Read Models / Projections

Read Models / Projections являются отдельным logical persistence class и могут первоначально физически храниться в PostgreSQL того же Placement.

Каждая projection:

- derived и не является source of truth;
- read-only относительно Domain state;
- имеет declared owner/producer;
- имеет Community Scope и tenant isolation, где содержит Community data;
- имеет visibility/authorization semantics;
- имеет freshness/consistency semantics;
- имеет rebuild/reconciliation semantics;
- считается rebuildable только при доказанной полноте source и процедуры rebuild.

Stale projection не предоставляет Access Right, Domain Power или admissibility и не является единственным основанием irreversible current-state action, когда требуется current authoritative state.

Полностью rebuildable projection может иметь отличные backup requirements. Она может позже переместиться в отдельное DB/search storage без изменения domain semantics или ownership. Physical storage, indexes, update delivery и monitoring отложены.

### 15. Purpose-specific cross-Community/platform reads

Billing usage, quotas и platform operational summaries используют purpose-specific Platform-owned aggregate/read models.

Каждый такой read model имеет explicit purpose, minimized data, owner/producer, visibility, freshness и rebuild/reconciliation semantics. Он не становится central copy всех Community domain data «на всякий случай».

Routine unrestricted cross-tenant SQL и casual RLS bypass не являются normal mechanism. Platform Admin status не означает unrestricted Community content access. Privileged cross-Community operation является explicit controlled process.

Cross-Community/platform reads не зависят от cross-Placement SQL joins и должны работать при нескольких PostgreSQL clusters и Dedicated Placements.

### 16. Binary/object storage

Production binary content хранится в S3-compatible object storage через abstraction. PostgreSQL хранит metadata, domain relationships и applicable lifecycle/provenance state, но не primary binary blobs.

Metadata может включать, где применимо:

- stable identifiers соответствующих domain Representation и/или File/blob/content object как distinct concepts;
- Community Scope;
- domain relationship;
- replaceable Storage Locator;
- checksum, size и content/media type;
- original filename;
- significant timestamps и provenance;
- retention/classification state.

Document, Document Revision, Document Representation, File/blob/content object и Storage Locator различаются. Binary object или storage key не является автоматически Document, Representation, Reading, domain identity или authorization credential. Knowledge of locator/key не предоставляет access.

Historically significant recognized representation не перезаписывается in-place. Изменение bytes означает новый applicable immutable content/representation identity согласно owning-domain semantics; Storage Locator может изменяться без изменения domain identity.

File access следует domain/technical authorization. Exact signed URL, bucket layout, provider, scanner и encryption implementation не определяются.

### 17. DB/object convergence и incomplete state

PostgreSQL и object storage не образуют distributed transaction. Их consistency достигается recoverable process semantics.

Architecture должна позволять:

- explicit/detectable incomplete state;
- idempotent completion/reconciliation;
- safe orphan/temporary object handling;
- distinction uploaded bytes from recognized domain fact;
- prevention of cleanup for object already referenced by authoritative state;
- recovery verification of required DB↔object relationships.

DB metadata commit без завершённого object action и object upload без committed metadata не считаются успешно завершённой recognized representation автоматически. Runtime mechanics принадлежат ADR-016.

### 18. Retention и lifecycle

Domain lifecycle, binary retention, temporary/orphan cleanup, Community archive, final deletion и backup retention являются distinct.

Removal, replacement или end of domain relationship не означает automatic physical deletion binary content. Retention зависит от representation/data class и applicable policy. Temporary uploads, failed/unrecognized imports и orphan objects могут иметь отдельные cleanup policies.

Community archive сохраняет data согласно archive policy. Final deletion является отдельным controlled lifecycle process. Backup copies истекают по собственному retention lifecycle; application deletion не обещает immediate disappearance из immutable backups.

Exact legal/configurable retention durations и legal hold rules не определяются.

### 19. Backup и coordinated recovery set

Backup/recovery охватывает authoritative relational state и binary objects, необходимые для recognized authoritative representations. Platform Persistence Boundary имеет собственную recovery responsibility, отдельную от Community Placements.

Physically atomic PostgreSQL+S3 snapshot не требуется. Требуется возможность восстановить semantically consistent authoritative state и определить/устранить допустимые incomplete states.

PostgreSQL persistence должна поддерживать PITR через appropriate base backup/WAL strategy или equivalent capability. Backups должны находиться вне primary Placement/failure domain.

Fully rebuildable projections могут быть rebuilt вместо equivalent restore только при доказанной rebuildability и наличии recoverable authoritative sources.

Backup без tested restore procedure недостаточен. Restore test должен исполнять recovery procedure, а не только проверять читаемость backup files.

Initial internal objectives:

- RPO ≤ 1 hour;
- RTO ≤ 4 hours.

Это internal operational objectives для обычного Platform/Placement disaster recovery baseline, а не external SLA и не обещание такого же RTO для complex Selective Community Recovery.

### 20. Placement Disaster Recovery и Selective Community Recovery

Placement-level PITR является основным disaster-recovery mechanism. Один tenant-local business error не откатывает всех Communities Shared Placement.

Business error обычно исправляется domain-aware correction, cancellation, recalculation или reclassification с сохранением history.

Selective Community Recovery допускается для exceptional tenant-local corruption и концептуально выполняется так:

```text
backup/PITR
→ isolated temporary restore copy of affected Placement
→ restore copy to target recovery point
→ extract affected Community
→ verify identity, scope, integrity and provenance
→ controlled reconciliation/recovery into current authoritative Placement
```

Production Shared Placement не откатывается к старому point ради одного Community. Selective recovery не является ordinary CSV import/export или способом silent rewrite. Dedicated Placement предоставляет stronger recovery isolation, но использует те же semantics.

Exact extraction/reconciliation tooling и privileged authorization/audit отложены.

### 21. Restore verification

Recovery не завершён только потому, что PostgreSQL process запускается. Перед normal service resume restored Platform/Placement проверяется на применимые:

- persistence и referential integrity;
- Community Scope и tenant isolation configuration;
- DB↔object storage consistency;
- expected Schema State compatibility;
- Placement mapping и Placement Generation consistency;
- technically checkable critical invariants;
- availability of authoritative binary representations.

Failure проверки не является successful recovery. Exact automation, monitoring, alerts и operational runbooks принадлежат ADR-017.

### 22. Community relocation

Community relocation является observable, resumable и controlled operation без изменения domain IDs.

Conceptual flow:

```text
prepare and validate target
→ verify compatible Schema State and object accessibility
→ pre-copy authoritative data where appropriate
→ enter short Community-specific write-fenced/read-only window
→ drain, finish, reject or re-resolve relevant active Web/API and Worker contexts
→ copy remaining authoritative state
→ verify consistency
→ switch Placement mapping and Placement Generation
→ enable target writes
→ monitor before retiring source
```

Source является authoritative до confirmed cutover; target — после confirmed switch. Independent authoritative writes в source и target одновременно запрещены.

После cutover context со stale Placement Generation не может писать в old Placement и должен быть rejected либо выполнить re-resolution. Это применяется к Web/API и persistent Worker work.

Rollback до cutover может abandon prepared target. После confirmed cutover возвращение является новой controlled relocation/recovery operation, а не silent rollback.

Binary/object accessibility является частью relocation consistency. Fully live zero-write-downtime migration не требуется first baseline. Job lease, retry engine, queue, CDC, replication/copy и exact fencing technology не определяются.

### 23. Shared и Dedicated Placement

Shared и Dedicated Community Placements используют одну logical persistence/isolation model. Даже single-Community Dedicated Placement сохраняет:

- explicit `community_id` и Community Scope;
- trusted transaction-scoped Community context;
- RLS;
- tenant-aware constraints;
- fail-closed behavior;
- совместимые schema/migration contracts.

Dedicated Placement предоставляет physical, operational и recovery isolation, а не другой domain model. Shared↔Dedicated relocation не требует преобразования во вторую persistence model.

### 24. Schema State и migrations

Platform Persistence Boundary и каждый Community Placement independently track versioned Schema State. Это не означает arbitrary per-Community schema forks: Shared и Dedicated Placements следуют compatible controlled migration contracts, хотя rollout timing/state может различаться.

Migrations являются versioned, deterministic controlled operations. Normal Web/API и Worker runtime roles не имеют DDL privileges. DDL выполняется отдельным migration operation/role.

Preferred lifecycle:

```text
expand
→ deploy compatible application
→ resumable/observable backfill
→ verify
→ contract in a separately controlled step
```

Destructive change является отдельным controlled action. Long backfill не является giant deployment transaction и может безопасно resume после interruption.

Limited coexistence of compatible schema states допускается там, где нужно rollout. Runtime проверяет supported Schema State и fail closed при unknown/incompatible state.

Placement Generation не является Schema Version. Relocation target должен иметь compatible Schema State до authoritative switch.

Migration framework, version table, exact compatibility window и rollout automation не определяются.

### 25. Indexing и uniqueness

Community Scope является частью physical access design. Indexing учитывает `community_id`, RLS и реальные query patterns, но ADR не требует, чтобы каждый index механически начинался с `community_id`.

Global uniqueness и Community-local uniqueness различаются. Community-local unique constraint должен включать или иначе enforce Community Scope там, где это применимо.

Exact indexes, partitioning и constraint SQL относятся к Implementation Baseline.

### 26. Referential deletion и final Community deletion

Domain-significant lifecycle выражается context-specific ended, revoked, cancelled, superseded, corrected и иными semantics, а не physical DELETE по умолчанию.

Universal `is_deleted`/soft-delete super-pattern не вводится. `ON DELETE CASCADE` допустим только для genuinely subordinate technical/internal structures, где ownership semantics это оправдывает. Независимые Finance, Governance, Resource, Documents и другие historically significant facts не исчезают через accidental cascade.

Final Community deletion является privileged explicit lifecycle process, а не one SQL DELETE. Он учитывает Community-owned transactional data, binary objects, derived projections, integration remnants и другие persistence artifacts.

Application deletion не означает immediate disappearance из immutable backups; residual copies истекают по backup retention policy. Authorization и security audit detail принадлежат ADR-015, reliable execution — ADR-016/ADR-017.

### 27. Persistence encryption boundary

Production persistence должна поддерживать protection in transit и at rest для PostgreSQL, object storage и backups.

Persistence formats, backup/restore, schema migration и relocation не должны препятствовать applicable encryption, key rotation или key recovery requirements. Selective application-level encryption может применяться к classified sensitive fields, но custom encryption каждого field не является baseline.

Настоящий ADR не определяет algorithms, KMS/provider, secret manager, key hierarchy/ownership, credentials, rotation procedure, privileged authorization или security audit. Эти решения принадлежат преимущественно ADR-015 и Implementation Baseline.

## Validation scenarios

### Pooled connection reused for another Community

Каждая transaction получает новый trusted Community context; отсутствие/mismatch context fail closed. Connection reuse не переносит tenant state. Exact mechanism deferred.

### Stale Worker после relocation

Worker context со stale Placement Generation не пишет в source после cutover, а rejected/re-resolved. Lease/retry mechanics deferred to ADR-016.

### DB metadata commit, object action incomplete

State остаётся detectable и recoverable; representation не считается полностью доступной автоматически. Reconciliation/completion mechanics deferred.

### Object upload succeeded, DB process crashed

Unlinked object остаётся temporary/orphan candidate, а не domain fact. Cleanup policy не удаляет object, если authoritative reference появился.

### One Community corrupted in Shared Placement

Обычная business error использует domain correction. Exceptional corruption использует isolated temporary restore copy и selective recovery, не rollback production Shared Placement.

### Full Placement failure

Off-failure-domain backups, PostgreSQL PITR, required objects и restore verification восстанавливают semantically consistent state в пределах internal objectives.

### Stale projection

Projection freshness определима; stale projection не предоставляет rights и не подтверждает irreversible current-state action.

### Incompatible schema during rollout

Runtime обнаруживает unsupported Schema State и fail closed. Placement Generation не используется как Schema Version.

### Interrupted migration/backfill

Controlled migration оставляет determinable compatible state; long backfill является resumable/observable.

### Final deletion while backups remain

Live artifacts удаляются controlled process; immutable backup residuals истекают отдельно и не представляются немедленно исчезнувшими.

### Dedicated Placement moved back to Shared

Одинаковые Community Scope, RLS, constraints, schema contracts и stable IDs позволяют controlled relocation без второй persistence model.

## Cross-context validation: meter photograph

```text
Meter
→ Meter Installation
→ Accounting Point

source/manual/integration
→ received information
→ photograph binary content + metadata/provenance
→ validation/recognition by Resource Accounting
→ Reading, only if recognized
→ Consumption/other consequences by their own rules
```

Persistence хранит bytes и metadata, но не владеет Reading semantics. Photograph может быть unreadable, показывать wrong Meter, содержать несколько registers/values или существовать без recognized Reading. OCR output остаётся derived/received information до domain recognition.

Photograph ≠ Reading; OCR/extracted value ≠ Reading; received information ≠ recognized domain fact; Meter ≠ Meter Installation ≠ Accounting Point; File/blob ≠ Document ≠ Revision ≠ Representation; Storage Locator ≠ identity; checksum equality ≠ semantic duplicate.

Если photograph/content/provenance historically significant для recognized result, они остаются explainable и recoverable согласно applicable retention policy. OCR/UI implementation не определяется.

## Архитектурные инварианты

1. PostgreSQL является primary transactional DBMS; cross-RDBMS portability не является целью.
2. Persistence boundary, database, schema и projection не являются bounded context автоматически.
3. Community-owned record имеет explicit Community Scope.
4. Platform/global data не получает искусственный Community Scope.
5. Client input не является trusted Community context.
6. Trusted DB Community context transaction-scoped и fail-closed.
7. Web/API и Worker соблюдают одну tenant-isolation model.
8. Application scope, RLS и tenant-aware constraints обязательны и дополняют друг друга.
9. RLS не заменяет authorization, domain admissibility, module boundary или integrity.
10. Dedicated Placement не отменяет `community_id`, trusted context, RLS или constraints.
11. Normal runtime не имеет arbitrary RLS bypass или DDL.
12. Platform и Community persistence имеют separate logical boundaries независимо от co-location.
13. Cross-boundary FK, ACID/2PC и distributed SQL не предполагаются.
14. Significant ID stable, opaque и Placement-independent.
15. Global uniqueness не предоставляет visibility или access.
16. Local surrogate не становится portable identity.
17. FK/constraint enforce contract, но не является application API.
18. Shared DB не разрешает direct access internals другого module.
19. Relational core обязателен для known domain-significant concepts.
20. JSONB и typed attributes не заменяют domain model.
21. Typed configurable attributes context-owned, не universal EAV.
22. Blind last-write-wins не является default.
23. Concurrency token, Schema Version, Placement Generation и domain versions различаются.
24. One ACID transaction не пересекает Transactional Persistence Boundary.
25. External/object/cross-boundary steps используют recoverable process, не distributed transaction.
26. Projection derived, tenant-isolated и не source of truth.
27. Stale projection не grants rights при требовании current state.
28. Purpose-specific platform read model не является central copy всех tenant data.
29. Binary content, domain Representation/File identity и Storage Locator различаются.
30. Object key не является authorization credential.
31. Historically significant representation не перезаписывается in-place.
32. DB и object storage converge recoverably с detectable incomplete state.
33. Domain lifecycle, binary retention, archive, deletion и backup retention различаются.
34. Backup не считается достаточным без tested restore.
35. Selective Community Recovery не откатывает production Shared Placement.
36. Restore завершается только после applicable integrity/consistency verification.
37. Relocation всегда имеет одну authoritative side.
38. Stale Placement Generation не пишет в old Placement после cutover.
39. Shared и Dedicated Placements используют одну logical model.
40. Schema State independently tracked, но не образует arbitrary per-Community fork.
41. Placement Generation не является Schema Version.
42. Domain lifecycle не заменяется universal soft delete.
43. Broad cascade не удаляет independent historically significant facts.
44. Application deletion не обещает immediate erasure immutable backups.
45. Persistence поддерживает encryption/recovery requirements без выбора security implementation.
46. Platform Admin status не означает unrestricted Community content access.
47. User Account, Subject Identity Anchor и Community Subject остаются distinct.
48. Photograph или stored bytes не являются Reading.

## Последствия решения

### Положительные последствия

- Shared SaaS baseline получает defense-in-depth tenant isolation.
- Community может переезжать между Shared и Dedicated Placements без изменения identity/model.
- Platform identity и Community-owned Subject data остаются изолированными.
- Module ownership сохраняется даже в shared PostgreSQL.
- Domain-significant state получает relational integrity и lost-update protection.
- Binary representations масштабируются отдельно от transactional metadata.
- Recovery охватывает authoritative DB/object state и проверяется practically.
- Selective tenant recovery не откатывает соседние Communities.
- Future multi-cluster evolution не требует cross-Placement SQL или domain redesign.

### Цена и риски

- RLS, application scope и tenant-aware constraints требуют согласованной реализации и тестирования.
- Logical boundary без physical separation требует строгой discipline roles/contracts/migrations.
- DB/object convergence, relocation, backfill, recovery и deletion требуют durable orchestration в ADR-016/ADR-017.
- Shared Placement усложняет selective recovery и может не уложиться в обычный RTO.
- Purpose-specific projections требуют freshness/visibility governance.
- Immutable significant binaries и retention policies увеличивают storage/operational cost.
- PostgreSQL-specific capabilities уменьшают cross-RDBMS portability сознательно.

## Рассмотренные и отклонённые альтернативы

- **Только application filters без RLS:** недостаточная defense in depth.
- **Connection-scoped tenant state:** опасно при pooling и context leakage.
- **Routine RLS bypass:** разрушает isolation boundary и делает privileged access нормой.
- **Schema-per-Community baseline:** усложняет migrations/operations и создаёт divergent model.
- **DB-per-Community baseline:** преждевременная operational cost; Dedicated остаётся option.
- **Другая model для Dedicated Placement:** ломает relocation и domain portability.
- **Distributed SQL joins:** несовместимы с multiple/dedicated Placements.
- **Cross-boundary FK или 2PC:** создают зависимость от co-location и false atomicity.
- **JSONB вместо domain model:** ослабляет identity, integrity, history и query semantics.
- **Universal EAV:** превращает known domain facts в generic attributes.
- **Shared DB как module API:** нарушает ADR-013 ownership/encapsulation.
- **Mutable significant binaries:** делает прошлый recognized result необъяснимым.
- **Universal soft delete:** стирает context-specific lifecycle semantics.
- **Broad cascade deletion:** может уничтожить independent domain history.
- **Backup без restore testing:** не доказывает recoverability.
- **Rollback Shared production Placement ради одного Community:** откатывает unrelated tenants.
- **Blind last-write-wins:** silently теряет domain-significant changes.
- **Mandatory cross-RDBMS portability:** запрещает нужные PostgreSQL capabilities без product value.

## Совместимость с ADR-001–ADR-013

### ADR-001 и ADR-008

Voting, snapshot, result и decision identities/history не заменяются persistence tokens или Schema State. Relational constraints и recovery сохраняют, но не определяют Governance semantics.

### ADR-002

Persistence boundaries, databases, schemas, modules и projections не становятся bounded contexts. Semantic ownership остаётся у принятых contexts.

### ADR-003

Typed attributes являются context-owned extension pattern, а не universal Configuration/EAV. Applicability, meaning и history остаются у owning context.

### ADR-004

WAL/PITR point, DB write/storage timestamps, concurrency token и Schema Version не являются domain history/time. Recovery и promotion не silently rewrite facts.

### ADR-005

Schema Version, RLS и technical constraints не являются Rule Version или universal Rule.

### ADR-006

Payment, Allocation, Financial Obligation, Charge и Expense остаются distinct relational domain concepts; persistence не схлопывает их и защищает integrity/concurrency/history.

### ADR-007

Meter, Meter Installation, Accounting Point, received information, photograph, Reading и Consumption distinct. Persistence хранит evidence, но Resource Accounting владеет recognition.

### ADR-009

Document, Revision, Representation, File/blob и Storage Locator distinct. Significant representation immutable согласно owning-domain semantics.

### ADR-010

RLS/DB role не являются Subject, Power или domain admissibility. Platform Admin не имеет automatic unrestricted access.

### ADR-011

Stored external representation не становится received/recognized fact автоматически. Provenance, mapping, correction и duplicate semantics остаются contract/context-specific.

### ADR-012

Community identity не зависит от Placement. Platform Anchor остаётся minimal/optional, Community Subject data move with Placement, Shared/Dedicated are modes one model.

### ADR-013

Module ownership, public contracts, one resolved local transaction boundary, derived projections и Web/Worker execution boundaries сохраняются. Shared DB не становится internal API.
