# ADR-018 — Основной технологический стек и структура решения

**Статус:** Accepted / Принято
**Язык документа:** русский

---

## Контекст

ADR-001–ADR-017 определили предметную, модульную, persistence, security, reliable-runtime и production-operations архитектуру Community OS. До начала реализации необходимо выбрать основной application stack и composition решения так, чтобы эти границы не принимались неявно в первом коде.

Выбор должен поддерживать сложную историческую и временную семантику, строгую tenant isolation, independently runnable Web/API и Worker hosts, PostgreSQL/RLS, durable work, browser applications и будущий Self-Hosted deployment. При этом стартовая структура не должна имитировать microservices или вводить enterprise patterns без доказанной необходимости.

## Решение

### 1. Основной backend stack

Primary backend stack Community OS:

- C# и .NET;
- ASP.NET Core для Web/API Host и application hosting;
- PostgreSQL как принятая ADR-014 primary transactional DBMS;
- Npgsql как PostgreSQL data provider;
- EF Core как основной ORM/persistence mechanism.

Persistence mappings должны быть explicit и reviewable. Точечный PostgreSQL-specific SQL допустим, когда этого требуют RLS, locking, reporting, performance или корректная PostgreSQL semantics. EF Core не отменяет module ownership, transaction boundaries или право использовать PostgreSQL capabilities.

Решение не вводит автоматически Generic Repository, universal Unit of Work, MediatR/CQRS framework, AutoMapper либо иной шаблон/библиотеку без конкретной потребности. Application и Domain contracts не должны зависеть от EF entities или transport DTO.

Exact supported .NET major/LTS, SDK pin, package versions и upgrade policy фиксируются Implementation Baseline/bootstrap manifest после проверки актуальной поддержки и совместимости; они не являются новой архитектурной семантикой.

### 2. Repository и solution composition

Community OS развивается в monorepo как logical modular monolith.

- Functional Module boundaries выражаются явно и, где объективно возможно, проверяются автоматически.
- Bounded Context не тождествен runtime module, project, process или service.
- Web/API Host и Worker Host являются independently runnable compositions общей Domain/Application реализации.
- Отдельные hosts не означают microservices и не создают network boundary между модулями.
- Точное число `.csproj`, каталогов и granular project decomposition не фиксируется до bootstrap.

Структура должна избегать двух крайностей: десятков преждевременных проектов и одного giant project без проверяемых границ.

### 3. Frontend applications и web surfaces

Для authenticated application UI принимается TypeScript + React.

Логически различаются:

1. **Platform Public Site** — публичный сайт проекта/сервиса: описание продукта и возможностей, plans, portfolio/reviews, contacts, public content и entry points регистрации/login/создания Community.
2. **Platform Application** — platform-level Account experience, Customer/Billing Account, Subscription, Plan/Entitlement, список доступных Communities, создание Community, Provisioning, Onboarding и иные Control Plane use cases.
3. **Community Application** — работа внутри конкретной Community и Community-owned domain functionality.
4. **Community Public Presence** — optional public surface конкретной Community.

Platform Application и Community Application являются логически самостоятельными frontend applications. Допустимы shared frontend packages только для действительно общей technical capability: design-system/UI primitives, localization, API tooling и подобных concerns. Их application semantics не смешиваются.

Platform Public Site является SEO-friendly server/static-rendered capability, но конкретная технология не выбрана. React SPA для authenticated applications не делает public site обязательным SPA, Next.js application или server-side JavaScript runtime.

Переход от public/marketing surface к регистрации или созданию Community вызывает Control Plane Application use cases. Public frontend не владеет Account, Customer/Billing Account, Subscription, Community, Provisioning или Onboarding и не пишет их непосредственно в persistence.

### 4. Frontend/API boundary

Frontend работает через Web API/BFF contracts и не зависит непосредственно от Domain entities, EF mappings или DB schema.

BFF является логической boundary для frontend-oriented contracts. Первоначально она может предоставляться ASP.NET Core Web/API Host и не требует отдельного runtime service. Separate BFF service вводится только при доказанной operational/ownership необходимости.

Platform Application и Community Application являются SPA. Public rendering остаётся отдельной capability с отдельно выбираемой технологией.

### 5. Localization, responsive UI и accessibility

- Default UI locale первого внедрения — украинский.
- Русский доступен как переключаемая locale.
- Localization architecture допускает добавление других locales.
- UI localization не означает автоматический перевод Community-authored content.
- Основные пользовательские сценарии полноценно работают в responsive mobile Web.
- Сложные administrative workspaces могут дополнительно оптимизироваться для desktop.
- Accessibility является baseline quality requirement.

Exact build tool, state management, component library, design-system implementation, i18n library, OpenAPI generator и PWA/offline capability не выбираются этим ADR.

### 6. Frontend security и browser authentication

Frontend permission/capability/Entitlement state используется только для UX. Authoritative authentication, authorization, Entitlement gates и mandatory domain admissibility проверяются server-side. Сохраняется `Entitlement != Access Right != Power`.

Для собственных Web UI используется opaque server-side revocable session:

- session credential передаётся secure HttpOnly cookie;
- state-changing cookie-authenticated requests имеют explicit CSRF protection;
- session credential не хранится frontend JavaScript в `localStorage` или `sessionStorage`;
- одна Account/authentication model может обслуживать Platform Application и Community Application.

Это не предполагает одну общую cookie для platform domain, Community subdomains и custom domains. Exact session/cookie/custom-domain topology deferred до соответствующего bootstrap/security review.

### 7. Initial production packaging

Initial production artifact является immutable OCI-compatible container artifact. Initial supported SaaS production target — Linux x86-64. Это support target, а не фундаментальный запрет других platforms.

- Web/API Host и Worker Host independently runnable.
- Один image с разными modes или несколько images — deferred packaging choice.
- Environment-specific technical configuration и Secrets находятся вне artifact.
- Domain/Community configuration не подменяется environment configuration.
- Production не собирает application из Git source.
- Один и тот же принятый artifact продвигается Staging → Production без rebuild.

OCI compatibility не требует Docker Compose, Kubernetes, service mesh или конкретного cloud/provider/registry. Kubernetes и service mesh не входят в initial baseline.

Архитектура сохраняет возможность будущего Self-Hosted deployment. Exact Self-Hosted installer/topology и граница OSS/SaaS editions этим ADR не определяются.

## Архитектурные инварианты

1. Backend stack не меняет Domain/Application/module ownership ADR-001–ADR-017.
2. Bounded Context не становится автоматически project/service/runtime module.
3. Web/API и Worker являются отдельными compositions, но не microservices baseline.
4. EF model, DTO и Domain model не тождественны.
5. Frontend не является security boundary и не создаёт authority.
6. Platform Public Site не владеет Control Plane semantics.
7. Platform Application и Community Application различны, даже если используют shared technical packages.
8. Browser session revocable и не становится captured domain authority.
9. OCI artifact/environment configuration/domain configuration различны.
10. Stack и packaging не создают provider lock-in или обязательный orchestrator.

## Последствия

Положительно:

- implementation получает единый strongly typed backend ecosystem;
- Web/API и Worker используют общие Application/Domain contracts;
- PostgreSQL-specific correctness совместима с ORM-first productivity;
- frontend surfaces получают явные ownership и security boundaries;
- immutable container packaging согласуется с ADR-017 promotion model;
- modular monolith остаётся проверяемым без преждевременных services.

Цена и риски:

- team должен поддерживать компетенции .NET, PostgreSQL и TypeScript/React;
- EF Core требует контроля mapping/query leakage и PostgreSQL-specific tests;
- две authenticated frontend applications требуют disciplined shared-package boundary;
- public site technology и multi-domain cookie topology потребуют отдельного implementation решения;
- OCI build/release discipline требуется до production delivery.

## Отклонённые альтернативы

- framework/stack выбирается неявно первым code commit;
- mandatory microservices или service per Bounded Context;
- один giant backend project без enforced module boundaries;
- Generic Repository/universal UoW/CQRS tooling by default;
- direct serialization of Domain/EF entities as API;
- separate BFF runtime без необходимости;
- React SPA как обязательная реализация всех public surfaces;
- frontend permissions как authorization;
- self-contained browser JWT/localStorage как primary own-Web session;
- rebuild artifact для Production после Staging;
- mandatory Kubernetes/service mesh/cloud provider;
- полный Self-Hosted installer до первого implementation increment.

## Отложенные решения

- exact .NET/SDK/package versions и update cadence;
- exact solution/project/folder decomposition;
- exact React/public-site build frameworks и frontend libraries;
- exact session persistence schema, cookie/domain topology и CSRF mechanism;
- one-image/multi-image and frontend delivery packaging;
- CI/CD, registry, container runtime и production orchestrator;
- Self-Hosted installer/topology и OSS/SaaS edition boundary;
- concrete PostgreSQL schema, RLS SQL, migrations и application code.

## Согласованность

ADR продолжает ADR-013 logical modular monolith и hosts, ADR-014 PostgreSQL/RLS boundaries, ADR-015 authentication/security semantics, ADR-016 Worker/reliable-work contracts и ADR-017 immutable promotion/runtime packaging. Он не изменяет domain ownership ADR-001–ADR-012, не вводит новый universal entity и не начинает implementation.

Blocking conflicts with ADR-001–ADR-017: **0**.
