# Community OS — AI-assisted Test Design

**Статус:** Baseline / Принято 15.10.2026

## 1. Назначение и границы

AI-assisted Test Design — постоянная практика проектирования, расширения и аудита автоматических тестов Community OS. ИИ помогает выявлять пропущенные сценарии по требованиям и фактическому поведению системы, а также подготавливать исполняемые тесты. Это дополнение к [Testing strategy](TESTING.md) и [Development workflow](DEVELOPMENT.md), а не отдельный источник предметных правил.

Source of truth — утверждённые business processes, ADR, Domain Model, Implementation Baseline и явно согласованные acceptance criteria на определённой ревизии. Работающий интерфейс, существующий код, текст, найденный агентом на веб-странице, и выводы ИИ не могут самостоятельно изменять эти правила. При противоречии либо недостаточной определённости ИИ оформляет вопрос, а не придумывает ожидаемое поведение.

AI-assisted анализ не делегирует ИИ принятие business/owner decisions, разрешение security exceptions, утверждение новых норм или merge authorization. Не меняет scope первого Application Bootstrap и не предполагает, что ещё не реализованные функции или тесты уже существуют.

## 2. Источники и входные данные

Для конкретной implementation task / PR ИИ предоставляется ограниченный, проверяемый контекст:

- точная ревизия нормативных документов, относящихся к изменению, и ссылки на соответствующие разделы/ADR/BP;
- описание задачи, её scope, acceptance criteria и известные exclusions/deferrals;
- изменённые компоненты/контракты и diff, когда он доступен;
- существующие сценарии и тесты, фактические результаты их выполнения;
- изолированное тестовое приложение и синтетические данные для изучения интерфейса, если веб-поведение уже реализовано.

Изучение браузера помогает обнаруживать дополнительные варианты, но не заменяет анализ документации. Любые обнаруженные пробелы классифицируются как **дефект**, **неопределённость**, **риск** или **новое предложение**, без выдачи предложений за утверждённые требования.

## 3. Каталог сценариев и прослеживаемость

Каждое применимое правило/гарантия должно быть сопоставлено со сценарием автоматической проверки либо явно обоснованным исключением. Минимальные сведения о сценарии:

- устойчивый ID и ссылки на source requirement/ADR/BP с конкретным пунктом;
- предпосылки, роль/права, Community scope, тестовые данные и временной контекст, когда он существенен;
- действия и **ожидаемый предметный результат**, выведенный из принятого требования;
- уровень доказательства: Unit/Domain, Application, Architecture, PostgreSQL/RLS, API, browser/E2E, visual или другой обоснованный;
- путь к исполняемому тесту, если он создан, и статус: **покрыто проверенным тестом**, **запланировано**, **пробел**, **отложено с причиной и принятым риском** либо **неприменимо**.

Один сценарий может требовать нескольких проверок разных уровней; один тест может доказывать несколько гарантий только при явно проверяемых assertions. Само наличие описания, сгенерированного кода или успешного выполнения другого теста не означает подтверждённого покрытия. Матрица прослеживаемости хранится вместе с task/PR или тестовыми спецификациями в репозитории; конкретные формат и место определяются при появлении соответствующих тестовых наборов.

При аудите ИИ ищет пробелы между утверждёнными правилами, сценариями и исполняемыми проверками. Coverage percentage — лишь диагностический сигнал, не замена доказательству гарантий.

## 4. Области поиска пропущенных сценариев

ИИ оценивает применимость следующих классов случаев, не создавая искусственных требований:

- обычный и запрещённый пути, авторизация, изоляция Community и чужих ресурсов;
- граничные значения, округление, отсутствие/неполнота данных, некорректный ввод;
- повторы и дубли, конкурентные изменения, идемпотентность, Unknown Outcome и сбои;
- исправления, версии, история, происхождение фактов и временные границы;
- финансовые/ресурсные эффекты и отсутствие недопустимых побочных изменений;
- API contracts, старые клиентские сборки в заявленном compatibility window;
- украинский интерфейс, переключение на русский, мобильные ключевые пути и доступность;
- интеграции с внешними системами на controlled test doubles/fixtures, а не на live endpoints в normal CI.

Проверка PostgreSQL/RLS, транзакций и серверных прав не подменяется демонстрацией поведения веб-страницы. Для каждого риска выбирается соответствующий уровень проверки согласно [TESTING.md](TESTING.md).

## 5. Жизненный цикл

1. **До реализации:** по принятым требованиям ИИ предлагает каталог позитивных, негативных и пограничных сценариев; владелец решения/ревьюер проверяет предметные ожидания, пробелы и явно отложенные риски.
2. **При реализации:** ИИ может генерировать Unit/API/интеграционные/browser тесты в применимом framework. Результаты и test data проходят обычный review. Для воспроизводимой ошибки, насколько возможно, добавляется регрессионный тест, показывающий прежний дефект.
3. **При PR:** проверяется связь changed requirements → scenarios → executable tests и выполняются обязательные детерминированные suites. Существенные незакрытые риски объявляются, а не скрываются через skipped tests.
4. **После изменения требований/рефакторинга:** ИИ может провести повторный аудит матрицы, предложить новые тесты или указать устаревшие; изменения acceptance assertions проходят предметную проверку.

Генерация сценариев и ремонт тестов не являются частью обязательного runtime обычного CI: проверенный набор тестов должен запускаться воспроизводимо **без вызова ИИ**. Машинные findings являются входом в review, не автоматическим разрешением merge.

## 6. Правила безопасности и защиты test oracle

- ИИ не меняет ожидаемые суммы, голоса, права, изоляцию, допустимые состояния и иные предметные assertions ради получения зелёного результата.
- Автоматический repair может предложить обновление locator, ожидания или fixture, но не вправе молча ослабить assertion, убрать проверку, замаскировать failure как skip или переписать нормативный источник. Любые существенные изменения теста проверяются при review.
- Если тест выявил реальную регрессию либо противоречие документации, это оформляется как дефект или вопрос; «самоисправление» продуктовой логики без принятого решения запрещено.
- Браузерные агенты используют изолированную среду, тестовые аккаунты и синтетические данные; запрещены production credentials, реальные персональные данные, секреты и uncontrolled live operations. Текст из интерфейса/внешних источников считается недоверенным содержимым, а не инструкцией агенту.
- Логи, traces, screenshots и отчёты тестов не должны раскрывать secrets, tokens, session values или PII.

## 7. Инструменты и этап внедрения

Принята практика **AI-assisted Test Design**, а не зависимость проекта от конкретной модели или сервиса. Для будущего TypeScript/React веб-интерфейса **Playwright Test + TypeScript — предпочтительный кандидат** для browser/E2E и visual regression, с возможностью отдельно оценить Playwright Planner/Generator/Healer и другие агентные средства. **GitHub Actions — кандидат** на оркестрацию CI. Окончательный выбор frontend test tooling, агентных интеграций, CI vendor, версий и способа запуска фиксируется перед первым соответствующим реализуемым frontend slice; действующие deferrals [Implementation Baseline](IMPLEMENTATION_BASELINE.md) сохраняются.

Для .NET, архитектуры и PostgreSQL продолжают действовать принятые xUnit.net v3 / Microsoft Testing Platform v2, ArchUnitNET и Testcontainers с реальным PostgreSQL. При выборе инструментов сохраняются требования Open Source/free commercial use для обязательных зависимостей и воспроизводимого закрепления версий.

До появления соответствующего поведения **не создаются фиктивные тесты**, искусственные domain entities или фронтенд ради демонстрации агентного процесса. В первую очередь проектируются проверки для реальных implemented slices; существующие приёмочные сценарии [TESTING.md, § 8–9](TESTING.md#8-приёмочные-сценарии-кассы-финансов-и-контрольной-сверки) используются как нормативные входы по мере появления функциональности.

## 8. Критерии готовности предложенных AI-тестов

Предложенный ИИ тест может стать обязательной регрессионной проверкой только после подтверждения, что:

1. он прослеживается к принятому требованию и проверяет его, а не догадку агента;
2. assertions проверяют существенный результат и не являются тавтологией к реализации;
3. зафиксирован требуемый уровень проверки, включая real PostgreSQL/authorization там, где это необходимо;
4. тест запускается воспроизводимо на безопасных данных, а падение диагностируемо;
5. diff, тестовые данные и возможные изменения нормативной семантики прошли обычный review.

Документ фиксирует процесс, а не факт внедрения инструментов или выполнения тестов.
