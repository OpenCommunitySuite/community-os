# I‑3. Регулярный расчётный период

Статус — проект для согласования первого сценария. Основания — [ADR‑005](../architecture/adr/ADR-005.md), [ADR‑006](../architecture/adr/ADR-006.md#15-тарифы-и-правила-начисления), [ADR‑007](../architecture/adr/ADR-007.md) и [финансово-ресурсный план](PILOT_FINANCE_FIRST_ROADMAP.md).

## Первый сценарий

Бухгалтер выбирает сообщество и расчётный период. Система подготавливает расчёт по индивидуальной точке электроэнергии и лицевому счёту, проверяет применимость внутреннего тарифа и показывает проект суммы с основаниями. Регулярный членский взнос рассчитывается отдельной строкой по своему правилу. Основание взноса, период, сумма и получатель определяются отдельно от ресурсного потребления. Первый сквозной сценарий проверяется на синтетических данных. Вода подключается после подтверждения её правила начисления.

1. Определить границы периода потребления, дату расчёта и срок оплаты как отдельные даты. Определить применимое правило связи точки с лицевым счётом и плательщиком. При неоднозначном основании показать причину и исключить счёт из готовых к проведению.
2. Получить признанные показания и воспроизводимый расчёт потребления. Сохранить ссылки на использованные показания, установку и коэффициент. Для двух регистров сохранить объём каждого регистра. При отсутствии границы периода или данных через замену показать неполноту. Потребление без достаточных данных не считать нулевым.
3. Выбрать применимую версию внутренних тарифных условий. Сохранить её идентификатор, основание, даты применимости, денежную единицу и использованные ставки. При конфликте версий либо отсутствии применимой версии не формировать сумму для соответствующей строки. Тариф поставщика учитывается только при наличии явно утверждённого основания для его использования.
4. Показать бухгалтеру по каждому счёту исходные объёмы, ставки, промежуточные суммы, округление, итог и причины исключения строк. Предпросмотр не создаёт начислений и обязательств.
5. При проведении подтвердить действующее полномочие и актуальность проекта. Для пилотного сценария зафиксировать начисление и связанное обязательство по каждой принятой строке, когда обязательство возникает по применимому основанию. Сохранить использованные данные, версию правила, автора и время проведения. Повтор команды для уже проведённого расчёта возвращает прежний результат. Изменение исходных данных после проведения обрабатывается как отдельное действие по [BP‑FIN‑005](../business-processes/BP-FIN-005-ACCRUAL-CHANGE.md).

## Решения для пилота

| Вопрос | Что потребуется для первого проведения |
| --- | --- |
| Период и срок оплаты | Начало и конец периода, порядок определения срока оплаты, обработка неполного периода |
| Потребление для начисления | Правило выбора граничных показаний, допустимость расчётного замещения и порядок учёта смены прибора |
| Электроэнергия | Внутренние ставки с датой начала и основанием, применимость для одно- и двухрегистрового учёта. Для двух регистров также порядок применения дневной и ночной зон |
| Смена тарифа в периоде | Порядок применения версий при смене ставки между граничными измерениями, включая ситуацию без показания на дату смены |
| Техническая вода | Основание начисления по индивидуальному объёму и порядок учёта общего расхода, если эти начисления применяются |
| Регулярный взнос | Ставка, периодичность, единица начисления и круг плательщиков |
| Коэффициенты и компенсации | Подтверждение области действия измерительных коэффициентов. Если используется компенсационная составляющая, требуется отдельное правило и основание |
| Денежное округление | Точность и этап округления, включая порядок суммирования строк |
| Проведение и исправление | Кто рассчитывает и кто проводит период, допустимо ли провести только готовые строки, какое основание и полномочие нужны для перерасчёта |

## Синтетическая приёмка

### Ревью доступа и проведения

Предпросмотр и история требуют отдельного права чтения расчётов. Проведение дополнительно требует основания в назначении оператора. Platform проверяет активное сообщество, связь оператора, сессию и право под блокировкой существующих строк и фиксирует допуск с границами периода и отпечатком проекта. Допуск сохраняется до начала записи Community. Отзыв закрывает выдачу новых допусков, включая запросы повтора. Уже выданный допуск может завершиться после отзыва. Сам допуск не создаёт обязательство.

В Community расчёт и запись выполняются в сериализуемой транзакции. Перед записью сервер заново получает показания, тариф и привязку счёта и сравнивает отпечаток проекта. Уникальность периода в сообществе защищает от конкурирующих подтверждений. Начисления, обязательства и снимок проекта записываются одной транзакцией. Повтор с тем же отпечатком возвращает сохранённый результат после проверки права, даже если входы уже изменились. Попытка с другим отпечатком для проведённого периода отклоняется. Запись без токена CSRF отклоняет существующий фильтр.

Для тестовой приёмки проводится целый период, только если готовы все строки выбранных счетов. Взнос хранится отдельной строкой с явной версией условий. Текущая связь счёта и плательщика применяется в синтетическом сценарии при однозначном владельце. Историческое правило определения плательщика пилота подлежит отдельному согласованию.

Первый фрагмент реализации проверяет чистый расчёт для одной установки с точными показаниями на обеих границах. Тариф должен покрывать весь полуоткрытый период. Частичное покрытие требует отдельного правила и блокирует расчёт. Для синтетического примера итог округляется один раз до копеек, половина копейки округляется вверх. Расчёт возвращает версию тарифа, исходные значения и идентификаторы показаний по каждому регистру. Это соглашение тестового предпросмотра.

Использовать вымышленные ставки, введённые явно для тестовой версии. Например, для однотарифной установки взять граничные значения 100 и 103 кВт·ч при коэффициенте 1 и ставку 4,00 грн/кВт·ч, действующую весь тестовый период. Ожидаемое ресурсное начисление составляет 12,00 грн. Для отдельно заданного взноса 25,00 грн бухгалтер видит две строки с разными основаниями. Для проверки коэффициента воспроизвести расчёт по уже проверенному синтетическому объёму 120 кВт·ч и проверить, что повторного умножения нет.

В отдельном наборе показать дневной и ночной объёмы, точку без конечного показания, конфликт применимости тарифа и смену тарифа без достаточных граничных измерений. Проверить отказ без полномочия, изоляцию сообществ, два конкурентных проведения одного проекта и повтор после получения результата. После изменения ставки или появления запоздалого показания убедиться, что проведённое начисление и его исходные данные воспроизводятся. Для изменившегося расчёта показать основание отдельного действия, сохранив прежнюю запись.
