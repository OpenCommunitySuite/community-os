# I‑3. Регулярный расчётный период

Для расчёта, проведения и открытия сохранённого периода доступны [контекстная справка и руководство бухгалтера](I5_FINANCE_HELP.md). Материалы поясняют границы периода, готовность строк, последствия подтверждения и переход к текущей сверке.

Статус — проект для согласования первого сценария. Основания — [ADR‑005](../architecture/adr/ADR-005.md), [ADR‑006](../architecture/adr/ADR-006.md#15-тарифы-и-правила-начисления), [ADR‑007](../architecture/adr/ADR-007.md) и [финансово-ресурсный план](PILOT_FINANCE_FIRST_ROADMAP.md).

## Первый сценарий

Бухгалтер выбирает сообщество и расчётный период. Система подготавливает расчёт по индивидуальной точке электроэнергии и лицевому счёту, проверяет применимость внутреннего тарифа и показывает проект суммы с основаниями. Регулярный членский взнос рассчитывается отдельной строкой по своему правилу. Основание взноса, период, сумма и получатель определяются отдельно от ресурсного потребления. Первый сквозной сценарий проверяется на синтетических данных. Вода подключается после подтверждения её правила начисления.

1. Определить границы периода потребления, дату расчёта и срок оплаты как отдельные даты. Определить применимое правило связи точки с лицевым счётом и плательщиком. При неоднозначном основании показать причину и исключить счёт из готовых к проведению.
2. Получить признанные показания и воспроизводимый расчёт потребления. Сохранить ссылки на использованные показания, установку и коэффициент. Для двух регистров сохранить объём каждого регистра. При отсутствии границы периода или данных через замену показать неполноту. Потребление без достаточных данных не считать нулевым.
3. Выбрать применимую версию внутренних тарифных условий. Сохранить её идентификатор, основание, даты применимости, денежную единицу и использованные ставки. При конфликте версий либо отсутствии применимой версии не формировать сумму для соответствующей строки. Тариф поставщика учитывается только при наличии явно утверждённого основания для его использования.
4. Показать бухгалтеру по каждому счёту исходные объёмы, ставки, промежуточные суммы, округление, итог и причины исключения строк. Предпросмотр не создаёт начислений и обязательств.
5. При проведении подтвердить действующее полномочие и актуальность проекта. Для пилотного сценария зафиксировать начисление и связанное обязательство по каждой принятой строке, когда обязательство возникает по применимому основанию. Сохранить использованные данные, версию правила, автора и время проведения. Повтор команды для уже проведённого расчёта возвращает прежний результат. Изменение исходных данных после проведения обрабатывается как отдельное действие по [BP‑FIN‑005](../business-processes/BP-FIN-005-ACCRUAL-CHANGE.md).

## Решения для пилота

| Вопрос | Что потребуется для первого проведения |
| --- | --- |
| Период и срок оплаты | Начало и конец периода, порядок определения срока оплаты, обработка неполного периода |
| Потребление для начисления | Правило выбора граничных показаний, допустимость расчётного замещения и порядок учёта смены прибора |
| Электроэнергия | Внутренние ставки с датой начала и основанием, применимость для одно- и двухрегистрового учёта. Для двух регистров также порядок применения дневной и ночной зон |
| Смена тарифа в периоде | Порядок применения версий при смене ставки между граничными измерениями, включая ситуацию без показания на дату смены |
| Техническая вода | Основание начисления по индивидуальному объёму и порядок учёта общего расхода, если эти начисления применяются |
| Регулярный взнос | Ставка, периодичность, единица начисления и круг плательщиков |
| Коэффициенты и компенсации | Подтверждение области действия измерительных коэффициентов. Если используется компенсационная составляющая, требуется отдельное правило и основание |
| Денежное округление | Точность и этап округления, включая порядок суммирования строк |
| Проведение и исправление | Кто рассчитывает и кто проводит период, допустимо ли провести только готовые строки, какое основание и полномочие нужны для перерасчёта |

## Сценарий приёмки начисления за воду

Первый этап реализации — предпросмотр по одному лицевому счёту с индивидуальной точкой воды. Список счетов и расчёт доступны по существующему полномочию чтения расчётов. Тестовые версии тарифа подготавливаются на синтетическом стенде. Предпросмотр использует дату начала и конца периода и возвращает основания расчёта без проведения.

В рабочей области предварительного расчёта за воду доступна [контекстная справка и руководство](I5_FINANCE_HELP.md). Они объясняют границы периода, проверку исходных данных и тарифа, отсутствие записи начисления при просмотре и отдельное проведение в общем периоде.

Для синтетической проверки задать отдельную версию тарифа в грн/м³, действующую весь период, и однозначную связь индивидуальной точки с лицевым счётом. При показаниях одного водомера 10,000 и 12,500 м³ и тестовой ставке 20,00 грн/м³ ожидаются объём 2,500 м³ и начисление 50,00 грн. Общий и уличный водомеры используются в контрольной сверке. В примере начисление формируется только по индивидуальному объёму.

В предпросмотре показать использованные показания, установку, границы периода, версию тарифа и сумму. Проверить, что одинаковые показания дают измеренный нулевой объём, а пропущенная граница или замена прибора без достаточных данных делают строку неготовой. При ошибке применимости тарифа показать причину. После проведения повтор запроса возвращает прежний результат. Частичная оплата 30,00 грн, распределённая на это обязательство, оставляет долг 20,00 грн. Суммы сверяются по лицевому счёту.

Стендовый режим `water-charge-preview` сверяет в браузере сумму 50 грн за 2,5 м³, измеренный ноль и идентификаторы установки, двух показаний и версии тарифа. При пропущенной границе, замене водомера, отсутствии тарифа, неполном покрытии периода или нескольких версиях сумма отсутствует. После отзыва чтения расчётов открытая форма получает HTTP 403, а показания воды остаются доступны. В Community сверяются неизменность исходных фактов и отсутствие проведённого периода, начисления и обязательства. В Platform сверяется отсутствие допусков записи. Команда запуска приведена в [инструкции стенда](../../ops/test-stand/README.md).

Тестовые условия используются только на синтетическом стенде. Для эксплуатации требуется подтверждённое правило начисления за воду, включая применимость тарифа, обработку общего расхода и порядок учёта замены водомера.

### Проведение начисления за воду

Вода включается в общий проект расчётного периода явным выбором бухгалтера. Начисления за электроэнергию, воду и членский взнос сохраняются отдельными строками. При включении воды наличие индивидуальной точки определяет применимость водной строки к счёту. Если точка есть, отсутствие готового расчёта за воду блокирует проведение проекта. Просмотр платы за воду по отдельному счёту остаётся предварительной проверкой.

Для проведения используется существующее полномочие и допуск Platform. Отпечаток общего проекта включает выбор воды, лицевой счёт, плательщика, обе границы, установку, использованные показания и версию тарифа со ставкой. Community повторяет расчёт в сериализуемой транзакции и сохраняет начисление, обязательство и снимок вместе с остальными строками периода. Повтор того же проекта возвращает ранее проведённый период. Попытка добавить воду к уже проведённому периоду через повторное проведение отклоняется. Ранее сохранённые периоды читаются по прежним снимкам.

Стендовый режим `water-period-posting` проводит через форму два неперекрывающихся периода. С включённой водой сохраняются три отдельных начисления и обязательства на 480, 25 и 50 грн. Во втором периоде сохраняются электроэнергия и взнос на 160 и 25 грн. Повтор с тем же отпечатком возвращает исходный период и снимок. Смена выбора воды для уже проведённых дат даёт HTTP 409. Сверка баз подтверждает пять обязательств и четыре допуска Platform, включая повтор и конфликт. После отзыва проведения открытое подтверждение получает HTTP 403, история и строка воды в сверке периода остаются доступны. Порядок запуска приведён в [инструкции стенда](../../ops/test-stand/README.md).

В синтетической приёмке проверить проведение с водой и без неё, повтор и конкурентные подтверждения, изменение входных данных после предпросмотра, отказ без права или CSRF и изоляцию сообществ. После проведения проверить отображение воды отдельной строкой в лицевом счёте и сверке периода, частичную оплату и остаток. Исправление проведённого начисления за воду требует отдельного сценария.

Стендовый режим `water-partial-payment` проверяет [договорённости I‑4](I4_MANUAL_PAYMENT.md) на проведённом периоде с водой. После регистрации 30 грн долг за воду остаётся 50 грн до подтверждения распределения. Предпросмотр показывает остаток 20 грн, после подтверждения эту же сумму показывают сверка периода и выписка. Электроэнергия и взнос сохраняют остатки 480 и 25 грн. Точный повтор возвращает прежнее распределение, а после отзыва права тот же запрос получает HTTP 403. Сверка баз подтверждает один платёж, одно распределение на воду и три допуска Platform для платежа, распределения и повтора. Снимок проведённого периода сохраняется.

## Синтетическая приёмка

### Ревью доступа и проведения

Предпросмотр и история требуют отдельного права чтения расчётов. Проведение дополнительно требует основания в назначении оператора. Platform проверяет активное сообщество, связь оператора, сессию и право под блокировкой существующих строк и фиксирует допуск с границами периода и отпечатком проекта. Допуск сохраняется до начала записи Community. Отзыв закрывает выдачу новых допусков, включая запросы повтора. Уже выданный допуск может завершиться после отзыва. Сам допуск не создаёт обязательство.

В Community расчёт и запись выполняются в сериализуемой транзакции. Перед записью сервер заново получает показания, тариф и привязку счёта и сравнивает отпечаток проекта. Уникальность периода в сообществе защищает от конкурирующих подтверждений. Начисления, обязательства и снимок проекта записываются одной транзакцией. Повтор с тем же отпечатком возвращает сохранённый результат после проверки права, даже если входы уже изменились. Попытка с другим отпечатком для проведённого периода отклоняется. Запись без токена CSRF отклоняет существующий фильтр.

Режим `water-posting-race` подтверждает один предпросмотр с водой из двух вкладок. Временная незакоммиченная строка с тем же ключом удерживает оба запроса на вставке. Стенд сверяет две ожидающие транзакции Community и два допуска Platform с одинаковым отпечатком, затем откатывает временную строку. Оба запроса получают HTTP 200. Один проводит период, второй возвращает его же снимок. Сохраняются один период, три начисления и три связанных обязательства.

Режим `water-stale-posting` меняет ставку применимого синтетического тарифа с 20 до 24 грн/м³ между предпросмотром и подтверждением. Первый допуск Platform фиксирует запрос со старым отпечатком. Community возвращает `StalePreview` с HTTP 409, период, начисления и обязательства отсутствуют. Новый предпросмотр использует те же показания и версию тарифа, пересчитывает воду с 50 до 60 грн и получает новый отпечаток. Проведённый снимок содержит новую ставку, а сохранённый период ссылается на второй допуск Platform.

Режим `water-billing-isolation` использует два синтетических сообщества и одну сессию оператора. После отзыва проведения во втором сообществе предпросмотр и история доступны, подтверждение получает HTTP 403. После отзыва чтения предпросмотр, список периодов, история и сверка получают HTTP 403. Учёт технической воды остаётся доступным. В первом сообществе проект проводится, а запрос сверки с действительным идентификатором периода второго сообщества получает HTTP 404. В каждом сообществе сохраняются свой период, три обязательства и один допуск Platform.

Для тестовой приёмки проводится целый период, только если готовы все строки выбранных счетов. Взнос хранится отдельной строкой с явной версией условий. Текущая связь счёта и плательщика применяется в синтетическом сценарии при однозначном владельце. Историческое правило определения плательщика пилота подлежит отдельному согласованию.

Первый фрагмент реализации проверяет чистый расчёт для одной установки с точными показаниями на обеих границах. Тариф должен покрывать весь полуоткрытый период. Частичное покрытие требует отдельного правила и блокирует расчёт. Для синтетического примера итог округляется один раз до копеек, половина копейки округляется вверх. Расчёт возвращает версию тарифа, исходные значения и идентификаторы показаний по каждому регистру. Это соглашение тестового предпросмотра.

Использовать вымышленные ставки, введённые явно для тестовой версии. Например, для однотарифной установки взять граничные значения 100 и 103 кВт·ч при коэффициенте 1 и ставку 4,00 грн/кВт·ч, действующую весь тестовый период. Ожидаемое ресурсное начисление составляет 12,00 грн. Для отдельно заданного взноса 25,00 грн бухгалтер видит две строки с разными основаниями. Для проверки коэффициента воспроизвести расчёт по уже проверенному синтетическому объёму 120 кВт·ч и проверить, что повторного умножения нет.

В отдельном наборе показать дневной и ночной объёмы, точку без конечного показания, конфликт применимости тарифа и смену тарифа без достаточных граничных измерений. Проверить отказ без полномочия, изоляцию сообществ, два конкурентных проведения одного проекта и повтор после получения результата. После изменения ставки или появления запоздалого показания убедиться, что проведённое начисление и его исходные данные воспроизводятся. Для изменившегося расчёта показать основание отдельного действия, сохранив прежнюю запись.
