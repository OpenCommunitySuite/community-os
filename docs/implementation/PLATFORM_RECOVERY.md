# Восстановление платформенного доступа

**Статус:** проект для независимого ревью. База `faeb3e38ec920e5d00697cf3c830add1ca7eb7ea`.

Источники — ADR-012, ADR-015 §§4, 15–16, ADR-018 и Implementation Baseline §6.

- Доверенный оператор после внешней проверки личности выпускает код локальной командой через отдельную роль PostgreSQL. Событие фиксирует целевой Account и аутентифицированный технический идентификатор PostgreSQL оператора. Личность пользователя и канал передачи в эксплуатации должны быть согласованы отдельно. Для репетиции используется контролируемая передача между синтетическими участниками.
- Код состоит из 32 криптографически случайных байтов. В базе хранится только SHA-256. Код связан с конкретной активной учётной записью, действует 15 минут, выдаётся только для восстановления пароля. Новый код заменяет ранее выданный. Коды не передаются в URL, логи или историю.
- Пользователь передаёт логин, код и новый пароль через HTTPS POST с CSRF. Действуют те же ограничения размера и вычислений, что при входе. Некорректный, просроченный, использованный код и неизвестный логин дают одинаковый отказ. До дорогого хеширования возможна предварительная проверка, но решение о применении принимается повторно под блокировкой.
- Под блокировкой Account атомарно проверяются срок и привязка кода, записывается новый хеш Argon2id, погашается код, отзываются все прежние сессии и добавляются события аудита. Права и статус Account не меняются. Новый вход выполняется обычным способом.
- Выдача, восстановление и защищённые операции согласуют порядок блокировок Account → сессия. Вход проверяет, что хеш пароля не изменился после Argon2id. Аудит содержит только идентификаторы, тип события и время. Отдельная роль оператора может выполнить только функцию выдачи, Web — только функцию применения. Публичный доступ к функциям PostgreSQL закрыт.

Проверить на ревью порядок конкурирующих операций, повтор, отказ на границе срока, атомарность аудита, минимальные права SQL-ролей и невозможность раскрытия кода. Вне объёма — выдача предметных полномочий, восстановление через внешних провайдеров, реальные данные и эксплуатационный канал доставки.

## Результат независимого ревью

Два рецензента проверили проект на базе `faeb3e3`. По их замечаниям порядок блокировок разделён явно. Срок проверяется после ожидания, прежний пароль отклоняется, а применение сверяет хеш, относительно которого проверялся новый пароль. Выдача второго кода заменяет первый. Сбой записи аудита откатывает погашение, смену пароля и отзыв сессий.

## Настройка ролей

Примените миграцию Platform `006_password_recovery.sql`. Функции имеют фиксированный `search_path`, а `PUBLIC` лишён права их вызова. Используйте закрытую роль-владельца миграции без входа, с правами на соответствующие таблицы. Дайте индивидуальной роли оператора `USAGE` на схему и `EXECUTE` на `issue_password_recovery(uuid, bytea)`. Веб-роли выдайте `EXECUTE` только на `consume_password_recovery(text, bytea, text, text)`. Прямой доступ к таблице кодов этим ролям не нужен. Веб-роли также не нужно право напрямую изменять хеш пароля.

После внешней проверки личности запустите `platform-recovery issue <account-id>` с отдельным подключением `Platform__RecoveryOperatorDatabase`. Код выводится только на защищённом терминале оператора. Не перенаправляйте его в журналы, CI или историю. Пользователь вводит логин, код и новый пароль на странице `/platform/`. После смены пароля он входит заново. Эксплуатационный канал передачи, проверка личности и политика хранения аудита остаются отдельными решениями.
