# Доставка кодов восстановления через email и Telegram

**Статус:** проект для независимого ревью. База `09becc48a1a6139bc5f6df63e1665d0b7c296910`.

- Email использует существующий SMTP с обязательным STARTTLS и отдельными учётными данными. Например, личный Gmail указывает лимит порядка 500 писем в день, а пароль приложения зависит от двухэтапной проверки и политики аккаунта. Это кандидат для пилота без подписки, не SLA. [Gmail](https://support.google.com/mail/answer/22839), [пароли приложений](https://support.google.com/accounts/answer/185833).
- Telegram использует Bot API `sendMessage` в личный чат после взаимодействия с ботом. Платная рассылка выключена. Ориентиры — до одного сообщения в секунду в чат и около 30 сообщений в секунду суммарно. [Bots FAQ](https://core.telegram.org/bots/faq#how-can-i-message-all-of-my-bot-39s-subscribers-at-once), [Bot API](https://core.telegram.org/bots/api#sendmessage).

## Привязка

Только отдельная роль PostgreSQL доверенного оператора может подтвердить, заменить или отозвать канал. До подтверждения оператор проверяет личность по внешней процедуре и контроль именно этого адреса или личного чата с ботом. Для Telegram проверяется тип `private` и идентификатор из сообщения боту, а не имя пользователя. Код проверки канала и подтверждение личности не равны коду восстановления. Для репетиции проверка проводится с синтетическими получателями. Эксплуатационный регламент проверки личности и подтверждения канала остаётся отдельным решением. Операция записывает инициатора из `session_user`; Web не может менять привязку. Замена или отзыв инвалидируют текущий код. На первом этапе у аккаунта один активный канал.

## Доставка

HTTPS POST с CSRF принимает только логин, возвращает одинаковый 202 без сведений об аккаунте. Ограничения — общий лимит запросов и один действующий код на аккаунт. При наличии активной привязки PostgreSQL одной транзакцией сохраняет дайджест кода и задачу доставки. Повтор при действующем коде не выдаёт новый. Код детерминированно выводится из UUID задачи с выделенным HMAC-ключом, общим для Web и Worker; в PostgreSQL остаётся дайджест и ссылка на привязку. Ключ поставляется как отдельный секрет, не хранится в задаче. Ротация требует завершить или инвалидировать прежние задачи.

Worker арендует задачу, проверяет срок, актуальность привязки и дайджеста, повторяет временные сбои с тем же кодом и ограниченным числом попыток. Поставщик может принять сообщение и потерять ответ, поэтому повтор сообщения допустим, но второй код не выдаётся. Отзыв сразу инвалидирует код, даже если внешний вызов уже начался. Журнал содержит только Account, тип канала и результат. Тело ответа провайдера, адрес, чат, код и секреты в журнал не попадают.

Проверить на ревью разграничение ролей, перечисление аккаунтов, атомарность, гонки отзыва и отправки, повторную доставку, ротацию ключа и условия живого запуска. Проверки обоих адаптеров выполняются на управляемых имитаторах.

## Итог ревью и настройка

Два независимых рецензента проверили проект на базе `09becc4`. По их замечаниям добавлены ревизия привязки, отдельный лимит повторного запроса по журналу выдач, сверка дайджеста при каждой попытке и проверка аренды при записи результата. Telegram 429 учитывает `retry_after` в пределах срока действия. Отдельный Worker отправляет максимум одну задачу за цикл с паузой две секунды. Запись `sent` означает, что SMTP или Bot API принял сообщение. Если ответ потерян, при повторе получатель может получить то же сообщение с тем же кодом. Эксплуатационный регламент подтверждения канала и очистка завершённых задач и аудита остаются открытыми.

Примените Platform migration `007_recovery_delivery.sql`. Дайте каждой роли `USAGE` на схему и только нужный `EXECUTE` для этого блока:

| Роль | Функция |
| --- | --- |
| Web | `request_recovery_delivery(text, uuid, bytea)` |
| Оператор подтверждения канала | `set_recovery_channel(uuid, text, text)` |
| Worker | `claim_recovery_delivery()` и `finish_recovery_delivery(uuid, integer, text, integer)` |

Владелец функций — закрытая роль миграций. Ролям выше не требуется прямой доступ к таблицам канала и задач. Существующие права для применения кода и ручной выдачи по миграции 006 остаются отдельными.

Подтверждение выполняется командой `platform-recovery-channel confirm <account-id> <email|telegram>` с проверенным адресом или ID чата на stdin. Отзыв — `platform-recovery-channel revoke <account-id>`. Обе команды получают отдельное подключение через `RecoveryDelivery__ChannelOperatorDatabase`. Подтверждение одного канала заменяет прежний и инвалидирует текущий код. Не запускайте процедуру с реальными получателями до согласования регламента проверки.

Web и Worker получают одинаковый выделенный 32-байтный ключ в hex через `RecoveryDelivery__Key`. Worker получает отдельную строку подключения через `RecoveryDelivery__WorkerDatabase`. Для SMTP задаются `RecoveryDelivery__Smtp__Host`, `Port` (по умолчанию 587), `Sender`, `Username` и `Password` в той же секции. Для Telegram задаётся `RecoveryDelivery__Telegram__Token`. Не включайте HTTP-трассировку пути Bot API, поскольку путь содержит токен. Ключ и учётные данные предоставляются из конфигурации секретов среды. Перед сменой ключа завершите или инвалидируйте старые задачи и коды.

## Шестизначные коды

Миграция 008 сохраняет ранее выданные и ручные коды прежнего формата. Новые задачи email и Telegram используют шесть равновероятных цифр и отдельный HMAC-проверочный результат, привязанный к UUID выдачи. Worker проверяет результат и повторно выводит тот же код из ключа и UUID. PostgreSQL связывает выдачу с конкретным аккаунтом.

На аккаунт допускается пять неверных проверок за скользящие 15 минут. Срок кода также 15 минут, поэтому на конкретную выдачу приходится не более пяти неверных попыток. Новый код, перезапуск, успешное восстановление и смена канала не обнуляют окно. Ручной длинный код сохраняет собственный путь проверки. PostgreSQL сериализует подсчёт и погашение блокировкой строки аккаунта.

Веб-роли дополнительно нужны EXECUTE на request_short_recovery(text, uuid, bytea), short_recovery_issuance(text) и consume_short_recovery(text, uuid, bytea, text, text). Остальные права остаются прежними. Порядок обновления после миграции — сначала Worker с поддержкой обоих форматов, затем Web. При откате Web на старую версию действующие шестизначные коды можно применить только после возврата совместимой версии или заменить ручным кодом.

Независимое ревью на базе 73207ae проверило изоляцию старого SQL-пути, конкуренцию, переносимость лимита и порядок обновления. По замечаниям старый путь ограничен длинным форматом, а фиксированное окно заменено скользящим.
