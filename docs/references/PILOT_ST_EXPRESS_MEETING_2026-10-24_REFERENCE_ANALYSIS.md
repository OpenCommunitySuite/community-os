# Пилотное СТ «ЕКСПРЕС» — анализ реальной процедуры общего собрания и письменного голосования 24.10.2026

**Статус:** Reference analysis / empirical pilot evidence / не нормативный источник требований  
**Источник:** предоставленные пользователем фотокопии документов Садівничого товариства «ЕКСПРЕС» (код ЄДРПОУ 24422823) + последующее фактическое уточнение пользователя о порядке проведения голосования и формировании тарифа электроэнергии  
**Дата процедуры:** 24 октября 2026 года  
**Связанные области Community OS:** Governance, Membership, Documents, Finance, Resources, Community Operations  
**Связанный этап:** Stage 11B — mixed open/anonymous voting

> Этот документ фиксирует наблюдаемые факты из предоставленных материалов и архитектурные выводы для Community OS. Он не подтверждает юридическую действительность процедуры и не заменяет отдельный legal-profile analysis.

## 1. Состав рассмотренного пакета

В предоставленный пакет входят фотокопии:

1. протокола общего собрания членов СТ «ЕКСПРЕС» от 24.10.2026;
2. опитувального листа / листа голосування;
3. уведомления о проведении общего собрания 24.10.2026;
4. приложений, перечисленных в протоколе:
   - реестр членов СТ, принявших участие в собрании/голосовании;
   - опросные листы / листы голосования;
   - иные материалы, относящиеся к проведению собрания, при наличии.

Сами реестр участников и полный комплект заполненных опросных листов в предоставленных фотографиях отсутствуют. Поэтому выводы о персональном составе голосующих, количестве реально выданных/возвращённых листов и случаях нескольких голосов одного Subject по разным участкам по этим материалам делать нельзя.

## 2. Наблюдаемые факты процедуры

Из протокола и уведомления следует следующая практическая цепочка:

```text
решение правления 29.09.2026
→ уведомление членов
→ опубликованный порядок дня
→ регистрация участников 24.10.2026
→ общее собрание / обсуждение
→ последующее письменное голосование
→ именные опросные листы
→ подсчёт
→ результаты по каждому вопросу
→ решения общего собрания
→ итоговый протокол + приложения
```

По протоколу:

- общее количество членов СТ согласно реестру — **340**;
- зарегистрировались / приняли участие в собрании и последующем письменном опросе — **181 человек**;

По дополнительному фактическому уточнению пользователя:

- на очной части собрания физически присутствовало примерно **60 участников**;
- присутствующим раздали опросные листы/бюллетени для фиксации позиций по вопросам;
- часть присутствующих отметила варианты ответа, часть не проголосовала по отдельным/всем вопросам;
- после очного собрания правление лично разносило опросные листы другим садоводам;
- итоговый протокол отражает результат уже расширенной процедуры, включавшей очную часть и последующее письменное офлайн-голосование.

Следовательно, предоставленная процедура не должна моделироваться как «одно очное собрание = один момент подачи всех голосов». Практически она имела как минимум:

```text
очное собрание / обсуждение
→ выдача бумажных листов присутствующим
→ часть голосов подана сразу
→ последующая личная доставка листов другим участникам
→ сбор письменных позиций
→ итоговый подсчёт
```

Это означает:

```text
physical presence
≠ participation in written voting
≠ ballot receipt
≠ Vote
```

Число 181 из протокола нельзя трактовать как количество физически присутствовавших в помещении/на территории одновременно.
- указанная доля участия — **53,24 %**;
- в протоколе прямо зафиксировано: **«Кворум: Наявний»**;
- председателем собрания избран Чернега Дмитрий Иванович;
- секретарём собрания избрана Григорьева Раиса Дмитриевна;
- голосование проводилось путём письменного опроса с использованием опросных листов;
- участники указывали ФИО, номер участка и подпись;
- по каждому вопросу выбирался один вариант: «ТАК», «НІ» или «УТР.»;
- результаты и процентные показатели вносились в протокол после подсчёта надлежащим образом заполненных листов.

Есть расхождение во времени начала регистрации:

- уведомление: регистрация участников с **09:30**;
- протокол: начало регистрации с **09:00**.

Это хороший пример того, почему опубликованный документ и фактический документ процедуры должны храниться как разные исторические факты/редакции, а не исправляться задним числом друг другом.

## 3. Повестка и фактически проголосованные вопросы

По итоговому протоколу рассмотрено семь вопросов:

1. приём новых членов и исключение прежних членов в связи с продажей участков;
2. организационно-технические мероприятия:
   - утепление водопроводной трубы;
   - обрезка деревьев возле линий электропередач;
3. создание резервного фонда и дополнительные взносы;
4. взнос на содержание и обслуживание водопровода с питьевой водой;
5. сроки оплаты коммунальных услуг и санкции;
6. норматив потерь электроэнергии;
7. порядок вывоза крупногабаритного мусора, скошенной травы и веток.

Уведомление и итоговый протокол имеют различия структуры/нумерации.

Например:

- вывоз мусора в уведомлении находится внутри вопроса 2 как подпункт 2.3, а в итоговом протоколе становится отдельным вопросом 7;
- сроки оплаты/санкции в уведомлении сформулированы как вопрос 7, а в итоговом протоколе — как вопрос 5;
- отдельные хозяйственные и финансовые формулировки были перераспределены между вопросами.

Это подтверждает необходимость различать:

```text
опубликованная повестка
≠ фактически обсуждавшаяся структура
≠ фактическая формулировка ballot/question
≠ решение по вопросу
```

## 4. Один подписанный бумажный лист содержит несколько голосов

Предоставленный «ОПИТУВАЛЬНИЙ ЛИСТ (лист голосування)» содержит:

- ФИО члена СТ;
- номер участка;
- подпись;
- семь вопросов;
- по каждому вопросу три колонки: «ТАК», «НІ», «УТР.».

Следовательно, в реальной процедуре:

```text
один бумажный Document / Representation
→ одна собственноручная подпись
→ несколько отдельных позиций
→ несколько Vote по разным Governance Questions
```

Из этого следует важный архитектурный инвариант:

> один ballot/document/file не равен одному Vote.

Community OS не должна проектировать обязательную связь `1 Vote = 1 отдельный файл/бюллетень`.

---

## 5. Реальная процедура является Open Offline Voting

Опросный лист содержит одновременно:

- идентичность участника;
- номер участка;
- собственноручную подпись;
- выбор по каждому вопросу.

Следовательно, предоставленная процедура соответствует **открытому офлайн-голосованию**:

```text
Subject / Voting Right
↔ signed paper ballot
↔ Position
```

Для Community OS это прямо подтверждает уже принятое требование:

- администратор/член комиссии может внести бумажный Vote;
- data-entry operator не является voter;
- к Vote можно прикрепить scan/photo подписанного листа;
- physical original остаётся внешним архивным evidence;
- scan/photo не является electronic signature и не создаёт новый Vote.

## 6. Физическое присутствие, участие, получение листа и действительная позиция — разные факты

По дополнительному фактическому уточнению пользователя:

```text
примерно 60 человек
→ физически присутствовали на очной части

далее
→ бюллетени лично разносились другим садоводам

по протоколу
→ 181 человек зарегистрировались / приняли участие
```

По каждому из семи вопросов сумма `ТАК + НІ + УТР.` при этом равна **139**.

Примеры:

- вопрос 1: 132 + 0 + 7 = 139;
- вопрос 2: 135 + 0 + 4 = 139;
- вопрос 3: 119 + 3 + 17 = 139;
- вопрос 4: 114 + 11 + 14 = 139;
- вопрос 5: 125 + 7 + 7 = 139;
- вопрос 6: 113 + 3 + 23 = 139;
- вопрос 7: 124 + 4 + 11 = 139.

Проценты в протоколе считаются относительно **181 участника**, а не относительно 139 учтённых позиций и не относительно всех 340 членов.

Например:

```text
132 / 181 = 72,93 %
7 / 181   = 3,87 %
```

Фактическое уточнение объясняет, что процедура продолжалась после очного собрания и бюллетени разносились другим садоводам, но всё ещё не объясняет точную предметную судьбу разницы между 181 участником процедуры и 139 учтёнными позициями по каждому вопросу. Нельзя без реестра/полного комплекта листов утверждать, что:

- было ровно 139 возвращённых листов;
- остальные 42 не получили лист;
- остальные 42 получили, но не сдали;
- все 42 листа были недействительными;
- эти 42 участника считаются «воздержавшимися».

Следовательно, Community OS должна сохранять различие:

```text
physical presence at meeting
≠ participation in procedure
≠ получение/выдача ballot
≠ сдача ballot
≠ признанная реализация Voting Right
≠ recognized Vote / Position
≠ «Воздержался»
```

Этот кейс является сильным эмпирическим подтверждением понятия **«Реализация права голоса / Voting Right Exercise»** и отдельной семантики участия.

## 7. Membership и Ownership различаются в реальном процессе

По первому вопросу одновременно:

- принимаются в члены новые владельцы участков;
- исключаются прежние члены в связи с продажей участков;
- решения об изменении членства оформляются общим собранием.

Практическая цепочка выглядит как:

```text
изменение Ownership
+
заявление / рассмотрение
+
решение общего собрания
→ Membership change
```

Это подтверждает уже принятую границу Community OS:

```text
Ownership
≠ Membership
```

Продажа участка сама по себе не должна автоматически переписывать Membership.

Документы также подтверждают полезность отдельного будущего BP вступления/прекращения членства, если этот процесс станет приоритетным.

## 8. Эти документы не подтверждают однозначно правило «1 участок = 1 голос»

Протокол оперирует количеством **членов**:

- 340 членов;
- 181 член принял участие;
- проценты рассчитаны относительно количества участвовавших членов.

Опросный лист содержит одновременно:

- ФИО члена;
- номер участка.

Но из предоставленных материалов **не следует**, что Subject с несколькими участками получил несколько листов либо несколько голосов.

Поэтому данный пакет:

- не опровергает сообщённую пилотную практику «1 участок = 1 голос»;
- но и не подтверждает её самостоятельно;
- усиливает необходимость focused validation по реестру участников, заполненным листам и фактической практике «множественного членства».

До такой проверки остаётся корректным текущий проектный статус:

> «1 участок = 1 голос» — реально используемое пилотное требование, юридическое и процедурное основание которого требует отдельной проверки.

---

## 9. Изменение предложения во время обсуждения ≠ изменение ballot

По вопросу резервного фонда в протоколе прямо указано:

- во время обсуждения прозвучало предложение изменить способ распределения целевого взноса;
- предложение зафиксировано как высказанное;
- поскольку вопрос в опросном листе не был переформулирован, голосование оставили по ранее опубликованной формулировке.

Это непосредственно подтверждает важный Governance invariant:

```text
proposal during discussion
≠ material edit of Governance Question
≠ new ballot formulation automatically
```

Community OS должна позволять исторически восстановить:

```text
опубликованный вопрос
→ обсуждение / предложения
→ фактическая ballot formulation
→ Vote
→ Calculation
→ Established Result
→ Management Decision
```

## 10. Термин «опитування» не означает автоматически Informal Survey

В реальной документации СТ формальное голосование называется:

- «письмове опитування»;
- «опитувальний лист»;
- «лист голосування».

При этом Stage 10 Community OS уже использует отдельный предметный термин:

```text
Informal Survey
≠ Voting
```

Следовательно, украинский UI не должен использовать голое слово **«Опитування»** как однозначный эквивалент Informal Survey.

Рекомендуемое продуктово-терминологическое различие:

```text
Неформальне опитування
→ Survey

Голосування
→ Voting

Письмове опитування / лист голосування
→ одна из возможных форм formal Voting
   в конкретном legal/governance profile
```

Предметную модель Stage 10 менять из-за этого не требуется.

## 11. Финансовые решения — соответствие текущей модели

### 11.1. Дополнительный членский взнос по площади

В протоколе предусмотрено увеличение членского взноса на 2026 год на **1,5 грн за 1 м²**.

Это хорошо соответствует текущей модели:

```text
Object Area
→ used value
→ applicable accrual rule
→ Accrual
→ Financial Obligation
```

Community OS уже различает:

```text
Object Area
≠ tariff/rate
≠ Accrual
```

Изменений фундаментальной модели не требуется.

### 11.2. Взнос на питьевой водопровод

Решение:

- **30 грн в месяц** на содержание и обслуживание водопровода с питьевой водой.

Это укладывается в обычную периодическую семантику Accrual / Financial Obligation.

### 11.3. Целевой взнос на резервный фонд

Решение предусматривает целевой взнос:

- **1000 грн в год**;
- с одной семьи;
- постоянно (круглогодично) проживающей на территории;
- независимо от количества участков;
- критерием постоянного проживания предлагается считать фактическое использование электроэнергии в течение года.

Это выявляет реальную предметную потребность, пока не закрытую текущей моделью:

> единицей применения начисления может быть не Subject и не Plot, а «семья/домохозяйство».

Нельзя молча подменить это:

- одним участком;
- одним собственником;
- одним Membership;
- одним Personal Account.

До реализации такого начисления требуется отдельный анализ:

- что является «семьёй/домохозяйством»;
- как определяется её состав;
- кто является обязанной стороной Financial Obligation;
- как избежать двойного начисления при нескольких участках/членах;
- как исторически определяется критерий постоянного проживания.

Новый fundamental `Household` настоящим reference analysis **не вводится**.

### 11.4. Резервный фонд и отдельный банковский счёт

В уведомлении резервный фонд связан с предложением аккумулировать средства на отдельном банковском счёте.

Это подтверждает полезность уже принятого различия:

```text
Funding Source
≠ target/use direction
≠ Bank Account
≠ technical reservation
```

Фактическое организационное правило конкретного сообщества может требовать отдельного счёта, но универсальная модель Community OS не должна считать любой резерв отдельным банковским счётом либо технически блокированным остатком.

## 12. Сроки оплаты, пеня, отключение и повторное подключение

Протокол фиксирует:

- воду оплачивать до 5-го числа текущего месяца;
- при просрочке воды предусматривается начисление пени;
- электроэнергию оплачивать до 10-го числа текущего месяца;
- при неуплате предусматривается отключение от электроснабжения;
- повторное подключение — после погашения задолженности и дополнительной платы **5000 грн**.

### 12.1. Срок и пеня

Это соответствует существующей финансовой модели:

```text
Financial Obligation
→ due date
→ overdue
→ applicable penalty rule
→ financial consequence
```

Но предоставленный протокол не устанавливает конкретную ставку пени. Поэтому никакое ранее обсуждавшееся значение нельзя считать правилом этого решения без отдельного основания.

### 12.2. Отключение электроэнергии

Здесь выявляется отдельный процесс на границе:

```text
Finance
→ overdue/debt fact

Community Operations
→ authorized enforcement/work action

Resource / Engineering
→ actual disconnection / reconnection
```

Текущая модель финансов выдерживает основание, задолженность и дополнительную плату, но полного BP отключения/повторного подключения пока нет.

Нельзя сводить:

```text
debt
= disconnection
```

Фактическое отключение должно оставаться отдельным предметно значимым operational/resource action с применимым authority/rule.

## 13. Норматив потерь электроэнергии и формирование внутренней цены

Протокол утверждает:

- общий норматив потерь — **10 %**;
- из них **3,5 %** — на трансформацию;
- **6,5 %** — потери в сетях товарищества.

Дополнительное фактическое уточнение пользователя определяет, как это применяется в пилоте:

```text
тариф поставщика: 4,32 грн/кВт·ч
нормативная компенсация потерь: 0,43 грн/кВт·ч
внутренняя цена для начисления: 4,75 грн/кВт·ч
```

Число 0,43 грн соответствует примерно 10 % от 4,32 грн с округлением денежной ставки до копеек:

```text
4,32 × 10 % = 0,432
→ 0,43 грн/кВт·ч

4,32 + 0,43 = 4,75 грн/кВт·ч
```

Следовательно, для текущей практики пилота 10 % используются не как отдельное распределение фактически признанной Operational Loss между владельцами, а как **нормативная надбавка / компонент внутренней цены электроэнергии**.

Предметная модель должна сохранять различие:

```text
supplier tariff = 4,32
≠
loss-compensation norm = 10 %
≠
derived compensation component = 0,43
≠
internal owner price = 4,75
≠
actual Operational Loss quantity
```

Практическая цепочка начисления:

```text
recognized individual Consumption
×
applicable internal electricity price
→ Accrual
→ Financial Obligation
```

При этом внутренняя цена исторически объяснима как композиция:

```text
supplier tariff
+
normative loss-compensation component
→ internal electricity price
```

Это хорошо соответствует уже принятой финансовой модели Community OS:

- внешний тариф поставщика и внутренний тариф сообщества не тождественны;
- внутренний тариф может явно зависеть от внешнего тарифа;
- норматив/коэффициент является входом правила, но не Operational Loss;
- применённые тариф, коэффициент, округление и итоговая ставка должны быть исторически определимы.

**Корректировка предыдущего вывода:** данный пилотный документ сам по себе **не доказывает необходимость отдельного BP распределения фактических потерь по владельцам**. Для первого внедрения подтверждён более конкретный процесс — формирование внутренней цены электроэнергии с нормативной компенсацией потерь.

Отдельный loss-allocation process остаётся возможным будущим сценарием для других способов распределения фактических/расчётных потерь, но не должен вводиться только на основании этого пилотного правила.

## 14. Организационно-технические решения

Решения о:

- утеплении водопроводной трубы;
- обрезке деревьев возле ЛЭП;
- организации вывоза крупногабаритного мусора/травы/веток;

## 16. Новые/усиленные кандидаты требований

### 16.1. Stage 11B — обязательный проверочный сценарий

Добавить scenario:

```text
eligible/registered participants = 181
recognized positions per question = 139
```

Система не должна автоматически превращать разницу 42 в:

- «Воздержались»;
- rejected Votes;
- missing ballots;
- non-participants.

Причина должна определяться только по фактическим evidence/process data.

### 16.2. Stage 11B — multi-question paper ballot

Зафиксировать:

> один подписанный бумажный Document может оформлять несколько independent Votes по нескольким Questions.

### 16.3. Stage 11B/UI — terminology

Различать:

- `Неформальне опитування`;
- `Голосування`;
- profile-specific `письмове опитування / лист голосування`.

### 16.4. Membership validation

Для проверки pilot rule `1 Plot = 1 Vote` желательно исследовать:

- приложение №1 — реестр участников;
- заполненные ballot sheets;
- наличие одного Subject несколько раз с разными Plot;
- фактический порядок выдачи листов Subject с несколькими Plot.

### 16.5. Finance — Household/Family charge target

Нужен отдельный stress-test реальной единицы начисления «семья/домохозяйство» без преждевременного введения fundamental Household.

### 16.6. Finance + Operations + Resource — disconnection/reconnection

Нужен отдельный BP/стресс-тест:

```text
debt/overdue basis
→ authorized enforcement decision
→ notice
→ operational work
→ engineering disconnection
→ later debt/payment conditions
→ reconnection
```

### 16.7. Finance + Resource — внутренний тариф электроэнергии с компенсацией нормативных потерь

Для пилота подтверждён не отдельный процесс распределения фактических потерь, а правило формирования внутренней цены:

```text
supplier tariff 4,32
+ loss-compensation component 0,43
→ internal tariff 4,75 грн/кВт·ч
→ Consumption × internal tariff
→ Accrual
```

Нужно сохранить исторически:

- supplier tariff/version;
- норматив 10 %;
- правило расчёта компонента;
- округление до 0,43;
- итоговую internal price 4,75;
- период применимости;
- связь начисления с использованной ставкой.

Не смешивать normative compensation component с фактически признанной Operational Loss.

## 17. Что нельзя считать установленным по этому пакету

Предоставленные материалы **не позволяют достоверно установить**:

1. юридическую действительность всей процедуры;
2. действующую на дату процедуры редакцию устава;
3. почему ровно 42 из 181 участников не отражены в итогах по каждому вопросу;
4. сколько опросных листов было фактически выдано;
5. сколько листов было возвращено;
6. сколько листов было признано недействительными;
7. получал ли один Subject несколько листов по нескольким участкам;
8. было ли правило `1 участок = 1 голос` фактически применено к этой процедуре;
9. конкретную ставку/формулу пени;
10. юридическую допустимость отключения и дополнительной платы 5000 грн;
11. юридический смысл и допустимость критерия «семья, постоянно проживающая»;
12. точный нормативный/правовой статус внутреннего механизма компенсации потерь и правила его изменения; фактический способ расчёта в пилоте уточнён: 4,32 + 0,43 = 4,75 грн/кВт·ч.

Эти пункты требуют дополнительных источников или отдельного legal/profile/process analysis.

## 18. Итог

Предоставленные реальные документы в основном **подтверждают**, а не опровергают текущую архитектуру Community OS.

Особенно хорошо подтверждаются:

- `Participation ≠ Vote`;
- `Voting Right ≠ Vote`;
- необходимость `Voting Right Exercise` для отдельной фиксации реализации права;
- mixed/offline data entry;
- `Document/Signing ≠ Vote`;
- `Document ≠ Calculation ≠ Established Result ≠ Management Decision`;
- `Ownership ≠ Membership`;
- versioned/traceable Governance Question semantics;
- `Object Area` как input начисления, а не финансовый факт;
- `Funding Source / target use / bank account` как разные понятия;
- `approved loss norm ≠ Operational Loss`;
- `Management Decision ≠ Operational Work`.

Главные новые практические пробелы:

1. точная семантика participation/ballot issuance/recognized Vote при расхождении количества участников и голосов;
2. отдельный process для начисления на семью/домохозяйство;
3. процесс отключения/повторного подключения из-за задолженности;
4. конкретное versioned правило формирования внутреннего тарифа электроэнергии с нормативной компенсацией потерь.

Этот reference analysis должен использоваться как **эмпирический источник пилотных сценариев**, но не как самостоятельный нормативный источник архитектуры или права.
