# Первый тестовый стенд Community OS

Стенд рассчитан на синтетические данные и Linux Docker на тестовой ВМ. Использует три контейнера `communityos-test-stand-{postgres,web,worker}`, отдельную внутреннюю Docker-сеть и два именованных тома для PostgreSQL и ключей ASP.NET Data Protection. Порты ВМ не публикуются. Web слушает HTTPS только на loopback контейнера. Worker запускается отдельным процессом, отправка кодов по умолчанию выключена.

## Подготовка

Нужны открытый SSH-туннель к Docker на `127.0.0.1:23750`, Python 3.11 или новее и PowerShell 7. Для сборки образа Docker на ВМ получает закреплённые базовые образы и зависимости из реестров. Образ содержит Web, Worker и собранный Platform Application. Базовые образы и PostgreSQL закреплены по digest, зависимости .NET и pnpm берутся из lock-файлов.

Создайте пустой каталог вне репозитория, доступный только доверенным пользователям. Пример для Windows:

```powershell
$cfg = Join-Path $env:LOCALAPPDATA 'CommunityOS-TestStand'
New-Item -ItemType Directory $cfg
$tag = 'communityos-test-stand:' + (git rev-parse --short HEAD)
./ops/test-stand/init.ps1 -Directory $cfg -Image $tag
python ops/test-stand/stand.py build $tag
```

Сценарий создаёт `stand.json` с тестовыми секретами, `https.pfx` с закрытым ключом и публичный `https.pem` для проверки сертификата. Сертификат действует 30 дней. Секреты не передавайте в чат и не добавляйте в репозиторий. Доступ к Docker даёт доступ к конфигурации контейнеров, поэтому туннель и учётная запись Docker предназначены только для доверенного оператора.

## Запуск и миграции

```powershell
python ops/test-stand/stand.py database (Join-Path $cfg 'stand.json')
python ops/test-stand/stand.py migrate
python ops/test-stand/stand.py up (Join-Path $cfg 'stand.json')
python ops/test-stand/stand.py status
```

Миграции выполняет отдельная учётная запись PostgreSQL в базах `communityos_platform` и `communityos_register`. Команда записывает версию и контрольную сумму каждой миграции вместе с её результатом. Повтор пропускает уже применённые версии. Изменение применённого файла приводит к отказу. Web получает ограниченную роль `stand_web`. Команда запуска печатает только UUID синтетических учётных записей, пароли остаются в локальном `stand.json`.

## HTTPS и проверка

Перед прогоном проверьте состояние стенда командой `status`. Для I‑1 используйте синтетические сообщества, операторов и формат XLSX из разделов ниже. При автоматизации повторяющейся подготовки добавьте в этот раздел команду запуска и ожидаемый результат. Пароли и другие секреты передавайте через локальную конфигурацию. При сбое указывайте шаг проверки, ожидаемый и полученный результат без содержимого выгрузок и секретов.

Оставьте локальный канал открытым в отдельном окне:

```powershell
python ops/test-stand/stand.py relay
```

Откройте `https://127.0.0.1:5443/platform/`. Канал принимает соединения только на loopback Windows и передаёт TLS через уже открытый SSH-туннель к Docker. Сверьте SHA-256 сертификата с выводом `init.ps1`. Для проверки состояния можно указать доверенный сертификат явно:

```powershell
curl.exe --cacert (Join-Path $cfg 'https.pem') https://127.0.0.1:5443/health/ready
```

Войдите как `stand-creator`. Создайте синтетическое сообщество и укажите UUID `stand-administrator`. Войдите под администратором, проверьте назначение в созданном сообществе и отказ для другого UUID. Под `stand-creator` отзовите назначение и проверьте журнал. Повтор с тем же идентификатором запроса не восстанавливает отозванное назначение.

## Остановка и повторный запуск

```powershell
python ops/test-stand/stand.py stop
python ops/test-stand/stand.py database (Join-Path $cfg 'stand.json')
python ops/test-stand/stand.py migrate
python ops/test-stand/stand.py up (Join-Path $cfg 'stand.json')
```

Остановка сохраняет контейнеры, базы и тома. Сценарий отказывается использовать контейнеры, сети или тома без метки этого стенда. Смена образа или конфигурации требует отдельно пересоздать только контейнеры стенда с сохранением именованных томов.

## Проверка живой доставки

SMTP и Telegram включаются отдельным изменением конфигурации стенда после согласования тестовых получателей. Для него нужны тестовый SMTP-сервер с STARTTLS, данные отправителя и тестовая почта, а также токен тестового бота и заранее подтверждённый личный чат. Секреты передаются через защищённое хранилище или вводятся владельцем непосредственно в закрытую конфигурацию. Worker понадобится управляемый исходящий доступ к SMTP и Telegram Bot API. Входящие порты ВМ для этого не нужны. [Роли и параметры доставки](../../docs/implementation/PLATFORM_RECOVERY_DELIVERY.md)

## Ручной реестр I‑1

Для проверки используйте закрытый стенд с синтетическими данными. Соберите новый образ Web и Worker и примените миграции командой `migrate`. Для обновления существующего стенда пересоздайте только контейнеры Web и Worker с новым образом. Сохраните контейнер PostgreSQL и тома. Команда `up` проверяет, что конфигурация существующих контейнеров совпадает с запрошенной.

Создайте два синтетических сообщества через Platform Application. Для каждого сообщества доверенный оператор стенда добавляет строку `platform_provisioning.register_availability` с его `community_id` и установленными `community_active` и `register_enabled`. В `platform_provisioning.register_operator` укажите идентификаторы сообщества, тестовой учётной записи и связанного с ней синтетического субъекта. Для действующей связи установите `linked`. Задайте права `can_read` и `can_add` отдельно. Для внесения записи укажите синтетическое основание в `addition_basis`. Тестовые назначения выполняются отдельно от назначения технического администратора.

Войдите через `/platform/` под тестовым оператором и откройте `/community/` на том же локальном HTTPS-адресе. Выберите сообщество, добавьте участок с новым собственником и второй участок с отдельным счётом, выбрав того же собственника. Проверьте конфликт номера участка и номера счёта. Перезапустите Web и повторно откройте реестр. Убедитесь, что записи сохранились. Для проверки отзыва сбросьте `can_add` у оператора и повторите запрос в той же сессии. После проверки удалите синтетические назначения или отключите функцию реестра для этих сообществ.

### Подготовка импорта OSBBX

После миграций установите `can_prepare_import` в тестовом назначении оператора. В разделе «Підготовка імпорту OSBBX» загрузите синтетический XLSX с листом «Власники» и колонками «Номер ділянки», «ПІБ», «Особовий рахунок». Счета с ведущими нулями запишите как текст. Стенд принимает архивы до 2 МиБ и до 500 строк данных.

Укажите проверенное имя и ключ собственника. Повторите ключ только для участков, которые относятся к одному собственнику. Сохраните черновик, выйдите, войдите снова и откройте его из списка. Для проверки изоляции войдите под другим тестовым оператором с тем же правом и убедитесь, что первый черновик недоступен. Затем сбросьте `can_prepare_import` у первого оператора и проверьте отказ в той же сессии. Предпросмотр читает текущий реестр и не применяет план.

### Утверждение и применение импорта

В том же синтетическом сообществе создайте отдельное назначение утверждающего с другой учётной записью и другим субъектом. Установите `can_approve_import` и задайте синтетическое основание в `import_approval_basis`. Под подготовщиком сохраните проверенные решения и нажмите «Передати на затвердження». Под утверждающим выберите ту же ревизию в разделе «Затвердження імпорту OSBBX», сверяйте строки и нажмите «Підтвердити й застосувати імпорт». В отчёте сопоставьте номера строк и идентификаторы созданных записей.

Для проверки устаревания передайте ревизию и сохраните новые решения до утверждения. Для проверки конфликта добавьте в реестр участок с совпадающим номером после открытия плана утверждающим. В обоих случаях импорт не должен создать записи. Повторите успешный запрос подтверждения и убедитесь, что отчёт сохранил первоначального утверждающего. Проверьте отказ по чужому сообществу и после сброса `can_approve_import` в действующей сессии.

### Исправление привязки собственника

Используйте участок из синтетического импорта и другого существующего собственника в том же сообществе. Оператору с правом чтения задайте `can_correct_ownership` и тестовое основание в `ownership_correction_basis`. Откройте историю участка, выберите правильного собственника и укажите причину. После исправления обновите страницу. Сверьте текущего собственника, историю, лицевой счёт и исходный отчёт импорта.

Для проверки конкуренции откройте участок в двух вкладках до первого исправления. Подтвердите запросы с одной ревизией. Устаревшая вкладка должна предложить обновить запись. Сбросьте `can_correct_ownership` и проверьте отказ без повторного входа. Для проверки истории без права чтения используйте отдельного тестового оператора.

## Ручной учёт электроэнергии I‑2

Переиспользуйте участок из синтетического реестра. Установите `electricity_enabled` у тестового сообщества и `can_read_electricity` у оператора. Для настройки и признания задайте `can_setup_electricity` и `can_recognize_electricity` и отдельные тестовые основания в `electricity_setup_basis` и `electricity_recognition_basis`. В разделе «Облік електроенергії» выберите участок и зарегистрируйте установку с датой начала.

Признайте два ручных показания в кВт·ч с разными датами. Сверьте разницу и даты интервала. Повторите одно значение за ту же дату и проверьте, что число показаний не меняется. Проверьте конфликт за ту же дату, дату до начала установки и значение, противоречащее соседним. Войдите заново и сверьте результат. Уберите основание признания и повторите запись в той же сессии. Сервер должен отказать, а чтение должно остаться доступным.

Для замены включите `can_replace_electricity` и задайте тестовое `electricity_replacement_basis`. На участке с установленным счётчиком укажите новое обозначение, дату начала его измерительного использования и причину. Выберите обе установки в истории и сверьте показания отдельно. Проверьте, что показание старого прибора на дату замены отклоняется, а запоздалое показание до границы можно внести после явного выбора старой установки. При отсутствии граничных данных оценка через замену не формируется.

Для проверки двух регистров выберите участок без установки и при регистрации прибора укажите «День і ніч». Внесите дневные и ночные показания на две одинаковые даты. Сверьте обе разницы и их сумму. Затем внесите промежуточное значение только для одного регистра. Раздельные оценки обновятся, а сумма для прежнего интервала исчезнет. Проверьте повтор и конфликт в одном регистре и отказ для суммарного канала. Ранее зарегистрированные суммарные приборы по-прежнему принимают показания без выбора регистра.

Перед миграциями Platform `015` и Community `011` остановите старый Web. После миграций запустите новый образ. Новый Web передаёт режим и канал при записи допуска, включая запросы по прежнему HTTP API.

Для общей точки выдайте оператору с правом чтения `can_setup_common_electricity` и задайте `common_electricity_setup_basis`. В форме «Зареєструвати загальну точку» укажите название, измерительную границу, обозначение прибора и дату установки. Внесите два показания. Переключитесь между общей точкой и индивидуальным участком и сравните отдельные интервалы. Повторите создание с тем же названием, затем сбросьте право создания и повторите запрос в той же сессии.

При регистрации и замене заполните модель, серийный номер, место и дату монтажа. При наличии пломбы укажите её номер. Дату начала измерительного использования укажите отдельно. На синтетической точке ТП задайте коэффициент 40 и признайте исходные показания 100 и 103. Проверьте разницу 3 и расчёт 120 кВт·ч. При замене задайте коэффициент 1 и проверьте расчёт новой установки и сохранность 120 кВт·ч в старой. Для двух регистров сверяйте преобразованные разницы и их сумму только на совпадающих интервалах.

### Деревья точек учёта

После миграций Platform `017` и Community `014` переиспользуйте три участка с установками и шесть общих точек синтетического сообщества. При необходимости создайте недостающие точки по инструкции выше. У оператора с правом чтения электроэнергии укажите тестовое основание в `topology_publication_basis`.

В разделе «Дерева точок обліку» откройте новую редакцию и добавьте две ТП. Назначьте два корня первой ТП и один второй. Под каждым корнем разместите одну контрольную точку улицы и один участок. Опубликуйте редакцию, затем скопируйте её и перенесите одну улицу под другой корень с более поздней даты. По очереди откройте обе даты измерения и сверьте пути. Замените счётчик на одной из точек и проверьте сохранность обеих редакций. После сброса `topology_publication_basis` повторите публикацию в той же сессии и проверьте, что чтение осталось доступным.

### Пакетный импорт показаний

Примените миграцию Community `015`. Создайте синтетическую установку с коэффициентом 40 и скопируйте её идентификатор из карточки установки. В CSV с заголовком `installation_id,measured_on,channel,value_kwh` добавьте значения 100 и 103 на две даты действия установки, строку с неверной датой и строку с неизвестной установкой. Укажите регистр `total` для однотарифной установки. Используйте прежние тестовые назначения чтения и признания показаний.

В разделе «Імпорт показань CSV» загрузите файл, проверьте строки предпросмотра и подтвердите применение. Сверьте результат по строкам и расчёт 120 кВт·ч в карточке установки. Повторите применение и проверьте, что число показаний не выросло. Загрузите новый файл с конфликтующим значением на уже записанную дату и допустимым значением на промежуточную дату. После отзыва права признания проверьте отказ в той же сессии и доступность предпросмотра. Порядок подготовки шаблона описан в [сценарии импорта](../../docs/implementation/I2_ELECTRICITY_READING_IMPORT.md).

### Техническая вода

Примените Platform `018` и Community `016`. Для синтетического сообщества установите `water_enabled`. Тестовому оператору с действующей связью задайте `can_read_water` и отдельные основания `water_setup_basis` и `water_recognition_basis`.

В разделе «Облік технічної води» зарегистрируйте общую точку на выходе насоса и точку участка из синтетического реестра. Внесите значения 10 и 12,500 м³ на разные даты для общей точки, сверив разницу 2,500 м³. Повторите первое значение, затем отправьте другое значение на ту же дату. Вставьте допустимое запоздалое значение между датами и проверьте перерасчёт интервалов. Внесите показание на участке и проверьте раздельный учёт. Сбросьте `water_recognition_basis` и проверьте отказ в прежней сессии при сохранении чтения.

### Регулярный расчётный период

Примените Platform `019` и Community `017`. Для отдельного синтетического сообщества включите `billing_enabled`. Выдайте тестовому оператору `can_read_billing` и задайте `billing_post_basis`. Создайте лицевые счета с однозначным владельцем и установки электроэнергии с показаниями на обеих границах периода. Мигратор добавляет в `community_billing.tariff` версию со ставками в JSON, например `{"total":4,"day":4,"night":2}`, и в `community_billing.member_fee` версию взноса 25 грн. Обе версии должны покрывать период и иметь тестовое основание.

В разделе «Розрахунковий період» задайте четыре даты, откройте предпросмотр и проверьте суммы. Измените тестовую версию тарифа до подтверждения и проверьте требование обновить расчёт. Проведите обновлённый период, откройте его по границам потребления и сравните сохранённый снимок. После изменения ставки проведённый снимок сохраняется. После сброса `billing_post_basis` в текущей сессии запись отклоняется, а история доступна.

### Перерасчёт электроэнергии

Примените Platform `020` и Community `018`. Переиспользуйте синтетический сценарий регулярного периода без распределённых оплат. Оператору с `can_read_billing` задайте тестовое основание `billing_recalculate_basis`. В проведённом периоде выберите счёт в разделе «Перерахунок електроенергії». После изменения синтетического тарифа укажите основание, проверьте прежнюю сумму, новый расчёт и разницу, затем подтвердите. Проверьте увеличение и уменьшение. При той же сумме должна добавиться запись проверки без изменения действующей суммы обязательства.

Поменяйте тариф между предпросмотром и подтверждением. Сервер должен потребовать повторный расчёт. После сброса `billing_recalculate_basis` проверьте отказ в той же сессии и сохранность истории. Сверьте исходный снимок периода, взнос и другой лицевой счёт. Действующая сумма доступна через `community_billing.effective_obligation`.

### Разовое начисление

Примените Platform `021` и Community `019`. В синтетическом сообществе с включённым расчётом выдайте оператору с правом чтения основание `one_off_post_basis`. В разделе «Разове цільове нарахування» загрузите счета, выберите два счета с однозначными плательщиками и задайте по 250 грн, назначение, основание и срок оплаты.

Проверьте сумму 500 грн в предпросмотре и отсутствие записей в истории до подтверждения. Проведите пакет, откройте его в истории и сверяйте две отдельные суммы по 250 грн. Измените плательщика между предпросмотром и подтверждением следующего пакета и проверьте отказ. Затем сбросьте `one_off_post_basis` и проверьте отказ в той же сессии при сохранении доступа к истории.

### Ручной платёж и первичное распределение

Примените Platform `022` и Community `020` на отдельном синтетическом экземпляре. Оператору с доступом к расчётам задайте отдельные основания `payment_record_basis` и `payment_allocate_basis`. Создайте два обязательства одного плательщика на 250 и 100 грн через разовые начисления.

В разделе «Платежі та розподіл» зарегистрируйте 300 грн. Проверьте предпросмотр распределения 200 и 75 грн, подтвердите и сверьте остатки 50 и 25 грн по обязательствам и 25 грн по платежу. Сбросьте основания по очереди и повторите соответствующий запрос в той же сессии. Для проверки гонки подготовьте два предпросмотра, использующих один доступный остаток, и подтвердите оба. Проведённый результат должен быть один.

### Приём наличных

Примените Platform `023` и Community `021` на отдельном синтетическом экземпляре. Кассиру с правом чтения расчётов задайте `cash_acceptance_basis`. В «Платежі та розподіл» выберите «Прийом готівки», плательщика, дату приёма, 300 грн и синтетическое основание. После подтверждения сверьте в истории идентификаторы приёма и платежа и доступную сумму 300 грн.

Под отдельным оператором с `payment_allocate_basis` распределите 200 и 75 грн по обязательствам на 250 и 100 грн. Сверьте остатки 50, 25 и 25 грн. У кассира сбросьте `cash_acceptance_basis` и проверьте отказ подтверждения в прежней сессии. Просмотр истории должен оставаться доступным.

### Признание переплаты

Примените Platform `027` и Community `026`. На отдельном синтетическом экземпляре задайте оператору с правом просмотра расчётов основание `overpayment_recognize_basis`. Распределите 500 грн на обязательство на 600 грн, затем пересчитайте его до 480 грн. В «Залишки розрахунків» выберите плательщика, введите 20 грн и основание, проверьте предпросмотр и подтвердите признание. Сверьте историю и неизменный нераспределённый остаток. Повторите запрос и проверьте отказ после снятия права в действующей сессии.

### Перераспределение платежа

Примените Platform `025` и Community `024` на отдельном синтетическом экземпляре. Оператору с правом просмотра расчётов задайте `payment_reallocate_basis`. Откройте платёж из сценария первичного распределения и перенесите 20 грн из строки на 200 грн на второе обязательство. Сверьте остатки 70 и 5 грн, нераспределённые 25 грн и историю обоих действий. Затем перенесите всю новую строку на 20 грн обратно. Проверьте отказ при превышении доступной суммы, устаревшем предпросмотре и после сброса основания в действующей сессии.

### Исправление суммы платежа

Для сверки откройте «Залишки розрахунків» в разделе платежей и выберите плательщика из сценария первичного распределения. Сверьте долг 75 грн и нераспределённый остаток 25 грн. Просроченная часть определяется сроками обязательств на текущую дату Киева. После переноса 20 грн проверьте сохранение долга и нераспределённого остатка.

Примените Platform `026` и Community `025` на отдельном синтетическом экземпляре. Оператору с правом просмотра расчётов задайте `payment_correct_basis`. Зарегистрируйте ручной платёж на 300 грн. В разделе «Виправлення суми платежу» введите 280 грн и основание, затем проверьте предпросмотр и подтвердите. Сверьте историю и доступные 280 грн. Распределите 200 и 75 грн по обязательствам на 250 и 100 грн. Должны остаться 50 и 25 грн по обязательствам и 5 грн по платежу. Проверьте отказ исправления после распределения. До распределения совпадающая сумма должна вернуть «без изменений» без записи в истории.

### Добровольный аванс на членские взносы

Примените Platform `028` и Community `027` на отдельном синтетическом экземпляре. Оператору с правом просмотра расчётов задайте `advance_basis`. Зарегистрируйте платёж 300 грн, выберите его в «Платежі та розподіл», откройте «Визнати аванс на членські внески» и подтвердите резерв 200 грн с основанием. Сверьте свободный остаток 100 грн.

Проведите период с членским взносом 150 грн для того же плательщика. Откройте аванс, выберите «Застосувати аванс» и подтвердите 150 грн. Сверьте нулевой долг, остаток аванса 50 грн, свободные 100 грн и историю обеих операций. Повторите подтверждение, проверьте отказ без CSRF и после сброса `advance_basis` в действующей сессии.
