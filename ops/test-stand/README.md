# Первый тестовый стенд Community OS

Стенд рассчитан на синтетические данные и Linux Docker на тестовой ВМ. Использует три контейнера `communityos-test-stand-{postgres,web,worker}`, отдельную внутреннюю Docker-сеть и два именованных тома для PostgreSQL и ключей ASP.NET Data Protection. Порты ВМ не публикуются. Web слушает HTTPS только на loopback контейнера. Worker запускается отдельным процессом, отправка кодов по умолчанию выключена.

Порядок развёртывания отдельного доступного через интернет стенда описан в [инструкции приёмки для бухгалтера](ACCOUNTANT_ACCEPTANCE.md).

## Подготовка

Нужны открытый SSH-туннель к Docker на `127.0.0.1:23750`, Python 3.11 или новее и PowerShell 7. Для сборки образа Docker на ВМ получает закреплённые базовые образы и зависимости из реестров. Образ содержит Web, Worker и собранный Platform Application. Базовые образы и PostgreSQL закреплены по digest, зависимости .NET и pnpm берутся из lock-файлов.

Создайте пустой каталог вне репозитория, доступный только доверенным пользователям. Пример для Windows:

```powershell
$cfg = Join-Path $env:LOCALAPPDATA 'CommunityOS-TestStand'
New-Item -ItemType Directory $cfg
$tag = 'communityos-test-stand:' + (git rev-parse --short HEAD)
./ops/test-stand/init.ps1 -Directory $cfg -Image $tag
python ops/test-stand/stand.py build $tag
```

Сценарий создаёт `stand.json` с тестовыми секретами, `https.pfx` с закрытым ключом и публичный `https.pem` для проверки сертификата. Сертификат действует 30 дней. Секреты не передавайте в чат и не добавляйте в репозиторий. Доступ к Docker даёт доступ к конфигурации контейнеров, поэтому туннель и учётная запись Docker предназначены только для доверенного оператора.

## Запуск и миграции

```powershell
python ops/test-stand/stand.py database (Join-Path $cfg 'stand.json')
python ops/test-stand/stand.py migrate
python ops/test-stand/stand.py up (Join-Path $cfg 'stand.json')
python ops/test-stand/stand.py status
```

Миграции выполняет отдельная учётная запись PostgreSQL в базах `communityos_platform` и `communityos_register`. Команда записывает версию и контрольную сумму каждой миграции вместе с её результатом. Повтор пропускает уже применённые версии. Изменение применённого файла приводит к отказу. Web получает ограниченную роль `stand_web`. Команда запуска печатает только UUID синтетических учётных записей, пароли остаются в локальном `stand.json`.

## HTTPS и проверка

Перед прогоном проверьте состояние стенда командой `status`. Для I‑1 используйте синтетические сообщества, операторов и формат XLSX из разделов ниже. При автоматизации повторяющейся подготовки добавьте в этот раздел команду запуска и ожидаемый результат. Пароли и другие секреты передавайте через локальную конфигурацию. При сбое указывайте шаг проверки, ожидаемый и полученный результат без содержимого выгрузок и секретов.

Оставьте локальный канал открытым в отдельном окне:

```powershell
python ops/test-stand/stand.py relay
```

Откройте `https://127.0.0.1:5443/platform/`. Канал принимает соединения только на loopback Windows и передаёт TLS через уже открытый SSH-туннель к Docker. Сверьте SHA-256 сертификата с выводом `init.ps1`. Для проверки состояния можно указать доверенный сертификат явно:

```powershell
curl.exe --cacert (Join-Path $cfg 'https.pem') https://127.0.0.1:5443/health/ready
```

Войдите как `stand-creator`. Создайте синтетическое сообщество и укажите UUID `stand-administrator`. Войдите под администратором, проверьте назначение в созданном сообществе и отказ для другого UUID. Под `stand-creator` отзовите назначение и проверьте журнал. Повтор с тем же идентификатором запроса не восстанавливает отозванное назначение.

### Запуск браузерной проверки из очереди Windows

Для согласованной задачи с браузерным прогоном диспетчер назначает `result: pr`. Для `result: report` диспетчер передаёт Codex `--sandbox read-only`. В задании `pr` действует режим из конфигурации исполнителя, поскольку диспетчер запускает его без этого флага. Проверяйте режим по фактическому запуску очереди. Учётная запись Windows определяет права ОС, а параметр `--expect-read-only` выбирает проверки прав в приложении. В `report` фиксируйте результаты уже состоявшихся прогонов.

В штатном прогоне используйте команду нужного сценария из этой инструкции, установленные Node, Playwright и Edge, внутренний синтетический шаблон и образ проверяемого SHA. Для сценария справки обычная точка входа — `check_finance_help.py`. Он передаёт запуск Edge дочернему Node, который наследует окружение. В задании `pr` создайте отдельный каталог прогона в разрешённой процессу временной области и передайте его в `TEMP` и `TMP` только процессу прогона. Убедитесь, что Node видит этот каталог через `os.tmpdir()`. Снимки храните отдельно от временных файлов браузера, вне репозитория.

При `EPERM` на создании временного каталога запишите режим запуска, код ошибки и операцию `mkdtemp`, если она видна в диагностике. Проверьте существование родительского каталога и попробуйте создать и удалить пробный подкаталог тем же Node из того же режима. `ENOENT` при отсутствующем родителе указывает на путь. Если родитель существует, проверяйте права записи Windows для фактического процесса и политику его изоляции. Сравнение с разрешённым прогоном на том же исполнителе помогает различить причины. Одного `EPERM` для вывода о причине недостаточно. В отчёт включайте SHA, сценарий, шаг и результат без персональных путей, локальных журналов, cookies и данных закрытого стенда.

Playwright создаёт в `os.tmpdir()` каталог артефактов и временный профиль Edge и удаляет их при штатном закрытии браузера. Обёртка проверки справки закрывает локальное реле, удаляет временную сессию и свой Web-контейнер. После выхода скрипта вызывающий процесс удаляет выделенный временный каталог вместе со служебными файлами, которые могли оставить дочерние процессы. Снимки убирайте после проверки результата. Для подтверждения повторяемости выполните ту же команду в новом процессе и после каждого запуска проверьте освобождение временных ресурсов.

```powershell

python ops/test-stand/stand.py database (Join-Path $cfg 'stand.json')
python ops/test-stand/stand.py migrate
python ops/test-stand/stand.py up (Join-Path $cfg 'stand.json')
```

Остановка сохраняет контейнеры, базы и тома. Сценарий отказывается использовать контейнеры, сети или тома без метки этого стенда. Смена образа или конфигурации требует отдельно пересоздать только контейнеры стенда с сохранением именованных томов.

## Проверка живой доставки

SMTP и Telegram включаются отдельным изменением конфигурации стенда после согласования тестовых получателей. Для него нужны тестовый SMTP-сервер с STARTTLS, данные отправителя и тестовая почта, а также токен тестового бота и заранее подтверждённый личный чат. Секреты передаются через защищённое хранилище или вводятся владельцем непосредственно в закрытую конфигурацию. Worker понадобится управляемый исходящий доступ к SMTP и Telegram Bot API. Входящие порты ВМ для этого не нужны. [Роли и параметры доставки](../../docs/implementation/PLATFORM_RECOVERY_DELIVERY.md)

## Справка финансовых сценариев

Для повторяемой проверки [справки I‑5](../../docs/implementation/I5_FINANCE_HELP.md) используйте существующий синтетический Web-контейнер как шаблон конфигурации. В его сообществе должны быть проведённый расчётный период, непогашенное обязательство, индивидуальная точка воды со счётом, признанный платёж, смета и хотя бы один признанный расход, а у тестового оператора — чтение финансов. Сначала соберите образ проверяемого коммита обычной командой `stand.py build`. Новые файлы `src` должны быть учтены в Git перед сборкой: упаковка использует `git ls-files`.

```powershell
python ops/test-stand/check_finance_help.py --image communityos-test-stand:<sha> --template-container <synthetic-web-container> --community <synthetic-community-uuid> --login <synthetic-reader-login> --node <path-to-node.exe> --screenshot <absolute-path-outside-repository.png> --expect-read-only
```

Требуется установленный Playwright для Node с браузером Edge; если пакет находится вне репозитория, укажите его каталог `node_modules` через `NODE_PATH`. Скрипт не устанавливает зависимости. Для проверки отсутствующих границ воды синтетический набор не должен содержать показаний на 02.01.2026 и 02.02.2026; прогон ожидает неготовый результат с неопределённой суммой. Без `--expect-read-only` можно повторить прогон под существующим оператором с правами записи. Он использует текущие назначения, не выдавая новых прав.

Скрипт создаёт отдельный Web-контейнер с образом проверяемого коммита, наследует закрытую конфигурацию и сертификат только из маркированного синтетического контейнера, создаёт временную тестовую сессию и открывает loopback-канал на порту 5543. В конце удаляет сессию и останавливает созданный контейнер; базы и исходный контейнер сохраняются. Текст секретов не выводится, cookie передаётся браузеру через окружение дочернего процесса. Не используйте реальные данные. Снимок экрана хранится вне репозитория.

Ожидаемый итог: `PASS` для двадцати трёх контекстных разделов, общего текста руководства, маршрутов читателя/оператора с 9/15 ссылками и возврата к 23 темам, сохранения маршрута при повторном открытии, выбора плательщика в остатках, расчёта воды без граничных данных, сводок начислений и поступлений с фильтром источника и ошибкой дат, перехода к платежу с сохранением дат отчёта, переходов реестр/выписка со сбросом фильтров, режима печати без справки, поиска и открытия проведённого периода, ошибки обратного диапазона и сброса фильтра, загрузки сверки, счетов и истории разовых начислений, выбора признанного платежа, его остатка и справки исправления/переноса, переплаты и аванса, банковской рабочей области и блокировки предпросмотра без файла/счёта, навигации, закрытия и фокуса, узкого окна, смены рабочей области и отсутствия запросов записи. С `--expect-read-only` дополнительно проверяется отсутствие форм регистрации сметы и признания расхода.

### Матрица флагов прав для справки

Добавьте `--permission-profiles` к той же команде. Прогон подставляет флаги только в браузерный ответ списка сообществ: без чтения финансов (даже при всех флагах операций), читатель, каждый из 15 флагов отдельно и все вместе. Для 17 профилей с чтением повторяется полный сценарий; для профиля без чтения проверяются отсутствие руководства, области платежей и запросов финансовых данных. Дополнительно проверяется видимость форм сметы, расхода и каналов ручного/кассового платежа. Ожидаемый итог: `PASS: 18 browser permission profiles`.

Нужны те же синтетические данные и существующее право чтения финансов. Назначения доступа в базах не меняются. Все браузерные запросы кроме GET блокируются до отправки; любая попытка записи проваливает прогон. Этот режим проверяет отображение справки при флагах интерфейса, а не серверную авторизацию или выполнение финансовых операций. Для матрицы временная сессия действует до 15 минут; после окончания она удаляется, как в обычном режиме. Снимок сохраняет последний профиль с полным набором флагов.

## Справка прибора и установки электроэнергии

Используйте `check_finance_help.py` с теми же параметрами закрытого синтетического стенда и `--scenario electricity-installation` вместо `--permission-profiles`. Нужны существующее чтение электроэнергии и индивидуальная точка с установкой; несколько записей в её истории позволят проверить также прежние характеристики. Прогон не создаёт данные; кроме POST предпросмотра CSV запросы записи блокируются. Он сверяет поля истории с ответом чтения API, общий текст справки и руководства, пример коэффициента, Escape/фокус, окно 390 px и снятие выбора сообщества. Ожидаемый итог: `PASS: electricity installation shared help`. Сценарий также сверяет справку ручного признания с её руководством и таблицу признанных показаний с данными чтения (дата, регистр, значение). С `--expect-read-only` проверяет отсутствие кнопки признания показаний у существующего читателя; назначения прав не меняются. Дополнительный снимок справки показаний сохраняется с суффиксом `.readings.png`.

## Единый синтетический прогон I‑2

Общий прогон последовательно выполняет все браузерные сценарии электроучёта и водоучёта из `check_electricity_topology_publication.py`. Каждый сценарий создаёт отдельное синтетическое сообщество. Используйте чистый по отслеживаемым файлам Git checkout, подготовленный стенд с миграциями, маркированный синтетический шаблон, тестовый логин и Node с Playwright. Порт локального реле должен быть свободен на время прогона.

```powershell
$commit = git rev-parse HEAD
$output = Join-Path $env:TEMP ('communityos-i2-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
python ops/test-stand/check_i2_acceptance.py --commit $commit --image-source-commit $commit --image $tag --template-container communityos-test-stand-help-template-web --login i1-operator --node 'C:\path\to\node.exe' --output-dir $output
```

Для уже собранного образа передайте в `--image-source-commit` полный SHA, из которого его собрали. Скрипт сравнит исходники, параметры сборки и Dockerfile с проверяемым коммитом. При наличии метки ревизии образа она тоже сверяется, иначе происхождение берётся из указанного SHA. Каждый сценарий запускается с одним и тем же локальным ID образа.

Новый каталог вне репозитория содержит снимки и `summary.json` с SHA, ID образа, источником сведений о сборке, статусом и результатом каждого сценария. При первой ошибке дальнейшие сценарии остаются `not_run`. Полностью успешный прогон даёт `passed` и код 0. Для подтверждения состояния I‑2 отдельно сохраните ссылку на CI того же SHA и сверьте оставшиеся критерии с [аудитом приёмки](../../docs/implementation/I2_ACCEPTANCE_EVIDENCE.md).

## Публикация электрического леса и отзыв полномочия

`check_electricity_topology_publication.py` создаёт новое синтетическое сообщество на каждый запуск, девять точек (три корня на двух ТП, три улицы, три участка) и временную сессию существующей синтетической учётной записи. Публикация выполняется через форму браузера с настоящим серверным полномочием. Назначения в прежних сообществах не изменяются. Требуются тот же Docker-туннель, Python, Node/Playwright и Edge, что и для справочных прогонов.

```powershell
python ops/test-stand/check_electricity_topology_publication.py --image $tag --template-container communityos-test-stand-help-template-web --login i1-operator --node 'C:\path\to\node.exe' --screenshot (Join-Path $env:TEMP 'topology-publication.png')
```

Укажите существующий маркированный синтетический контейнер вместо `communityos-test-stand-help-template-web`; при необходимости задайте `NODE_PATH` к установленному Playwright. Используйте образ проверяемого приложения. Допустимо повторно использовать образ при подтверждённом отсутствии различий `src` между его коммитом и проверяемым SHA.

Ожидаются два сообщения `PASS`: браузерная публикация и отказы (повтор даты 409, отсутствие CSRF 403, отправка из открытого редактора после отзыва 403), затем сверка одной редакции и двух допусков (успешная публикация и конфликт даты). Сверяются все девять связей и отсутствие нового допуска после отзыва. После перезагрузки редактор скрыт, чтение опубликованного леса доступно. Подстановка флагов браузеру не используется.

В `finally` удаляются временная сессия и контейнер, право публикации нового сообщества отзывается. Синтетические данные и аудит сохраняются для сверки; повтор создаёт другой набор. Пароли/ключи наследуются из закрытой конфигурации шаблона и не выводятся. Скриншот хранится вне репозитория. Этот сценарий закрывает публикацию топологии; признание показаний и остальные операции I‑2 требуют своих прогонов.

Режим `--scenario forest-replacement` использует те же параметры. Выдаёт отдельные права публикации и замены в новом синтетическом сообществе. Браузер публикует три корня на двух ТП с 01.01.2026, копирует редакцию, переносит улицу с участком под корень другой ТП и публикует с 03.01.2026. После замены счётчика участка с 04.01.2026 проверяет оба пути на дату и две установки одной точки. После отзыва публикации открытая форма получает 403, чтение дерева и право замены сохраняются. Первый `PASS` подтверждает браузерный сценарий, второй — две редакции по девять точек и одну замену со ссылками ровно на три предметных допуска Platform. При завершении отзываются оба права.

## Регистрация счётчика и история параметров установки

Режим `--scenario installation-history` создаёт свободный участок в новом синтетическом сообществе и временно выдаёт права регистрации и замены. Используются те же параметры образа, шаблона, логина, Node и снимка. Оператор регистрирует двухрегистровый прибор с коэффициентом 40, затем заменяет его прибором с коэффициентом 1. Сверяются модель, серийный номер, место, дата монтажа, дата начала использования, пломба и коэффициент обеих установок в API и интерфейсе. На новой установке пломба оставлена пустой. Режим регистров и идентификатор точки сохраняются.

Каждая форма получает 400 при дате монтажа позже начала использования. После отзыва права замены открытая форма получает 403, просмотр обеих установок доступен. Первый `PASS` подтверждает браузерный сценарий. Второй подтверждает две установки и одну замену, связанные с двумя допусками Platform. При завершении отзываются оба права.

## Регистрация поверки водомера

Режим `--scenario water-verification` подготавливает новое синтетическое сообщество с двумя действующими водомерами и временным правом поверки. Даты берутся от серверного `today` в Europe/Kyiv; ответы не подменяются.

Через форму регистрируются четыре поверки на разные даты: срок просрочен, сегодня, через 30 и через 31 день. Новый режим даёт три `PASS`, включая сверку шести фактов на трёх типах точек и восьми допусков Platform.

## Проведение расчётного периода с водой

Режим `--scenario water-period-posting` использует те же параметры. Стенд готовит один синтетический лицевой счёт с электроэнергией, водой и членским взносом. Браузер проводит период с водой и ещё один без неё. Для первого периода сохраняются 480, 25 и 50 грн отдельными строками. Для второго сохраняются 160 и 25 грн. Повтор возвращает прежний идентификатор и снимок, изменение выбора воды для проведённых дат получает 409. После отзыва проведения открытая форма получает 403, история и строка воды на 50 грн в сверке остаются доступны.

Первый `PASS` подтверждает браузерный сценарий. Второй подтверждает два периода, пять пар начисление и обязательство, четыре допуска Platform и соответствие отпечатков сохранённым снимкам.

Для конкурентного проведения запустите ту же команду с `--scenario water-posting-race`. Две вкладки готовят одинаковый проект с водой. Стенд удерживает оба запроса на вставке временной строкой для ключа синтетического периода, сверяет два допуска и откатывает временную строку. Первый `PASS` подтверждает ответы `Posted` и `Replayed` с одним идентификатором и снимком. Второй подтверждает две ожидавшие вставки, три начисления и три обязательства на суммы 480, 25 и 50 грн, два допуска Platform и связь сохранённого периода с одним из них.

Режим `--scenario water-stale-posting` меняет синтетическую ставку с 20 до 24 грн/м³ после предпросмотра. Старое подтверждение получает `StalePreview` и 409. Перед новым расчётом стенд сверяет отсутствие периода, начислений и обязательств в Community и один допуск Platform. Первый `PASS` подтверждает отказ, новое проведение 60 грн за воду и прежние ссылки на показания. Второй подтверждает один сохранённый снимок, три начисления и обязательства, а также привязку периода к допуску с новым отпечатком.

Режим `--scenario water-billing-isolation` создаёт два синтетических сообщества и работает в одной сессии. Сначала браузер проводит период во втором сообществе, чтобы проверить доступ к существующей истории. После отзыва проведения там сохраняются предпросмотр и история, подтверждение получает 403. После отзыва чтения финансовые разделы скрыты, предпросмотр, список, история и сверка получают 403. В первом сообществе проведение и сверка доступны, запрос с идентификатором периода второго сообщества получает 404. Второй `PASS` подтверждает по одному периоду, три связанных обязательства и один допуск Platform в каждом сообществе.

## Частичная оплата воды

## Ручной учёт электроэнергии I‑2

Переиспользуйте участок из синтетического реестра. Установите `electricity_enabled` у тестового сообщества и `can_read_electricity` у оператора. Проверьте конфликт за ту же дату, дату до начала установки и значение, противоречащее соседним. Войдите заново и сверьте результат. Уберите основание признания и повторите запись в той же сессии. Для замены включите `can_replace_electricity` и задайте тестовое `electricity_replacement_basis`. Проверьте, что показание старого прибора на дату замены отклоняется, а запоздалое показание до границы можно внести после явного выбора старой установки. Для проверки двух регистров выберите участок без установки и при регистрации прибора укажите «День і ніч». Внесите дневные и ночные показания на две одинаковые даты. Сверьте обе разницы и их сумму. Затем внесите промежуточное значение только для одного регистра. Раздельные оценки обновятся, а сумма для прежнего интервала исчезнет. Проверьте повтор и конфликт в одном регистре и отказ для суммарного канала. Ранее зарегистрированные суммарные приборы по-прежнему принимают показания без выбора регистра.

Перед миграциями Platform `015` и Community `011` остановите старый Web. После миграций запустите новый образ. Новый Web передаёт режим и канал при записи допуска, включая запросы по прежнему HTTP API.

В форме «Зареєструвати загальну точку» укажите название, измерительную границу, обозначение прибора и дату установки. Внесите два показания. Переключитесь между общей точкой и индивидуальным участком и сравните отдельные интервалы. Повторите создание с тем же названием, затем сбросьте право создания и повторите запрос в той же сессии.

При регистрации и замене заполните модель, серийный номер, место и дату монтажа. При наличии пломбы укажите её номер. Дату начала измерительного использования укажите отдельно. На синтетической точке ТП задайте коэффициент 40 и признайте исходные показания 100 и 103. Проверьте разницу 3 и расчёт 120 кВт·ч. При замене задайте коэффициент 1 и проверьте расчёт новой установки и сохранность 120 кВт·ч в старой. Для двух регистров сверяйте преобразованные разницы и их сумму только на совпадающих интервалах.

### Предпросмотр импорта электроэнергии при проверке справки

Сценарий `--scenario electricity-installation` также проверяет справку импорта и синтетический CSV, составленный в памяти из уже признанного тестового показания и строки с неверной датой. Ожидаются «Уже записано» и «Некоректна дата», отказ неверного заголовка и клиентский лимит 128 КиБ. Смена файла должна убрать прежние предпросмотр и кнопку применения. Применение не вызывается. В этом сценарии разрешён только POST точного пути предпросмотра выбранного сообщества; все остальные запросы записи блокируются. Дополнительный снимок руководства импорта сохраняется с суффиксом `.import.png`. Используйте существующее синтетическое сообщество электроэнергии с показаниями; действующие назначения доступа сохраняются.

### Справка замены электросчётчика

Тот же сценарий `--scenario electricity-installation` проверяет общий текст справки замены и её руководства, форму только у оператора с правом замены на действующей установке, сообщения о закрытии/причине замены и отсутствующих границах в существующей истории. Для полной проверки истории используйте синтетическую точку со старой и новой установками после уже выполненной замены. Новая замена не вызывается; блокировка запросов записи сохраняется с прежним исключением для предпросмотра CSV. Снимок нового руководства имеет суффикс `.replacement.png`.

### Справка деревьев электроэнергии

Тот же сценарий электроэнергии требует существующие синтетические редакции 01.03.2026 и 02.03.2026 с девятью точками, тремя корнями на двух ТП. Проверяет отсутствие редакции на 01.01.1900, пути обеих редакций в интерфейсе относительно ответа чтения, видимость редактора согласно действующему праву и локальное копирование девяти положений у оператора. Публикация не вызывается. Проверяются общий текст справки/руководства, Escape/фокус и окно 390 px; снимок имеет суффикс `.topology.png`. Назначения прав и топология стенда не изменяются.

Если у существующего тестового оператора нет права публикации, добавьте `--topology-editor-ui` к этому сценарию для отдельной проверки локального копирования. Только флаг `canPublishElectricityTopology` в ответе браузеру становится истинным; серверные назначения не меняются. Это проверка редактора интерфейса, не серверной авторизации публикации. POST публикации по-прежнему блокируется. Обычные прогоны без флага подтверждают отсутствие редактора при фактических правах.

Прогон сверяет даты и точные значения таблиц показаний и потребления с данными чтения, видимость кнопки признания по фактическим правам, общий текст справки/руководства, Escape/фокус, окно 390 px и снятие выбора сообщества. ### Предпросмотр импорта показаний воды

### Справка замены водомера

Проверяет даты/причину, общий текст справки и руководства, форму по действующему праву, Escape/фокус и окно 390 px. Дополнительный снимок имеет суффикс `.replacement.png`. Новая замена не вызывается; серверные назначения и данные не меняются. Серверная авторизация этим режимом не проверяется. Прежнее исключение POST предпросмотра CSV сохраняется, остальные запросы записи блокируются.

## Ограничение накопления ресурсов

Перед каждой сборкой сценарий удаляет завершённые временные контейнеры с меткой и именем стенда, сохраняет образы всех существующих контейнеров и три самых свежих образа Community OS. Промежуточные образы новых сборок имеют отдельную метку и очищаются адресно. Базовые контейнеры стенда и PostgreSQL защищены от этой очистки. Именованные тома сохраняются.

Проверка и очистка вручную:

```powershell
python ops/test-stand/retention.py
python ops/test-stand/retention.py --apply --check-space
```

Первая команда показывает кандидатов. Вторая выполняет очистку и проверяет запас не менее 2 ГиБ на файловой системе запущенного PostgreSQL. Перед первой сборкой нового стенда, когда контейнера PostgreSQL ещё нет, эту проверку проводит оператор на самом сервере. Применяйте команды к Docker-порту нужного стенда через параметр --docker-port.

Новые контейнеры стенда получают ротацию журналов по 10 МиБ, до трёх файлов. Временный контейнер проверки справки удаляется после завершения. Действующие контейнеры и их образы сохраняются. Промежуточные образы старых сборок очищаются только при отсутствии тегов, digest и ссылок контейнеров и при наличии в истории команды сборки с путём src/CommunityOS. Остановленные контейнеры без меток и устаревшие запущенные экземпляры сначала проверяются отдельно. Общая очистка томов в этот порядок не входит.

При отказе по месту сначала освободите пространство средствами Docker, затем проверьте pg_isready, выполнение SELECT 1 и чтение синтетических данных. Возвращайте прогоны в расписание после успешной проверки.

Автоматический диспетчер Windows выполняет тот же адресный проход и проверку места после разрешения квоты до вызова модели. При отказе записывает stand-maintenance-blocked и откладывает рабочий запуск. После изменения этих сценариев обновите локальную копию обслуживания в %USERPROFILE%/.codex/community-os-dispatch/stand-maintenance.
