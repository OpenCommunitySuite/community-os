# Первый тестовый стенд Community OS

Стенд рассчитан на синтетические данные и Linux Docker на тестовой ВМ. Использует три контейнера `communityos-test-stand-{postgres,web,worker}`, отдельную внутреннюю Docker-сеть и два именованных тома для PostgreSQL и ключей ASP.NET Data Protection. Порты ВМ не публикуются. Web слушает HTTPS только на loopback контейнера. Worker запускается отдельным процессом, отправка кодов по умолчанию выключена.

## Подготовка

Нужны открытый SSH-туннель к Docker на `127.0.0.1:23750`, Python 3.11 или новее и PowerShell 7. Для сборки образа Docker на ВМ получает закреплённые базовые образы и зависимости из реестров. Образ содержит Web, Worker и собранный Platform Application. Базовые образы и PostgreSQL закреплены по digest, зависимости .NET и pnpm берутся из lock-файлов.

Создайте пустой каталог вне репозитория, доступный только доверенным пользователям. Пример для Windows:

```powershell
$cfg = Join-Path $env:LOCALAPPDATA 'CommunityOS-TestStand'
New-Item -ItemType Directory $cfg
$tag = 'communityos-test-stand:' + (git rev-parse --short HEAD)
./ops/test-stand/init.ps1 -Directory $cfg -Image $tag
python ops/test-stand/stand.py build $tag
```

Сценарий создаёт `stand.json` с тестовыми секретами, `https.pfx` с закрытым ключом и публичный `https.pem` для проверки сертификата. Сертификат действует 30 дней. Секреты не передавайте в чат и не добавляйте в репозиторий. Доступ к Docker даёт доступ к конфигурации контейнеров, поэтому туннель и учётная запись Docker предназначены только для доверенного оператора.

## Запуск и миграции

```powershell
python ops/test-stand/stand.py database (Join-Path $cfg 'stand.json')
python ops/test-stand/stand.py migrate
python ops/test-stand/stand.py up (Join-Path $cfg 'stand.json')
python ops/test-stand/stand.py status
```

Миграции выполняет отдельная учётная запись PostgreSQL в базах `communityos_platform` и `communityos_register`. Команда записывает версию и контрольную сумму каждой миграции вместе с её результатом. Повтор пропускает уже применённые версии. Изменение применённого файла приводит к отказу. Web получает ограниченную роль `stand_web`. Команда запуска печатает только UUID синтетических учётных записей, пароли остаются в локальном `stand.json`.

## HTTPS и проверка

Перед прогоном проверьте состояние стенда командой `status`. Для I‑1 используйте синтетические сообщества, операторов и формат XLSX из разделов ниже. При автоматизации повторяющейся подготовки добавьте в этот раздел команду запуска и ожидаемый результат. Пароли и другие секреты передавайте через локальную конфигурацию. При сбое указывайте шаг проверки, ожидаемый и полученный результат без содержимого выгрузок и секретов.

Оставьте локальный канал открытым в отдельном окне:

```powershell
python ops/test-stand/stand.py relay
```

Откройте `https://127.0.0.1:5443/platform/`. Канал принимает соединения только на loopback Windows и передаёт TLS через уже открытый SSH-туннель к Docker. Сверьте SHA-256 сертификата с выводом `init.ps1`. Для проверки состояния можно указать доверенный сертификат явно:

```powershell
curl.exe --cacert (Join-Path $cfg 'https.pem') https://127.0.0.1:5443/health/ready
```

Войдите как `stand-creator`. Создайте синтетическое сообщество и укажите UUID `stand-administrator`. Войдите под администратором, проверьте назначение в созданном сообществе и отказ для другого UUID. Под `stand-creator` отзовите назначение и проверьте журнал. Повтор с тем же идентификатором запроса не восстанавливает отозванное назначение.

## Остановка и повторный запуск

```powershell
python ops/test-stand/stand.py stop
python ops/test-stand/stand.py database (Join-Path $cfg 'stand.json')
python ops/test-stand/stand.py migrate
python ops/test-stand/stand.py up (Join-Path $cfg 'stand.json')
```

Остановка сохраняет контейнеры, базы и тома. Сценарий отказывается использовать контейнеры, сети или тома без метки этого стенда. Смена образа или конфигурации требует отдельно пересоздать только контейнеры стенда с сохранением именованных томов.

## Проверка живой доставки

SMTP и Telegram включаются отдельным изменением конфигурации стенда после согласования тестовых получателей. Для него нужны тестовый SMTP-сервер с STARTTLS, данные отправителя и тестовая почта, а также токен тестового бота и заранее подтверждённый личный чат. Секреты передаются через защищённое хранилище или вводятся владельцем непосредственно в закрытую конфигурацию. Worker понадобится управляемый исходящий доступ к SMTP и Telegram Bot API. Входящие порты ВМ для этого не нужны. [Роли и параметры доставки](../../docs/implementation/PLATFORM_RECOVERY_DELIVERY.md)

## Ручной реестр I‑1

Для проверки используйте закрытый стенд с синтетическими данными. Соберите новый образ Web и Worker и примените миграции командой `migrate`. Для обновления существующего стенда пересоздайте только контейнеры Web и Worker с новым образом. Сохраните контейнер PostgreSQL и тома. Команда `up` проверяет, что конфигурация существующих контейнеров совпадает с запрошенной.

Создайте два синтетических сообщества через Platform Application. Для каждого сообщества доверенный оператор стенда добавляет строку `platform_provisioning.register_availability` с его `community_id` и установленными `community_active` и `register_enabled`. В `platform_provisioning.register_operator` укажите идентификаторы сообщества, тестовой учётной записи и связанного с ней синтетического субъекта. Для действующей связи установите `linked`. Задайте права `can_read` и `can_add` отдельно. Для внесения записи укажите синтетическое основание в `addition_basis`. Тестовые назначения выполняются отдельно от назначения технического администратора.

Войдите через `/platform/` под тестовым оператором и откройте `/community/` на том же локальном HTTPS-адресе. Выберите сообщество, добавьте участок с новым собственником и второй участок с отдельным счётом, выбрав того же собственника. Проверьте конфликт номера участка и номера счёта. Перезапустите Web и повторно откройте реестр. Убедитесь, что записи сохранились. Для проверки отзыва сбросьте `can_add` у оператора и повторите запрос в той же сессии. После проверки удалите синтетические назначения или отключите функцию реестра для этих сообществ.

### Подготовка импорта OSBBX

После миграций установите `can_prepare_import` в тестовом назначении оператора. В разделе «Підготовка імпорту OSBBX» загрузите синтетический XLSX с листом «Власники» и колонками «Номер ділянки», «ПІБ», «Особовий рахунок». Счета с ведущими нулями запишите как текст. Стенд принимает архивы до 2 МиБ и до 500 строк данных.

Укажите проверенное имя и ключ собственника. Повторите ключ только для участков, которые относятся к одному собственнику. Сохраните черновик, выйдите, войдите снова и откройте его из списка. Для проверки изоляции войдите под другим тестовым оператором с тем же правом и убедитесь, что первый черновик недоступен. Затем сбросьте `can_prepare_import` у первого оператора и проверьте отказ в той же сессии. Предпросмотр читает текущий реестр и не применяет план.

### Утверждение и применение импорта

В том же синтетическом сообществе создайте отдельное назначение утверждающего с другой учётной записью и другим субъектом. Установите `can_approve_import` и задайте синтетическое основание в `import_approval_basis`. Под подготовщиком сохраните проверенные решения и нажмите «Передати на затвердження». Под утверждающим выберите ту же ревизию в разделе «Затвердження імпорту OSBBX», сверяйте строки и нажмите «Підтвердити й застосувати імпорт». В отчёте сопоставьте номера строк и идентификаторы созданных записей.

Для проверки устаревания передайте ревизию и сохраните новые решения до утверждения. Для проверки конфликта добавьте в реестр участок с совпадающим номером после открытия плана утверждающим. В обоих случаях импорт не должен создать записи. Повторите успешный запрос подтверждения и убедитесь, что отчёт сохранил первоначального утверждающего. Проверьте отказ по чужому сообществу и после сброса `can_approve_import` в действующей сессии.

### Исправление привязки собственника

Используйте участок из синтетического импорта и другого существующего собственника в том же сообществе. Оператору с правом чтения задайте `can_correct_ownership` и тестовое основание в `ownership_correction_basis`. Откройте историю участка, выберите правильного собственника и укажите причину. После исправления обновите страницу. Сверьте текущего собственника, историю, лицевой счёт и исходный отчёт импорта.

Для проверки конкуренции откройте участок в двух вкладках до первого исправления. Подтвердите запросы с одной ревизией. Устаревшая вкладка должна предложить обновить запись. Сбросьте `can_correct_ownership` и проверьте отказ без повторного входа. Для проверки истории без права чтения используйте отдельного тестового оператора.

## Ручной учёт электроэнергии I‑2

Переиспользуйте участок из синтетического реестра. Установите `electricity_enabled` у тестового сообщества и `can_read_electricity` у оператора. Для настройки и признания задайте `can_setup_electricity` и `can_recognize_electricity` и отдельные тестовые основания в `electricity_setup_basis` и `electricity_recognition_basis`. В разделе «Облік електроенергії» выберите участок и зарегистрируйте установку с датой начала.

Признайте два ручных показания в кВт·ч с разными датами. Сверьте разницу и даты интервала. Повторите одно значение за ту же дату и проверьте, что число показаний не меняется. Проверьте конфликт за ту же дату, дату до начала установки и значение, противоречащее соседним. Войдите заново и сверьте результат. Уберите основание признания и повторите запись в той же сессии. Сервер должен отказать, а чтение должно остаться доступным.

Для замены включите `can_replace_electricity` и задайте тестовое `electricity_replacement_basis`. На участке с установленным счётчиком укажите новое обозначение, дату начала его измерительного использования и причину. Выберите обе установки в истории и сверьте показания отдельно. Проверьте, что показание старого прибора на дату замены отклоняется, а запоздалое показание до границы можно внести после явного выбора старой установки. При отсутствии граничных данных оценка через замену не формируется.
